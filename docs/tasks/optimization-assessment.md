## 1. 评估目的、依据与口径

### 1.1 目的

基于本次测试（自动化回归、离线 Mock E2E、真实模型链路部分执行）的实际证据，结合现有代码勘察与既有设计文档，梳理平台当前的强项、短板与风险，按优先级给出可落地的优化方向，并明确每条建议的验收要点。本文回答三个问题：

1. 现在哪些能力是已实现且被证据验证过的，哪些只是设计在册、实现未闭环；
2. 本次测试暴露的阻塞与隐患，根因落在模型层、执行层还是工程化层；
3. 后续迭代应该先做什么、后做什么，哪些已在既有规划内、哪些是本次新增。

### 1.2 依据材料

- 测试证据：[`test-report.md`](./test-report.md)（A/B/C 三组执行记录、指标、缺陷 D-01）、[`test-case-checklist.md`](./test-case-checklist.md)（用例追溯与结果回填）。
- 代码勘察：`backend/app/engine/`（`agent_loop.py`、`runners.py`、`context.py`、`orchestrator.py`）、`backend/app/tools/registry.py`、`backend/app/models/budget.py`、`backend/tests/`。
- 既有设计与已知限制：[`../设计规格说明书.md`](../设计规格说明书.md)、[`../迭代优化-可靠执行.md`](../迭代优化-可靠执行.md)、[`../评审与测试体系设计.md`](../评审与测试体系设计.md)、[`../模型接入配置设计.md`](../模型接入配置设计.md)、README §8「已知限制（M1 计划）」。

### 1.3 分级口径

| 级别 | 定义 | 处置原则 |
| --- | --- | --- |
| P0 | 阻塞真实模型闭环或导致运行无法终态，直接影响主链路可用性 | 近期优先解决，先打通「真实模型一次跑通」 |
| P1 | 影响可靠性、可维护性或质量保障体系，虽不阻塞当前离线演示，但放大真实使用风险 | 中期补强，围绕执行可靠性与评审/测试体系 |
| P2 | 工程化、可观测性、体验与工程规范类改进 | 随迭代排期推进，不影响主链路正确性 |
| P3 | 规模化、平台化与远期方向，依赖前序能力成熟 | 列入 backlog，暂不投入 |

## 2. 现状评估

### 2.1 编排引擎与可靠执行

**已验证强项**

- 依赖调度、波次分层、关键路径计算由服务端确定性完成，PM 只提议任务、不裁决依赖；环、缺依赖、章节不可追溯均有错误码与定位。
- 可靠执行一期机制齐备：进程级并发闸门、节点级超时、指数退避 + 抖动、attempt 心跳、取消收据、运行指标聚合；离线 Mock E2E 与 durability 回归覆盖了闸门、超时、退避、seq 缓存与取消路径。
- 人工门一等公民：通过 / 驳回（反馈 + 目标节点回退）/ 编辑后通过；门挂起不占协程，重启后待决门原样保留。
- 工件链版本化落盘，front-matter 记录状态与输入；事件 `(run_id, seq)` 唯一且单调，状态迁移先写事件。

**现存问题与缺口**

- **批内隐式屏障**：当前按「最小波次批次」`gather`，下游要等同批最慢者结束才进 ready，并非「依赖就绪即跑」。评审/测试钩子无法穿插进波次，与测试体系设计 §7.1 的目标存在差距。
- **重试粒度粗**：失败是整节点重来，没有 attempt 级 checkpoint / 幂等键；崩溃恢复会丢弃未回执的 attempt。
- **并行工作区无隔离**：同一波或跨波并行的 dev 节点共享 `runs/<run_id>/workspace`，无文件级锁；多 agent 并行改同一文件时后写覆盖先写。
- **单进程语义**：并发闸门、seq 缓存、心跳仲裁都在进程内，未做跨进程租约，多 worker 部署需要外部锁或 DB 租约。
- **死锁与恢复**：无节点可执行且未全部完成时判死锁并置 failed；恢复逻辑覆盖 running 作废、waiting_human 保留、未终态重入队，但缺 attempt 级续跑能力。

### 2.2 模型接入与 Agent 执行

**已验证强项**

- Provider / Model / Binding 三层分层清晰：协议、URL、密钥、并发归供应商；模型名、窗口、能力、价格归模型；角色模板绑定到模型。
- 协议适配器覆盖 `openai_chat`（完整流式 + 工具调用）；无原生工具能力的模型自动降级为提示词 JSON 协议；密钥 Fernet 加密落盘，接口只回显末四位。
- 连接测试可带模型真发一轮对话回传延迟；模型发现支持 `GET /models` 拉取与批量导入去重；429 / 5xx / 网络错误有一次退避重试与中文化错误提示。
- 本次真实模型接入验证：DeepSeek 供应商连接测试 `ok=true`，11 个角色模板全部绑定到可用模型，无「尚未配置模型」报错；文档链与前 4 道人工门在真实模型下跑通。

**现存问题与缺口（本次测试重点暴露）**

- **dev 节点收尾契约不稳（P0，缺陷 D-01）**：执行层把「是否调用 `finish` 工具」作为 dev 节点完成的硬判定；模型在多轮工具调用后空回复（无 `tool_calls`、content 为空）时，循环直接按普通最终回复返回，执行层再判为「未调用 finish，视为未完成」。同模型 `dev_T1.1` 一次通过、`dev_T2.1` 连续 3 次卡在同一收尾问题，说明问题集中在长上下文 + 多轮工具后的收尾遵循度，而非接入链路不通。
- **上下文历史无裁剪落地**：执行循环内消息历史只增不减；代码层只对输入工件做 token 截断，README §4.5 描述的「工具截断 → 历史摘要 → 工件降为引用 → 转人工」降级链在执行层尚未完整实现。本次 `dev_T1.1` 单节点输入 token 已达 18.7 万，上下文膨胀会放大后续节点的收尾失稳与预算消耗。
- **错误分类粒度不足**：预算耗尽（`BudgetExceeded`）与「未调 finish 未完成」在节点失败记录里混在一起，重试策略与人工判读难以直接区分根因；本次 attempt 2 即叠加了一次预算耗尽，attempt 3 仍是收尾问题。
- **模型能力与角色未做运行时分级兜底**：角色绑定只记录默认模型，运行时不区分文档类角色与 dev/评审类角色对工具遵循度、输出结构化程度的不同要求；工具遵循较弱的模型被绑到 dev 角色时，缺少前置冒烟校验与运行时降级提示。
- **适配器能力不齐**：Anthropic / Gemini 适配器暂为伪流式；JSON 协议降级路径下，模型格式错误靠「再提示一轮」纠正，没有结构化重试或字段级修复。

### 2.3 测试与质量保障

**已验证强项**

- 后端 pytest 回归 **87 passed**，覆盖图解析、任务行格式、front-matter、预算估算、门禁通过/驳回/升级重试、供应商与模型 CRUD、模板绑定校验、计划校验错误码/波次/关键路径/环路径、计划 API 生成/编辑/提交/幂等/归档、并发闸门/超时/退避/seq/取消/metrics、模型发现、评审节点/阻塞回退/轮次用尽、节点动作矩阵与审计事件。
- 验收以证据为准（退出码、schema、工件），而非模型自称完成；人工门与评审回退形成闭环骨架。

**现存问题与缺口**

- **无真实模型链路回归**：现有自动化全部基于离线 Mock 或确定性桩；没有把「账本」这类真实案例固化成可重复的 live 回归（或可切换 mock/live 的双套 E2E），本次 C 组只能手工驱动、人工回填。
- **无前端自动化测试栈**：前端把血缘、门阻挡、相位分列抽成纯函数模块，但仅靠 `typecheck` + 手工验收守护，未引入 vitest 等测试框架；画布交互、撤销栈、覆盖度计算缺自动化断言。
- **评审是启发式静态评审**：只把 workspace 文本摘要（最多 16 文件 / 2.6 万字）连同验收清单交给模型，没有真正的 diff、AST 或测试覆盖分析；阻塞问题必须带合法 `task_uid` 才触发回退，模型漏标即放行。
- **缺陷概念薄弱**：运行结果只有 pass / fail，无缺陷状态机、无分级闭环台账、无回归策略；测试目前主要由 dev 自写 unittest，缺独立 QA 角色与 `test.md` 工件（测试体系设计 §1 已列为缺口）。
- **E2E 持久化与断线场景覆盖不足**：断线重连 `Last-Event-ID` 补发、重启后待决门保留、动作 409 保护等仅有局部自动化或未在真实断连/重启场景复核。

### 2.4 可观测性与运维

**已验证强项**：metrics 端点即时聚合节点状态、attempt / 重试 / 忙碌时长 / P95、token 用量与估算成本、门等待与逐节点明细；事件流支持 SSE 与断线补发；attempt 心跳区分长任务与僵死；日志落 `logs/`。

**现存问题与缺口**

- metrics 是即时全表扫描聚合，不落库、无历史趋势，无法对比多轮运行的耗时 / 成本 / 一次通过率。
- 事件表随长 run 无限增长，未做按 run 归档或分区。
- 无模型调用级追踪（单次调用延迟、token、错误码、重试次数与根因归类）的结构化留存；失败节点的复盘主要靠人工翻 messages 与事件。
- 无告警 / 健康巡检：限流、预算逼近、attempt 长期心跳停滞等情况只在 metrics 里被动查看。

### 2.5 前端与交互体验

**已验证强项**：运行详情命令栏 / 阶段圆盘 / 执行图 / 运行账本 / 内联裁决卡；编排工作台四视图（任务详情 / 流程监控 / 活动 / 执行图），画布坐标落库、依赖增删带环检测、撤销栈、设计覆盖率、快照回滚。

**现存问题与缺口**

- 单包体积约 1.35MB（AntD + xyflow），未做路由级代码分割。
- 撤销栈随页面刷新 / 切换计划清空，只在当前浏览器生效；删除任务不可撤销；画布坐标不进快照，历史版本恢复不恢复布局；连线未适配触屏。
- 多波次大图在默认缩放下需要横向滚动；任务详情等视图共用右侧内容区，宽屏利用率有限。

## 4. 分优先级优化建议

### 4.1 P0 近期：先打通真实模型闭环

> 目标：让一个真实模型运行能从 idea 跑到 `finished`，产物可被 CLI / unittest 现场验收，并把这套链路固化成可重复回归。

**4.1-1 强化 dev 收尾契约，并对空回复做兜底续步（对应 R-01）**

- 现状：dev 完成判定只认 `finish` 工具；模型空回复或纯文本结束时，循环不区分「正常答完」与「没收尾」，直接判失败。
- 建议方向：
  - 在 dev 系统提示词与工作区规则里把收尾写成硬约束：完成实现与测试后**必须**调用 `finish` 工具，禁止用纯文本结束；说明 `finish` 需包含改动文件、测试命令与结果、遗留问题。
  - 在执行循环增加兜底：当 dev 类节点收到「无工具调用且内容为空 / 明显未完成」的回复时，不直接终判，而是追加一条纠偏提示（提醒还需调用 `finish` 收尾，或继续未完成的工具步骤）再续一步；仅在兜底后仍未收尾时才记失败。
  - 把失败原因显式归类为「未调 finish」「空回复」「跑满步数」「预算耗尽」「工具异常」，写入 attempt 错误与事件，便于重试与复盘区分根因。
- 预期收益：降低模型偶发空收尾导致的整节点失败，减少无谓重试与转人工。
- 验收要点：同一账本案例，dev 节点在目标模型下稳定以 `finish` 收尾；失败记录里能看到明确根因归类；兜底续步不改变正常节点的行为。

**4.1-2 落地上下文裁剪与历史压缩（对应 R-02）**

- 现状：消息历史只增不减，仅输入工件被截断；长上下文推高 token 消耗并加剧收尾失稳。
- 建议方向：
  - 按 README §4.5 的预算分区落地降级链：先截断工具结果，再对早期对话 / 工具历史做摘要压缩，工件降级为章节引用；逼近窗口时主动预警，而不是等超窗或预算耗尽。
  - 工具结果（读文件、命令输出）在落进历史前按长度与相关性裁剪，长文件只保留相关片段与文件清单。
  - 为单节点 / 单角色设置输入 token 软阈值，逼近时记录告警事件并在 metrics 可见。
- 预期收益：控制单节点上下文规模，降低收尾失稳概率与成本，缓解长 run 上下文膨胀。
- 验收要点：长任务节点的历史消息在逼近窗口时被摘要 / 裁剪而非无限堆叠；metrics 能看到节点级输入 token 与裁剪事件。

**4.1-3 预算保护与错误解耦（对应 R-02）**

- 现状：run 级预算在每次调用后扣减，超限抛 `BudgetExceeded`；预算耗尽与收尾失败在失败记录中混叠。
- 建议方向：区分「预算类失败」与「执行类失败」的重试策略与人工提示；预算接近阈值时提前告警；在节点明细里分别展示预算占用、剩余与收尾状态。
- 验收要点：预算耗尽的节点不会被误判为模型能力问题；重试与人工门提示能直接指出是预算还是收尾原因。

**4.1-4 角色-模型能力分级与前置冒烟（对应 R-03）**

- 现状：绑定只记录默认模型，运行时不校验模型是否适配角色的工具 / 结构化输出要求。
- 建议方向：
  - 模型条目补充能力标签（工具遵循、结构化 JSON、长上下文、成本档），角色按要求选择：文档类可选用轻量快模型，dev / 评审类优先工具遵循与稳定性更强的模型（如本次备选 `deepseek-v4-pro`）。
  - 连接测试 / 绑定校验增加最小工具遵循冒烟：带一个一两步的工具调用小用例，确认模型能正确发起工具调用并收尾；不通过时在绑定页给出明确提示。
- 验收要点：把弱工具遵循模型绑到 dev 角色时能被提前发现；dev / 评审角色优先匹配能力达标模型。

**4.1-5 固化真实模型回归用例（对应 R-04）**

- 现状：C 组案例靠手工创建运行、手工过门、人工回填；没有可重复执行的回归脚本。
- 建议方向：以 `ledger-idea.txt` 案例为基础，做成可切换「Mock / Live」两套模式的 E2E 脚本：Mock 模式跑确定性桩用于 CI 回归，Live 模式用真实模型做周期性抽样验收；把 5 门检查点、CLI 演示、unittest 全绿固化为断言或检查清单。
- 验收要点：一条命令可重复跑通案例；Live 模式结果与产物能自动留痕，回填到清单 / 报告的固定位置。

### 4.2 P1 中期：可靠性与质量体系补强

**4.2-1 拆分批内屏障，改为事件驱动解锁（对应 R-05）**

- 建议方向：调度从「波次批次 gather」改为「依赖就绪即跑、单节点完成即唤醒调度」，让评审 / 测试钩子能穿插进依赖图；对齐测试体系设计 §7.1。
- 验收要点：同波内慢节点不阻塞已就绪的下游节点；钩子节点在其依赖完成后及时触发；并发闸门仍然生效。

**4.2-2 attempt 级 checkpoint 与幂等重跑（对应 R-06）**

- 建议方向：为可重入的工具步骤记录 checkpoint 与幂等键，崩溃后从断点续跑而非整节点重来；工件写入结果可校验、可重放。
- 验收要点：执行中杀进程重启后，已完成的工具步骤不重复执行；未回执 attempt 可定位到续跑点。

**4.2-3 并行工作区隔离（对应 R-07）**

- 建议方向：并行 dev 节点按任务隔离目录或 worktree，写入前检测冲突；合并节点负责汇总与冲突提示；短期先在文档与校验层提示「任务按文件拆分」，中期落地隔离与合并。
- 验收要点：并行节点改不同文件互不覆盖；改同一文件时有冲突提示而非静默后写覆盖。

**4.2-4 评审证据升级（对应 R-08）**

- 建议方向：评审从纯文本摘要升级为基于 diff / 文件清单 / 测试覆盖的独立证据；结构化 issues 保留 `task_uid` / 文件 / 级别 / 建议；对「应发现而漏标」的情况补充兜底复核（如高风险任务二次评审）。
- 验收要点：评审结论能对应到具体改动与测试结果；阻塞问题可回溯到文件与任务；漏标有机制兜底。

**4.2-5 补缺陷状态机与独立测试角色（对应 R-09）**

- 建议方向：落地缺陷台账与状态机（发现 → 分级 → 指派 → 修复 → 回归 → 关闭）；引入 QA 角色与 `test.md` 工件，测试用例前置到设计 / 任务阶段；形成回归策略与版本基线。
- 验收要点：运行发现的问题可登记、流转、回归与关闭；任务清单带可执行验收用例，dev 实现与测试职责分离。

**4.2-6 前端测试栈（对应 R-10）**

- 建议方向：引入 vitest，先覆盖 `graphLayout` 等纯函数（血缘、门阻挡、相位分列、覆盖率计算），再逐步补关键交互（门阻挡、撤销、依赖增删校验）。
- 验收要点：纯函数有单元断言；关键交互有组件级或端到级用例；CI 可跑前端测试。

### 4.3 P2 工程化、可观测性与体验

**4.3-1 metrics 落库与历史趋势（对应 R-11）**

- 建议方向：运行结束后把节点耗时、token 成本、一次通过率、返工次数、门等待等指标落库，支持多轮对比与趋势查看；必要时接入 Prometheus 等外部指标系统。

**4.3-2 事件归档与调用级追踪（对应 R-11、R-12 之外）**

- 建议方向：事件表按 run 归档 / 分区；留存每次模型调用的延迟、token、错误码、重试次数与根因归类；为失败节点提供结构化复盘视图；对预算逼近、限流、心跳停滞增加被动告警。

**4.3-3 前端工程与体验优化（对应 R-12）**

- 建议方向：路由级代码分割减小首包；快照纳入画布坐标；评估删除任务的撤销能力；大图布局与宽屏利用优化；连线适配触屏。

**4.3-4 协议适配器补齐（对应 R-13）**

- 建议方向：Anthropic / Gemini 补真流式与工具调用；JSON 协议降级增加结构化解析修复与字段级重试，减少格式错误带来的空转。

### 4.4 P3 远期：规模化与平台化

- 跨进程租约 / DB 心跳仲裁，支持多 worker 部署；容器化执行与沙箱隔离；MCP 工具接入；记忆向量检索与记忆面板；Twin 数字分身、多 run 调度面板；分布式协作模式（见 [`../分布式执行模式设计.md`](../分布式执行模式设计.md)，当前封存仅设计）。
- 这些方向依赖 P0/P1 的执行可靠性、隔离与可观测能力成熟后再排期。

## 6. 复测与验收建议

### 6.1 真实模型复测前置条件

1. dev 收尾契约按 §4.1-1 强化，空回复兜底与失败根因归类落地（或先切换到工具遵循更强的模型验证）。
2. 上下文裁剪 / 预算保护至少覆盖单节点历史压缩与预算-收尾错误解耦。
3. 测试连接 / 绑定页能确认目标模型的工具遵循能力达标。
4. 保留离线 Mock 基线 run `4fc784fd76f9` 作为对照，不被复测覆盖或清理。

### 6.2 建议通过标准（对齐 test-report §7 放行条件）

- 真实模型运行从 idea 跑到 `finished`：文档链、人工门、并行 dev、verify、评审 / 验收门链路完整。
- dev 节点以 `finish` 收尾，配套 unittest 实际运行退出码 0；账本 CLI `add` / `list` / `summary` 现场演示通过（总额、笔数、分类与验收清单一致）。
- 节点失败记录根因可区分；长节点上下文与预算在阈值内；事件 seq 唯一、指标齐全。
- 自动化回归保持全绿；新增前端 / 回归用例不破坏既有行为。

### 6.3 建议补充的回归项

- 断线重连 `Last-Event-ID` 补发的真实断连场景；重启后待决门与工件保留；节点动作 409 / 终态 run 保护。
- 模型限流（429）与超窗场景的降级与人工提示；并行节点文件冲突的冲突提示。
- 评审漏标与阻塞回退的正向 / 反向用例。
