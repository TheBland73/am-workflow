## 2. 目标行为（走查剧本）

以 `docs/tasks/ledger-idea.txt` 为输入，mock 模型下讨论阶段应发生：

```
idea(PASS) → discuss_pro        R1 主张：输出「目标与非目标/首批范围/技术路线 2-3 选项对比/关键假设/风险缓解」骨架（工件 v1）
          → discuss_con         R1 质疑：读主张，输出质疑 Q1..Qn（每条=质疑理由+建议动作；追加进工件 v2）
          → discuss_response    R2 主张回应：读质疑，逐条回应（采纳/不采纳+理由；追加进工件 v3）
          → discuss_mod         蒸馏：读全文，追加「共识蒸馏」章（工件 v4，终版结构）
          → proposal（现有，inputs=[idea, discussion] 不变）
```

- 每个发言节点独立 attempt、独立 `node_token` 流（前端日志抽屉天然可看发言过程）。
- 轮次上限：本期固定 2 轮（R1 交互 + R2 回应 + 蒸馏），不做可配置循环——通用"讨论循环节点"留 M2。
- 预算：每节点 `max_steps=3`（无工具，一次调用即完）；讨论阶段 token 约为原 2 节点方案的 1.8–2 倍，属预期。

## 3. 角色模板变更（`backend/app/agents/templates/roles.py`）

### 3.3 新增 `discuss_mod`（追加到 ROLES 列表，放在 `discuss_con` 之后）

```python
{
    "role_key": "discuss_mod",
    "name": "讨论主持人",
    "system_prompt": (
        "你是讨论环节的主持人（裁判）。通读讨论稿全文（主张、质疑、回应），只做蒸馏裁决，不添加新观点：\n"
        "输出「共识蒸馏」部分，结构固定：\n"
        "## 共识蒸馏\n"
        "### 共识\n- C1、C2……每条注明依据（必须引用前文发言原文，用 > 引用块）\n"
        "### 分歧（保留）\n- D1、D2……每条 = > 引用质疑原文 + > 引用回应原文 + 状态（未决 / 主持人裁决+裁决理由）\n"
        "### 证据\n- 讨论中引用过的事实/约束/数据，去重汇总\n"
        "### 未决项\n- 需要人拍板的问题（写入 questions[]，格式：- [ ] 问题……）\n"
        "纪律：分歧不得抹平；未决项不得替人做决定；引用原文必须与讨论稿逐字一致；"
        "若讨论稿各部分齐全，蒸馏部分控制在 800 字以内。"
    ),
    "tools_json": DOC_TOOLS,
    "memory_scope": "agent",
    "max_steps": 3,
}
```

> 提示词纪律对应[调研报告 §2.1 原则 7](../research/前沿技术调研与技术选型.md)（Agents meeting 五步协议：裁判引用证据，分歧保留）与调研 §6.3"结论必须引用原文"（防"三个 agent 都同意但读了同一个错误来源"）。

## 4. 模板编排变更（`templates/sdlc_workflow.json`）

在 `discuss_con` 与 `proposal` 之间插入 2 个节点，并把 `proposal.deps` 从 `["discuss_con"]` 改为 `["discuss_mod"]`：

```json
{
  "key": "discuss_response", "type": "AGENT", "name": "讨论·回应", "phase": "discussion",
  "deps": ["discuss_con"], "assignee": {"role": "discuss_pro"},
  "config": {"artifact": "discussion", "append": true,
             "instruction": "阅读讨论稿中的「质疑」部分（Q1..Qn），逐条回应：采纳/不采纳 + 理由 + 调整后的方案。输出「回应」部分并追加到讨论稿。"}
},
{
  "key": "discuss_mod", "type": "AGENT", "name": "讨论·主持人蒸馏", "phase": "discussion",
  "deps": ["discuss_response"], "assignee": {"role": "discuss_mod"},
  "config": {"artifact": "discussion", "append": true,
             "instruction": "通读讨论稿全文，追加「共识蒸馏」部分：共识 / 分歧（引用原文，保留分歧）/ 证据 / 未决项。"}
}
```

注意三点：

1. `discuss_response` 复用 `discuss_pro` 角色（同一身份两轮出场，轮次差异全在 `instruction`）——这是"三方"而不是"四方"。
2. `discuss_con`/`discuss_response`/`discuss_mod` 的 inputs 都走 `DEFAULT_INPUTS["discussion"]=["idea"]`，但 **`_run_doc_agent` 对 append 节点会自动带上工件旧文**（`previous` 拼接发生在写入侧，读取侧靠 `build_user` 注入的 inputs）——**核查**：`discuss_con` 现在能读到讨论稿全文是因为工件全文也在 prompt 里吗？事实是：`build_user` 注入的是 `inputs` 列出的工件（idea），而讨论稿旧文通过 `append` 逻辑只拼在**输出**侧。若实测发现 `discuss_con` 看不到主张原文，把 `discuss_con`/`discuss_response`/`discuss_mod` 的 `config.inputs` 显式改为 `["idea", "discussion"]`（模板里写上即可，`_run_doc_agent` 优先取 config.inputs）。**这一条是实现时必须先用 mock 跑通验证的第一件事。**
3. phases 不变（仍在 `discussion` 阶段）；`phase_entered` 事件不受影响。

## 5. discussion.md 目标结构（工件契约）

```markdown
---
id: <run_id>-discussion   # 以 artifacts/store.py 实际序列化为准（{run_id}-{kind}）
kind: discussion
status: draft          # 过方案确认门后 approved（现有机制）
version: 4             # 每个发言节点写一版，version 递增
inputs: [idea]         # kind 列表（非版本号）
created: 2026-11-22
---

# 多方讨论记录

## 主张（R1 · discuss_pro）
<目标与非目标 / 首批范围 / 技术路线对比 / 关键假设 / 风险缓解>

---

## 质疑（R1 · discuss_con）
- Q1 …（质疑理由 + 建议动作）
- Q2 …

---

## 回应（R2 · discuss_pro）
- Q1：采纳/不采纳 + 理由 + 调整后的方案
- Q2：…

---

## 共识蒸馏（discuss_mod）
### 共识
- C1：…（依据：> "主张原文引用"）
### 分歧（保留）
- D1：> "质疑原文" ↔ > "回应原文" → 未决 / 裁决：…（理由）
### 证据
### 未决项
- [ ] 需要人拍板的问题……
```

实现要点：章节标题由各节点 `instruction` 指定输出（模型生成），不做程序改写；`---` 分隔线是 `append` 机制自动加的，不要在提示词里要求模型输出分隔线。工件版本按节点写入递增（现有 `write_artifact` 行为），**不合并版本**——版本链就是发言历史，前端工件抽屉可回看每一轮。

## 7. 澄清联动（小改动）

设计规格 §5.2 的"澄清强制门"：讨论/PM 输出含 `questions[]` 时转人工门内容。主持人蒸馏的「未决项」就是 questions 的来源之一。**现状：后端没有任何 questions 处理逻辑（已核查）**——本工单实现：在 `gates.py` 为 `gate_proposal` 建门时，从 discussion 工件提取「未决项」条目并拼进门卡描述（改动 ≤5 行）。验证：mock 蒸馏输出未决项 → 方案确认门卡片描述含该问题。
