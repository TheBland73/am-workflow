## 2. 从老师课件提炼的设计原则（本报告的方法论基线）

### 2.1 编排侧（《多Agent协作与编排》，赵筠哲）

编排器管三件事：**控制流**（谁决定下一步）、**上下文**（信息怎么流动）、**状态**（出错后以什么为准）。模型只是其中一种节点。

1. **控制流谱系**：代码写的图（LangGraph/n8n）→ 模型的循环（Ralph、/goal）→ 模型写脚本+运行时执行（journal/前缀重放）→ **任务账本**（任务表+依赖+认领+信箱，Agent teams/Orca）。所有走到多 Agent 的系统，最后都长出了一本外部任务账本 → 我们的编排核按"任务账本"形态设计。
2. **完成要由别人判断**：干活的模型说了不算；完成需要证据（测试退出码、schema 校验），状态需要一本只追加的账本。
3. **循环必须有上限，分支必须有可检查的条件**：返工最多 N 轮，超限交给人；条件由程序判定（退出码/schema/字段齐全）。
4. **少用 subagent，拆分要有证据**（Anthropic 2026-10-22）：先建强单 Agent 基线；agent 的边界跟着上下文划，不跟着部门划；每合并/拆分一次就跑端到端评测。
5. **交接是有损的**：返回值丢过程、消息丢上下文、任务表丢决策理由、共享文件有并发风险。对策是**让交接物变厚**——案卷随任务走、审查问题直达负责人、分歧必须引用原文。
6. **需求是一条贯穿始终的线**：版本化 spec 是所有 Agent 的共享上下文与验收基线；改需求=带版本和理由的补丁；**Agent 可以提议变更，不能批准自己的补丁**。
7. **Agents meeting 五步协议**：讨论（各持立场）→ 蒸馏共识（裁判引用证据，分歧保留）→ proposal（结论+证据+未决项）→ 需求化（版本化+验收条件）→ **反向确认**（从需求生成验收用例，对照最初目标），N 轮不收敛交人。
8. **Easy Workflow 案例（Spec is all you need）**：声明式 Spec 编译出运行图+画布+工人上下文包+校验报告；一处声明三处生效；画布结构编辑只生成 Spec 补丁；程序、小模型、Agent 各管各的。

### 2.2 记忆侧（《Agent Memory System》《Agent Memory Engineering》，张琰翔）

记忆系统回答三问：**存储**（记什么/存成什么形式）、**检索**（怎么找/什么时候找）、**维护**（何时写/变了怎么办/多了怎么办）。

9. **三类记忆**：事实（semantic）/ 经历（episodic）/ 做法（procedural，即 Skill）。
10. **写入五步流水线**：Trigger → Extract → Validate → Reconcile（对账旧记忆）→ Commit；原子化（一条记忆只承载一个可更新的判断）；每条带 schema：type / content / scope / source_event / status / evidence / valid_from。
11. **正文、检索目录、原始依据三件套**，靠记忆 ID 关联，更新必须同步索引。
12. **多租户作用域就是"角色记忆"的答案**：user_id 区分人、session 区分会话，可扩展到 project / agent / 单次任务作用域——角色私有记忆=scope:agent，共享黑板=scope:project。
13. **检索不是 Top-K**：BM25 关键词 + 语义向量 + 实体/时间多路合并去重重排；先过滤作用域与有效性，再控制 token 预算。
14. **冲突处理**：分清"改了规则"还是"只管今晚"；只追加 + 按时间挑当前有效；失效不删除。
15. **记忆是参考不是硬规则**：拦人靠 hook/权限；历史文本不可升级成系统指令（注入防护）；越能长期影响 Agent 的信息，写入与使用门禁越严格。
16. **后台整理（dreaming）**：空闲期合并重复、提炼经验为 Skill；改动可自动生效或先让人审。
17. **记忆不是目的**：评估看任务成功率、重复错误率和可控成本，不是"存了多少"。

### 4.3 记忆系统

| 项目 | stars(实测) | 架构 | 与我们需求的匹配 |
|---|---|---|---|
| Mem0 | 68.9k | 记忆中间件：`add()/search()`；ADD-only 写入+时间过滤；**user/agent/run 三级作用域天然对应角色隔离**；组件可替换（LLM/Embedding/Store） | 最接近；但抽取策略是通用的，我们要按角色定制写入策略 → 用其接口约定，自研实现，Mem0 作可插拔后端 |
| Letta (MemGPT) | 25.4k | 记忆是 agent 运行时的一部分，agent 自编辑记忆块；共享 block 的 `read_only` 是**块级全局属性而非 per-agent**（做不出"PM 可写、开发只读"），且官方已声明 **memory blocks 弃用**、转向 shared memory repositories | 排除：自带运行时会绑架编排核+权限粒度不足+机制方向被官方弃用 |
| Graphiti/Zep | 32.8k | 时序知识图谱：实体+带有效期的事实+episode 溯源；沿关系走；**group_id 命名空间是现成的两层作用域**（一实例多 group，检索传列表即跨层查） | 关系密集场景才划算，需图库运维，且 group_id 过滤≠授权；借鉴"带有效期、失效不删除、可溯源" |
| memU | 14.6k | 宿主 Agent 自理记忆：agent 产出 memory.md/SKILL.md 可读资产，服务只做持久化/Embedding/检索（commit_results / progressive_retrieve） | **与我们最契合的哲学**：记忆是可读资产，人能看能改；写入决策留给宿主 agent |
| **Hindsight** (vectorize-io) | 60.9k | retain/recall/reflect 三操作；四路混合检索（语义+BM25+图+时间）+RRF 重排；**0.8B 开源判决模型**做写入门控；后台自动把事实巩固成**带证据引文+proof count** 的 observations；**bank 严格隔离**（每角色/每项目一个 bank，应用层管权限）。MIT、Python、高频活跃 | **最完整且最轻的引擎候选**：pip / 单容器 / embedded 三档部署，机制与课件五步同构；但 2026 新项目生态尚浅（官方对比分数为自报），只作我们 MemoryService 的可插拔引擎 |
| Cognee | 33.3k | 知识图谱+向量，全嵌入式（LanceDB+本地图库 LadyBug+SQLite），活跃 | 零外部服务的图谱路线备选；图谱构建/维护成本在课程规模下收益存疑 |
| LangMem | 1.8k | 库非服务；依附 LangGraph BaseStore，多级命名空间 `("org", user, role)`；活跃 | 命名空间分层范式参考；绑定 LangChain 生态、社区小 |

> 关键事实（增量调研确认）：**命名空间分层人人都有，但"按角色差异化写权限"没有任何框架内建**——记忆条目自带 `scope` 字段+写入按角色 gate+读取 union 共享 scope，是我们必须自己做的一层（与课件 schema 的 scope 字段正好接轨）。Letta 共享 block 并发上 `memory_rethink` 最后写者胜，官方建议单 owner 编辑其余只 append。

结论：**产品层自研轻量 MemoryService**（四层作用域 + scope 字段 + 角色写门控——这层无现成实现，正是课程亮点）；**引擎层可插拔**：首选 Hindsight（判决模型=课件 Validate、observations=课件 Reconcile、bank=scope，开箱即用），备选自研 Postgres/pgvector+BM25（零新依赖，与老师 MemPlus 同构）；架构哲学保持对齐 memU（记忆是可读资产）。

### 6.2 编排引擎：自研轻量编排核（主推） vs LangGraph（备选）

| 维度 | 自研轻量编排核 | LangGraph 1.x |
|---|---|---|
| 人工门/恢复 | 自己实现（事件溯源+状态表，约 3-5 天，课件给了完整配方：确定性控制流+只追加日志） | `interrupt()`+checkpointer 开箱即用 |
| 可观测事件流 | 事件即产品，前后端事件同源 | stream 事件需再翻译一层 |
| 节点类型定制（老师产品 8 种节点） | 完全自由 | 需在图框架内模拟 |
| 学习成本 | 低（纯 Python+SQL） | 中高（State 归并/Send/interrupt 交互） |
| 框架耦合 | 无 | 有（LangChain 生态迭代快，需锁版本） |
| 评分叙事 | "我们自己实现了编排器"——与课件 Easy Workflow 案例同构 | 用了业界标准框架 |

**推荐**：自研轻量编排核。理由：①我们的流程是**结构化 DAG（类型化节点+依赖+Waves）**而非自由 agent 循环，LangGraph 的重型抽象收益低；②老师课件与产品验证的正是自研路线（任务账本+journal+Gate）；③可视化事件源是产品核心卖点，自建事件表让"画布状态=数据库状态"天然一致；④课程规模引入框架的学习/排错成本可能高于自研本身。**风险与缓解**：checkpoint/恢复的边角（并发写、部分失败）——用"事件溯源+幂等节点+状态机"兜底，把 LangGraph 的 interrupt/checkpoint/stream 作为设计对照。若组长评估后倾向框架加速，LangGraph 是唯一合理备选（其余框架均不支持依赖图+人工门+恢复的完整组合）。

### 6.3 节点间通信与协议

- **编排器→节点**：任务派发五要素（目标/输出格式/工具指引/边界/停止条件，Anthropic/课件验证）。
- **节点→编排器**：完成回执带**双 ID**（task_id + attempt_id），旧尝试的迟到回执不会误完成新一轮（Orca 验证）。
- **节点↔节点**：默认**只经共享工件/黑板**（传引用不传全文），禁点对点私传（MAST FM2.4/2.5 对症）；讨论轮内用结构化消息（Topic/Claim/Evidence/Verdict），防止"三个 agent 都同意但其实读了同一个错误来源"。
- **协议取舍**：MCP **真实现**但只做工具层（开发 agent 通过 stdio 调 git/filesystem 等现成 server，约半天工作量）；A2A/ACP 只借鉴概念（AgentCard 的能力声明 JSON → 我们的节点注册表），不引协议栈——课程平台是单体应用，跨组织互操作的成本远大于收益；AG-UI 借鉴其 ~16 种事件枚举的命名与语义，用 SSE 下发。
- **不引入** Redis Streams/Kafka/Temporal（超出课程体量；Celery 若用仅做 LLM 调用异步池）。

### 6.4 记忆系统（本产品差异化重点）

**四层作用域**（=课件多租户 scoping 的落地）：

| 层 | 作用域 | 内容 | 谁写 | 谁读 |
|---|---|---|---|---|
| L0 会话工作记忆 | run/task | 当前任务上下文 | 运行时 | 当前节点 |
| L1 角色私有记忆 | agent_id | 该角色的经验卡、踩坑记录、评审偏好（如"本项目测试 agent 惯于漏测并发"） | 角色自己（任务完成后 Reflexion 式提炼） | 角色自己（新任务开场注入） |
| L2 项目共享黑板 | project_id | 工件链+决策日志+审查往来 | 各节点 | 全体节点（以工件为主，消息只做解释） |
| L3 平台规范记忆 | global | constitution + 用户全局偏好 + 跨项目经验 | 人批准后写入（写权限门禁） | 全体（开场注入） |

**机制**（全部来自课件三问+论文）：写入五步流水线（Trigger→Extract→Validate→Reconcile→Commit）；原子化条目；schema=type/content/scope/source_event/status/evidence/valid_from；正文+检索目录+原始依据三件套；检索=作用域过滤→BM25+语义+实体混合→有效性过滤→token 预算裁剪；失效不删除（问"现在"用新记录，问"上月"读历史版本）；后台 dreaming（空闲期合并重复→提炼经验→人审后生效）；注入防护（记忆只作背景信息，不进系统指令）；权限越高的记忆写入门禁越严。

**L1 角色私有记忆的落地形态**（BMAD v6 sanctum 约定，直接可抄）：每角色一个文件夹=5 个身份文件（PERSONA/CREED/BOND/HOW-I-REMEMBER/CAPABILITIES）常驻轻载 + 主体 slug 文件 + **按日期命名的事件文件**（`decisions/2026-11-04-xxx.md`）+ `pending.md`（下次该提的事）+ `raw/`（原始交接材料）；**standing 文件"改写不追加"，事件文件按日期追加**——与课件"只追加账本"原则一致；唤醒只加载身份文件+记忆地图，正文按需读。

**写入模型分层**（maximem 调研）：抽取/判决用中价位小模型（热路径），合并重写等低频重活用强模型；确定性门控先行（无存储模式、证据不在原文中的直接拦截）；记录判决标签便于重校准；测量"规则率"防止把一次性要求写成永久规则。

**实现（两条已验证路径，产品层接口不变）**：`MemoryService`（add/search/update/list + scope 字段 + 角色写门控）；引擎层二选一——① **Hindsight**（60.9k★，MIT：pip/单容器/embedded 三档部署；0.8B 判决模型承担"这条该不该写"，observations 自动做"加强/削弱/扩展"式 reconcile 并保留证据引文，四路混合检索）——机制与课件五步流水线同构，省掉最难调的部分；② **自研最简**（Postgres+pgvector+BM25 或 SQLite FTS5，零新依赖，与老师 MemPlus 同构，约 1-2 千行，课程展示价值高）。

**写入策略采点**：Mem0 v3 = 每轮 ADD-only（只插入不覆盖，过期默认不进检索+近因衰减，矛盾需显式处理）；LangMem = hot path（即时写，加延迟）vs background（会话末/闲置后巩固，召回更高）双模式——我们默认 background，用户显式纠正类关键偏好走 hot path。

### 6.5 工件格式（spec-kit/Kiro 约定 × 老师产品实证）

```
constitution.md（平台宪法：质量原则/技术栈约束，一次创建多变更复用）
idea-brief.md → discussion.md（共识+分歧+证据引用）→ proposal.md → review.md（并行评审意见）
→ requirement.md（EARS 句式 WHEN…THE SYSTEM SHALL…；用户故事 P1/P2/P3；AC=Given/When/Then）
→ design.md（固定章节：架构/时序/数据流/错误处理/测试策略）
→ task.md（每行任务：id / deps / design-section / test-cases / assignee(角色+模型) / wave / status）
→ test.md + code + changelog.md
```

- 每工件 YAML front-matter：id / status / version / inputs / created。
- 变更管理：Change=(Team, Process模板, Level)；改需求=带版本和理由的补丁，只重跑受影响节点，可回退。
- **变更文件夹三段式（OpenSpec 74.8k★ 印证）**：propose 产出 proposal + spec delta + design + tasks 四件套 → 执行前强制人工评审门 → 归档时 delta 合入总规格——与老师 Change 模型互证，直接采用为我们的变更生命周期。BMAD v6 另将规划产物放独立 git 仓库（规划历史与代码历史分离），可作加分实现。
- task.md 即账本：编排器按 deps 拓扑出 Waves（同波并发、波间串行），人工可手动增删查改（画布双向同步）。
- 这套格式与老师产品 task.md 的内联元数据完全一致，也与 spec-kit（149.7k★）和 Kiro 的约定一致——三方互证，直接采用。

### 6.6 前端与可视化

- **@xyflow/react v12**（39k★，MIT，仅 Pro 示例代码订阅收费不影响使用）+ **elkjs** 自动布局；Ant Design 5（工作台组件全、中文文档）。
- 状态管理：zustand（运行态 Map<nodeId,status/logs/tokens>，React Flow 内部同栈）+ TanStack Query（REST 资源）。
- **SSE**：`GET /runs/:id` 快照初始化 → 订阅 `/runs/:id/events`；事件枚举对齐 AG-UI（run_started/phase_entered/node_started/node_log/node_token/node_finished/gate_requested/run_finished）；断线用 Last-Event-ID 续传；审批/取消/反馈走 REST POST。
- 动画纪律：执行高亮**只由后端事件驱动**，不做本地模拟（n8n 社区踩坑）。

### 6.7 模型层（Models Pool）

- OpenAI-compatible 统一适配器（GLM / Doubao / DeepSeek / Qwen / OpenAI / 本地模型均可接），每角色模板绑定默认模型、每任务可覆盖。
- 分级用模（课件 Easy Workflow + maximem 双验证）：小模型做抽取/判决/校验（固定输出形状，可用非 LLM）；中模型做讨论与开发；强模型做方案与终审。
- 记录每节点 token 用量与耗时 → 成本面板（评估用）。

### 7.2 角色清单（Agent 身份模板 = 提示词模板 + 记忆策略 + 工具权限 + 默认模型）

| # | 角色 | 职责 | 关键约束 |
|---|---|---|---|
| 1 | 需求启发师 | 把一句话想法问透，产出 idea-brief | 反向确认对照用户最初目标 |
| 2 | 主持人 Facilitator | 组织多体讨论：立场分配→蒸馏共识→proposal | 裁判必须引用证据，分歧保留 |
| 3 | 讨论者 ×N | 持立场互辩（技术可行/用户体验/成本工期/风险合规） | 立场模板；只读共享工件发言；**讨论算力分级**（单人代演→关键轮独立 agent→全员独立，带降级链控制成本，BMAD party-mode 实证）；persona 写具体偏好而非标签（Du 2305.14325：3 立场×2 轮起步） |
| 4 | 方案架构师 | proposal → 建设方案（含技术选型） | 输出带证据与未决项 |
| 5 | 评审团（并行） | 多视角打分+过程性反馈（Agent-as-a-Judge） | 与生成者分离；分歧引用原文；**统一评审 schema**（对抗/边界/验证缺口等 lens 单一报告，零发现也是合法结果），修改清单逐条 accept/reject（BMAD advanced-elicitation） |
| 6 | 需求分析师 | requirement.md（EARS/P1P2P3/AC） | 信息不足禁止进入下一阶段（澄清强制门） |
| 7 | 设计师 | design.md（固定章节） | 引用需求编号 |
| 8 | 任务分解器 Decomposer | design → task.md（DAG+deps+design-section+test-cases），**自行创建任务节点并分配合适的角色模板与模型** | 用户可手动增删查改 |
| 9 | 编排器 Orchestrator | Wave 调度、预算与轮次上限、门禁判定 | **程序为主，不是 LLM** |
| 10 | 开发者（按任务克隆） | 单任务实现 | 文件所有权隔离；不越任务边界；**工人纪律**：一次只领一个任务、不自选下一张、终态写回工件，派发权归编排器（BMAD build-auto） |
| 11 | 测试工程师 QA | test.md→可执行测试 | 验收=AC 逐条勾选 |

| 13 | 集成交付 | 合并/构建/发布门禁 | 凭证据合并 |

### 7.3 产品工作全流程（含人工介入点 ★）

```
想法输入 → ★澄清对话(启发师,人可追问) → 多体讨论(人可插话/旁听) → ★方案确认门
→ 多方评价(并行评审) → ★评审裁决门(采纳/驳回+意见) → 需求规格 → ★需求审查门
→ 设计规格(讨论式设计) → ★设计审查门(默认交付人审；可配置"规格产出后自动送往分解并开工")
→ 任务分解(DAG) → ★任务图人工编辑(增删查改节点/模型分配)
→ 编排执行(Wave 并行, GATES 自动门禁) → ★抽查门(可选) → 测试/评审(失败带反思重试,轮次上限)
→ ★验收门(GA Checkpoint) → 交付(changelog+工件归档) → 记忆沉淀(dreaming,人审)
```

**自动化等级**（对齐老师 LEVEL）：L1 全程人审 / L2 关键门人审（默认）/ L3 仅验收门。**不变量：Agent 可以提议变更，不能批准自己的补丁**；每个门=通过 / 驳回+反馈（返工到指定节点，重试带反思、有上限）/ 直接编辑产物。

**回流是一等公民**（agent-orchestrator 实证）：测试失败、评审意见、集成冲突**自动路由回产出该工件的节点**（问题直达负责人，不沿管道回传、不重置无关下游），循环直至通过或轮次上限交人。

### 7.4 附加功能

- **Agent Factory**：角色模板库（克隆/修改/派生），对齐老师 Agents Market；
- **Models Pool**：多供应商接入+按节点绑定+成本面板；
- **记忆面板**：四层记忆可视化（查看/编辑/删除/审批写入），条目带**证据引文**（observation 溯源），写入按角色门控——把记忆做成"可读、可审计资产"，透明度是差异化卖点；
- **执行看板（四车道）**：Working / Needs you（需人）/ In review / Ready to merge，节点按状态自动归道、需人的置顶（agent-orchestrator 模式），与双图互补；
- **双图+事件时间线+审批队列**：Twin Graph（阶段管道↔任务图谱）、Activity 流、待审批泳道；
- **变更管理**：Change=(Team,Process,Level)+版本补丁+局部重跑+回退（M3）；归档时 spec delta 合入总规格（OpenSpec 模式）；
- **评测面板**（关联"项目优化评估"）：记忆评估指标（事实准确率/Recall@K/过时误用率/任务成功率/成本）+ **迷你记忆基准**（20-30 条合成对话埋 10-15 条目标事实，含覆盖/拒答/时间题；新会话问答+LLM 评分+**跨 scope 泄漏测试**，一天成本）+ MAST 失败模式自查清单。

### 7.5 与老师产品对照

对齐：双图、节点类型、门禁/检查点/恢复、任务账本、工件四件套、Agent Factory/Models Pool、自动化等级。
差异化（我们的特色）：记忆面板与四层角色记忆的产品化；讨论过程的结构化可视化（立场/证据/共识蒸馏）；成本面板；MAST 自查清单内置。

## 9. 失败模式清单（"项目优化评估"直接使用）

**A. 规格误解（MAST FC1，约占失败 42%）**：不遵守任务规格（传结构化工件而非自由转述）；不主动澄清（设澄清强制门）；委派含糊（派发固定五要素）。
**B. 角色串话**：越角色行动（角色模板显式声明"只负责 X"）；忽视他人输入（结论落盘共享工件）；互相刷屏（限广播，默认工件共享）。
**C. 上下文丢失**：历史截断（产物写文件传引用）；会话重置（checkpoint+恢复）；长对话膨胀（定期摘要+干净交接）。
**D. 级联错误**：上游错误流入下游（每阶段产物过审）；言行不一（行动结果与声明对账）；错误复利（重试必须带反思，禁静默重跑）。
**E. 验证缺失（FC3，约 21%）**：过早终止（完成判据=AC 逐条勾选）；弱验证（AC 直接转可执行测试）；错误验证（评审者与生成者分离）。
**F. 成本与流程失控**：多智能体约 15× token（评审循环硬上限+前缀缓存）；重复已完成步骤（状态机+产物登记去重）；不知何时停（终止条件入系统提示+硬上限）；过度编排（先单 agent 基线，拆分要证据）。
**G. 记忆四类失败**：污染（写入前核验来源）；过时（valid_from/失效标记）；注入（历史文本不进系统指令）；泄漏（scope filter 强制）。**自评方法**：迷你记忆基准+跨 scope 泄漏测试（§7.4 评测面板），一天成本直接产出评估数据。

## 10. 待确认问题

> 状态更新（2026-11-14）：以下各项已裁决，并由[设计规格说明书 §2](../设计规格说明书.md) 吸收为既定决策——第 1/2/3 项按推荐采纳（引擎+模板、自研编排核、自研 MemoryService+Hindsight 可插拔）；第 4-6 项的答案见设计规格（模型全量可配置、6 周排期与 W1 原型、调研报告本身即分享材料）。本节保留作为决策过程记录。

1. **产品定位**：采纳"通用可定制引擎 + 预置 SDLC 模板"（我的推荐）还是只做固定 SDLC 流水线？——影响 M2 的工作量分配。
2. **编排核**：自研轻量编排核（我的推荐）还是直接上 LangGraph？——建议组长结合自身栈拍板（§6.2 对比表）。
3. **记忆引擎**（产品层 MemoryService 接口已定，无需再议）：引擎层接 **Hindsight**（60.9k★，MIT，单容器部署；写入判决模型+自动巩固+四路混合检索开箱即用）还是**自研最简**（Postgres+pgvector+BM25，零新依赖，与老师 MemPlus 同构，约 1-2 千行）？
4. **模型接入**：团队手上有哪些 API（doubao/GLM/DeepSeek/OpenAI 兼容？）、预算多少、是否需要本地模型兜底？——决定 Models Pool 的默认配置。
5. **时间盒**：本周之后还有几个开发周？——决定 MVP 从 M1 还是 M1+M2 开始裁剪。
6. **分享载体**：本周"前沿技术资料分享"以什么形式提交（本文档 / PPT / 口头+文档）？需要的话我可以把本文转成分享用 PPT。
