# 节点交互设计（NODE-ACTIONS-01）

> 版本 v1.0 · 日期 2026-11-22 · 状态：已实现（待合入） · 基线：`main@d83331a` · 对应分支：`feat/node-interaction`
> 交付物：公共模块 `backend/app/engine/node_actions.py`、`backend/app/api/nodes.py`（GET 扩展 + retry 改造 + reset/skip/feedback）与 4 个审计事件；不含运行中 cancel/pause、run 级 resume、`PATCH /nodes/{id}/config`（F8 未做）。

## 1 目标与现状缺口

### 1.1 目标与依据

把运行图节点从「只能看」升级为**可操作、受状态机约束、可审计**：人工可对单节点重试（可带反馈）/ 重置 / 跳过 / 注入反馈，
每次动作留下 `actor="human"` 审计事件。本轮不是自选方向：

- README §4.1 把重试定义在调度层（「指数退避 + 抖动……`retry_at` 写入节点 config，等待期间不占并发槽」），§4.2 写明「门挂起时 run 置 `waiting_human`，**不占协程**；重启后待决门原样保留」——人工介入是一等公民，但人工对**节点**的介入此前只有 retry。
- `docs/迭代优化-可交互编排画布.md` §6 下一步：「增量 3：提交计划后在执行页复用同一套视觉，展示 `dev_* + verify` 的运行图（状态色、当前节点、重试标记）」。
- `docs/设计规格说明书.md` L22 把「节点可手动增删查改」写进产品目标；L354 把运行详情拆为「M0=阶段列表+节点卡片；M1=xyflow 只读画布+MiniMap；M2=画布编辑+双图」——节点交互是 M1 之前就能交付的能力。

### 1.2 现状：节点级 API 只有两个

| API | 位置（基线 `main@d83331a`） | 改造前能力 | 缺口 |
|---|---|---|---|
| `GET /api/nodes/{id}` | `backend/app/api/nodes.py:19-53` | 基础字段 + `attempts/messages`，仅 `messages` 参数 | 无 `max_attempts`（前端「尝试 n/max」显示 undefined）、无 `can_*`、无上下游、无 `open_gate`、无节点事件、无 `artifact_kinds` |
| `POST /api/nodes/{id}/retry` | `backend/app/api/nodes.py:56-89` | 接受 `feedback`，清 `escalation`，节点置 pending | 不校验 run 终态（复活终态 run）、不重置下游、无幂等、自动批准 open 门且不发 `gate_decided`、无操作人审计 |

表中行号指基线 commit（`git show d83331a:backend/app/api/nodes.py` 可复核）；改造后实现见 §5.2 与 §11。三个缺口：观察信息不全、
失败恢复只能绕门/评审面板、无法表达「放弃当前节点」且人工动作无审计。

## 2 设计原则

1. **人的操作显式化**：每个动作对应明确人类意图（重试/重置/跳过/注入反馈），不做「万能 PATCH 节点」。
2. **状态迁移合法化**：是否允许只看 §3 矩阵；非法迁移返回结构化错误码 + `hint`，不静默改库、不静默成功。
3. **事件即审计**：不新增审计表，动作写 `events`（`actor="human"`），并把 `before/after`、`reset_nodes` 回给前端。
4. **不碰调度器**：`orchestrator._loop/_run_node/_run_attempt` 零改动；动作只改状态 + `kick()`（红线 1）。
5. **向后兼容 + 零迁移**：不加表/列；`GET` 只加字段；旧 retry 请求体（只带 `feedback`）仍可用。

## 3 节点动作矩阵

允许的 `Node.status`：`pending / running / done / waiting_human / skipped`；`run 终态` = `{"finished","failed","stopped"}`（`orchestrator.py:20`）。

| 动作 | pending | running | done | waiting_human（普通节点） | HUMAN_GATE | skipped | run 终态 |
|---|---|---|---|---|---|---|---|
| retry | 409 `node_not_retryable` | 409 `node_running` | ✅ → pending | ✅ → pending | ✅ → pending（重新开门） | ✅ → pending | 409 `run_terminal` |
| reset | ✅ → pending（清调度键） | 409 `node_running` | ✅ → pending | ✅ → pending | ✅ → pending | ✅ → pending | 409 `run_terminal` |
| skip | ✅ → skipped | 409 `node_running` | 409 `node_not_skippable` | ✅ → skipped（关 open 门） | 400 `gate_node_protected` | 幂等返回当前状态 | 409 `run_terminal` |
| feedback | ✅ 注入 | 409 `node_running` | ✅ 注入（不重跑） | ✅ 注入 | ✅ 注入 | 409 `node_not_retryable` | 409 `run_terminal` |

列语义：pending 是「未执行（含被 reset 回退）」——retry 拒绝的理由是没执行过、改反馈请用 feedback；running 是 attempt 进行中，v1 不可打断；waiting_human（普通节点）是失败升级门挂起中，动作置 pending 并关闭其 open 门后由 `kick` 重新调度；HUMAN_GATE 的 reset/retry 允许回退重开门；skipped 是人工跳过（可被 retry/reset 拉回）；run 终态下任何动作 409 `run_terminal`（不再「复活」）。

`can_*` 由矩阵实时推导、随 `GET /nodes/{id}` 返回：`can_retry / can_reset / can_skip / can_feedback / can_edit_config`。
`can_edit_config` 也按状态推导（running、以及 HUMAN_GATE 挂起时为 false，见 `node_actions.py:217-251`）；但 v1 未提供
`PATCH /nodes/{id}/config` 端点（F8 未做），前端不渲染编辑入口，字段仅作后续预留。

## 4 状态机与迁移

### 4.1 v1 状态子集

`running` 由 `orchestrator.py:158` 写入，`done` 由 `orchestrator.py:201-202` 写入，`waiting_human` 由 `gates.py:118`（`request_gate`）写入，`pending` 由基线 retry（基线 `nodes.py:81`）、门回退（`gates.py:164/195/218/222`）、取消（`orchestrator.py:182`）与本轮动作接口（`node_actions.py:119/413/432`）写入；`skipped` 此前只被读、没有写入口，本轮 `skip` 首次写入（`node_actions.py:480`）。`Node` 从不写 `failed`——失败体现在 `NodeAttempt.status` 与 `Run.status`。

### 4.2 合法迁移

```text
pending ──reset──▶ pending（清 feedback/retry_at/retry_count/escalation 等调度键）
done / waiting_human / skipped ──retry/reset──▶ pending
done ──feedback──▶ done（config.feedback 更新，不重跑）
pending / waiting_human ──skip──▶ skipped
running / run 终态 ──任意动作──▶ 409（不可打断 / 不复活）
```

统一后置：事务内置 `node.status`（skip 为 `skipped`）并清调度键；`_resume_run` 只在 **run 非终态且没有其他 open 门**时
把 `run.status` 置 `running` 并清 `run.error`，否则保持 `waiting_human`（`node_actions.py:147-159`）；事务提交后 API 层
`emit(...)`，retry/reset/skip 再 `orchestrator.kick(run_id)`（feedback 不唤醒调度）。

### 4.3 skipped 语义与门保护

- `skipped` 被视为依赖满足：`_deps_done` 用 `("done","skipped")` 判断（`orchestrator.py:486-488`），完成判定同样接受
  `skipped`（`orchestrator.py:104`）；skip 后 `kick` 即可解锁下游。skip 的节点不产出工件，下游按「缺失输入」继续——这正是
  前端跳过弹窗必须显示风险提示的原因（见前端文档 §6）。
- HUMAN_GATE 不可 skip（400 `gate_node_protected`）；门只走 `POST /gates/{id}/approve|reject`（README §4.2）。

### 4.4 终态保护

基线 retry 无条件把 run 置 `running`（基线 `nodes.py:82-83`），会复活终态 run；本轮先校验 `TERMINAL`（`node_actions.py:127-134`），
命中即 409 `run_terminal`，run 状态与 `error` 保持原样（需要恢复终态 run 时应另做 run 级 `resume`，见 §10）。动作关闭 open 门时
记录 `decided_by`（`human-retry/human-reset/human-skip`）与 `feedback`，但**不**发 `gate_decided`（`node_actions.py:375-388`）。

### 5.5 错误码表

统一错误体：`HTTPException(status_code, detail={"code","message","hint","details"})`；前端 `ApiError` 取 `detail.message`
（`client.ts:25-35`）。现有 retry 的两条 404/400 字符串错误允许保留以兼容。

| 错误码 | HTTP | 触发条件 | 前端处理建议 |
|---|---|---|---|
| `node_not_found` | 404 | `node_id` 不存在 | 关闭检查器并提示刷新 |
| `run_not_found` | 404 | 节点关联 run 缺失（数据损坏兜底） | 同上 |
| `node_running` | 409 | 节点 running | 禁用动作，等 attempt 结束 |
| `node_not_retryable` | 409 | retry 用于 pending；feedback 用于 skipped | 按 `can_*` 隐藏按钮 |
| `node_not_skippable` | 409 | skip 用于 done | 同上 |
| `gate_node_protected` | 400 | skip 用于 HUMAN_GATE | 门节点只显示「前往裁决」 |
| `run_terminal` | 409 | run ∈ `{finished,failed,stopped}` | 禁用整条动作条 |
| `status_conflict` | 409 | `expected_status` 与当前 `node.status` 不一致 | 刷新详情后让用户确认 |
| `feedback_required` | 400 | `feedback` 为空（超长在 schema 层由 `max_length=4000` 拦截为 422） | 表单校验拦截 |

### 5.6 幂等语义

`expected_status`（可选）与当前 `node.status` 不一致 → 409 `status_conflict`，**不写状态、不发事件**（`nodes.py:70-79`）。
skip 对已 `skipped` 节点幂等返回当前状态（`closed_gates=0`、`reset_nodes=[]`），实现层返回 `changed=False` 且 API 不重复 emit、
不重复 kick（`node_actions.py:469-477`、`nodes.py:162-170`）。重复 retry 时节点已 `pending`，再次提交按矩阵 409（或带
`expected_status` 时 `status_conflict`），不会一次动作两条事件；run 终态统一 409 `run_terminal`。

## 7 数据模型与迁移

**零迁移**：不新增表/列（红线 2）。节点仍用 `nodes`（`models.py:115-132`）的 `status/max_attempts/config_json/order_index/wave`；
动作审计写 `events`（`models.py:171-186`，`(run_id, seq)` 唯一，`payload_json` 存 `actor/reason/reset_nodes`）；动作历史用事件抽屉或
`GET /nodes/{id}` 的 `events`，不新建表；`can_*` 实时推导、不持久化。

将来若要持久化（如 `nodes.status_reason`）：按 `db/base.py:76-106` 的 `_ensure_columns()` 先例在 `additions` 加 **nullable TEXT** 列，
旧行业务兜底；必须「先在事务外 `inspect` 读完列、再 `engine.begin()`」（`db/base.py:93-98`），否则单连接池自锁到 `pool_timeout`（60s）。

## 10 已知边界与后续

- **运行中 cancel/pause 不做**：单节点 `task.cancel()` 会让 `CancelledError` 在 `_run_attempt` 重抛（`orchestrator.py:179-183`），
  冒泡杀掉调度循环；需 attempt 句柄 + 改 `_loop` 的 `gather` 语义（`orchestrator.py:116`），列为 M1。
- **run 级 resume 不做**：retry 只处理非终态 run；恢复 `finished/failed/stopped` 需单独设计 `POST /runs/{id}/resume`。
- **单进程语义**：`kick`、seq 缓存、并发闸门都在进程内；多 worker 需要 DB 租约或外部锁（M2）。
- **attempt 级幂等缺失**：重试 = 整节点重来，无 checkpoint/幂等键；防重放靠 `expected_status`。
- **门节点保护与 config 编辑**：HUMAN_GATE 不可 skip 但可 retry/reset 回退；`can_edit_config` 按状态推导（`node_actions.py:238-243`）但无 `PATCH config` 端点，编辑能力不在本轮。
- **重置不删除工件**：reset/skip 只改节点与任务状态，已落盘工件保留，重跑产生新版本（README §4.4 supersede 语义）。
