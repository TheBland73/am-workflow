# 设计规格 → 任务分解 → 编排 → 可视化

> 讲框架，不讲实现细节。一句话：**输入是一份设计规格；PM Agent 只把它拆成候选任务，编排器把候选任务变成可执行、可校验、可提交的编排，并且这个编排能被看见和修改。**
> 实现散落在 `backend/app/{api/plans,engine/plan_generation,engine/planner,engine/orchestrator}` 与 `frontend/src/{pages/PlanPage,canvas/PlanGraph,canvas/ExecutionMap}`，本文只描述它们之间的结构关系。

---

## 1. 为什么需要一层「编排」

设计规格到代码之间隔着一堆判断：有哪些事、谁先谁后、哪些能并行、哪条链决定工期、每个任务依据规格的哪一章。这些判断如果交给模型，就会变成一份「看起来合理、跑起来死锁」的图：模型很擅长写任务标题，不擅长保证 DAG 无环、并行度可控。

所以框架的第一刀不是「怎么让模型拆得更好」，而是**把「拆」和「排」拆开**：

- 拆：需要读设计、理解模块，是模型擅长的；
- 排：校验、分层、算关键路径、定并发，是确定性计算，程序比模型可靠。

由此得到整个系统的骨架：**模型提案，程序判定，人确认。**

## 2. 总体框架：三层 + 三个角色

```
   角色       人                        模型（PM Agent）              程序（编排器）
              │                              │                            │
   契约      设计规格 ──────────────▶ 候选任务清单 ──────────────▶ 编排快照
   （数据）   design_text              tasks[{uid,deps,…}]          waves / critical / coverage
              │                              │                            │
   层次      ┌─ 规格层 ─┐            ┌──── 提案层 ────┐          ┌──── 判定层 ────┐
             │ 设计文本  │            │ 角色提示 + 流式 │          │ 校验 / 拓扑 / 指标 │
             │ 章节索引  │            │ 严格 JSON 输出  │          │ 版本化快照        │
             └──────────┘            └────────────────┘          └────────────────┘
                                                                        │
                                                              人工门：确认 / 修改
                                                                        │
                                                          ┌──── 执行层 ────┐
                                                          │ Run / Task / Node│
                                                          │ 调度 · 重试 · 门  │
                                                          └────────────────┘
```

| 层 | 内容 | 是否含模型 | 产物 | 出错时的后果 |
| --- | --- | --- | --- | --- |
| 规格层 | 设计正文、章节索引、来源 | 否 | `design_text` + `sections` | 分解无依据，后续全歪 |
| 提案层 | PM 角色、提示词、流式输出 | 是 | 候选任务 JSON | 可重生成，不影响已有运行 |
| 判定层 | 校验、波次、关键路径、指标、覆盖率 | 否 | 不可变快照 | 进入 `invalid`，禁止提交 |
| 执行层 | 任务账本、节点、调度、重试、门 | 否（节点内才调模型） | Run + 事件流 | 可重试 / 转人工 / 恢复 |

关键性质：**只有提案层有模型**。判定层是纯函数，同一份任务清单永远算出同一张图——这让「评测、回归、复现」成为可能，也让错误可以定位到规则而不是「模型今天心情不好」。

## 3. 四条契约

框架的稳定性来自契约，不来自代码组织。这条链上有四份必须说清楚的数据。

### 3.1 输入契约：设计规格必须可定位

一份能用来分解的规格，最小要求是**有章节**。章节是任务与规格之间唯一的锚点：没有它，`design_section` 只能写「相关部分」，任务就再也无法回答「你依据什么做这个」。

因此规格层的职责很窄：保存原文与来源（三种来源同等对待）、解析出 `{层级, 标题, 行号, key}`、给出章节索引。太短的规格在入口就被拒绝，而不是让模型去猜。

### 3.2 提案契约：PM 只输出任务，不输出编排

PM 的输出是一份**结构化候选清单**，字段固定：

| 字段 | 语义 | 谁在下游使用 |
| --- | --- | --- |
| `uid` / `title` / `description` | 任务身份与做什么 | 画布、执行时的任务说明 |
| `deps` | 先后关系 | 波次、关键路径、执行依赖 |
| `design_section` | 依据的章节 | 可追溯、覆盖率 |
| `acceptance` | 可测试标准 | 验收、执行侧测试用例 |
| `role` / `effort` / `priority` | 谁做、多大、多急 | 选模型与提示、点数、角标 |

契约里刻意**没有** wave、没有并行组、没有运行时节点。这些是程序算出来的，模型写进输出也会被忽略——不给模型留出「以为自己在控制调度」的空间。

### 3.3 判定契约：编排是一次可版本化的计算

编排器的输出不是「一张图」，而是一份**快照**：任务快照 + DAG（节点与边）+ 波次 + 关键路径 + 指标 + 覆盖率 + 校验结果 + 版本号。

- 波次回答「最早什么时候能开始」；
- 关键路径按工作量点数而非任务数算，回答「哪条链最慢」；
- 指标回答「有多少事、最大并行几路」；
- 覆盖率回答「规格里有几章没人接」。

快照是不可变的、带版本的：每次校验新增一版，最新通过的那版是「当前生效版本」，历史版本可回看、可恢复。编辑出错不会摧毁上一版——这是「人敢改」的前提。

### 3.4 执行契约：任务语义必须跟着节点走

提交成运行时，计划行被物化成 `Task` 账本 + 一组开发节点 + 一个验证节点。要点是：**节点不只带「执行什么」，还带「依据什么」**——角色、任务说明、设计章节、工作量、优先级都进节点配置。

理由很直接：执行期选哪个模型、追加哪段角色提示、失败后怎么解释，都依赖这些字段。如果物化时丢掉它们，计划层做的所有判断在执行时就蒸发了。

验证节点是单独的：所有开发节点完成后跑一次验收命令，结果由退出码判定。这是「证据判定」在框架里的落点——不靠模型说「做完了」。

## 4. 六个核心设计决策

| 决策 | 选择 | 理由 | 代价 |
| --- | --- | --- | --- |
| 谁定 DAG | 程序定，模型只提案 | 模型无法保证无环、可调度 | 模型的好想法可能被规则否掉 |
| 任务形态 | 结构化清单，不是自由文本 | 可校验、可编辑、可执行、可 diff | 需要一次性定义 schema |
| 校验失败 | 给错误码 + 位置 + 修复提示 | 人要能修；只报「有错」等于没报 | 每个错误码都要写清语义 |
| 版本策略 | 每次校验一版不可变快照 | 敢改、可回滚、可审计 | 存储冗余，无 diff |
| 视图拆分 | 计划图与执行图分开 | 一个回答「怎么排」，一个回答「卡在哪」 | 两套图、两套语义 |
| 人工门位置 | 生成后、提交前、执行中 | 幻觉不变成代码；执行异常不静默 | 多一步点击 |

还有一条不是决策而是纪律：**产品名不许写进代码与提示词**。所有产品差异只能来自 `design_text`，测试用两份结构不同的规格互为对照。否则这套框架就只是「为某个 demo 定制的工具」。

## 5. 生命周期

```
设计规格 ──▶ 草稿 ──▶ 生成中 ──▶ 有效 / 有错误 ──▶ 编辑 ⇄ 重校验 ──▶ 已提交 ──▶ 运行
                       │              │                                  │
                       └─ 失败 ───────┘                                  └─ 归档
```

三段一锁：

1. **规格锁定**：计划创建后原文不再变，改规格就新建计划——保证「这份任务来自这份设计」永远成立。
2. **编排锁定**：任何编辑都会让计划回到「编辑中」，重校验通过才算有效；只有有效才能提交。生成结果默认待确认，没有人点提交，它就只是一份提案。
3. **运行锁定**：提交后计划只读，带运行链接。要改就复制计划，不改历史。

人工门有三处：生成后（接受/重生成）、提交前（确认任务数与预算）、执行中（人工门节点、失败耗尽重试后自动升级为门）。门是挂起而不是失败——进程重启后门还在。

## 6. 可视化框架

可视化的目标不是「画得好看」，而是回答四个问题：

| 问题 | 编码方式 |
| --- | --- |
| 有多少事？ | 指标条：任务数 / 波次 / 最大并行 / 关键路径 / 总点数 / 覆盖率 |
| 先做什么、什么能并行？ | **列 = 波次**，同列即并行组；泳道标题标明波次与任务数 |
| 哪条链最慢？ | 关键路径连线加粗，卡片 `CRIT` 角标 |
| 每个任务依据哪一章？ | 卡片章节标签、章节 chip、覆盖率缺口 |

在此之上叠一层**编辑器语义**：角色用颜色区分（谁做）、跨角色依赖画虚线（交接有损）、错误边变红并给角标（哪里不能提交）、选中高亮上下游并把其余压暗（读上下文，不影响执行）。

交互是一条闭环：**改动 → 防抖重校验 → 新快照 → 画布/指标/错误同步更新**。撤销、历史、重置布局都围绕这条回路，保证「改错了能回去」。

计划图与执行图共享同一套视觉语法（列、颜色、连线、角标、遮罩），但语义不同：计划图按波次排，执行图按工作流阶段排；执行图多一层「门阻塞了下游」的遮罩，用来解释为什么后面不动。

视图策略也属于框架：默认给一个能读清文字的缩放，绝不自动缩放去「塞下全图」；要全貌是用户的明确动作。校验刷新不能改变视野——否则人每改一个字，图就跳一次。

## 7. 数据与接口的分层

| 对象 | 角色 | 是否可变 |
| --- | --- | --- |
| 计划（`plans`） | 一份规格的一次编排，含来源、原文、章节、状态、画布坐标 | 可变（状态与坐标） |
| 任务（`plan_tasks`） | 可编辑的任务账本 | 可变 |
| 快照（`plan_snapshots`） | 每次校验的结果与版本 | 不可变 |

接口按职责分组，不按页面分组：

- **输入**：创建计划（三源）；
- **生成**：触发 → 流式事件 → 结束事件（可中止、并发生成拒绝）；
- **判定**：校验；
- **编辑**：任务字段、依赖增删、坐标（服务端做环检测，返回环路径）；
- **版本**：快照列表与恢复；
- **提交**：仅保存 / 创建运行（幂等）；
- **执行**：运行详情、事件流、门决策、节点重试。

两类事件流：生成期推 token（不落库，只看过程），执行期推状态变更（落库，可回放）。前端对终态事件自动断开，避免无限重放——这是「事件是事实，不是通知」的体现。

## 8. 扩展点

框架留了这些口子，后续不需要推翻结构：

1. **换模型**：提案层只依赖「角色 → 模型」的解析与流式接口，换成另一个模型不动判定层。
2. **换工作流**：执行层按模板实例化，SDLC 只是其中一个模板；新增阶段不影响力。
3. **加视图**：快照是自包含的数据，甘特、燃尽、表格都只是同一份快照的另一种渲染。
4. **版本 diff**：快照已带全量任务与规则结果，diff 是纯展示层能力。
5. **并行隔离**：执行层目前共享工作目录；把「一个节点一个目录」放进去，不影响计划层。

真正需要谨慎的是**不要把编排逻辑重新交给模型**：一旦允许模型改 DAG、改波次，快照就失去确定性，校验、回滚、评测全部失效。

## 9. 架构级边界

- 一个计划对应一次运行：想对比两种拆法，就建两个计划。
- 任务数有上下限：太少说明规格没拆开，太多说明模型在凑数。
- 调度语义是单进程的：并发靠进程内信号量，不支持多实例分担。
- 画布坐标属于视图偏好，不进快照、不参与审计。
- 快照存全量，不做增量；历史对比目前只能靠指标与版本号。
- 计划图只在桌面宽度下完整展开，触屏与窄屏是降级形态。

## 10. 与任务书的三处差异（实现取舍）

- 任务书列了「已生成 / 校验中」两个状态，实现不落库——它们是瞬时中间态，用前端 loading 表达更诚实。
- 任务书希望提交时复用模板里的任务图节点，实现改为直接物化开发节点加一个验证节点——提交路径不该依赖模板中是否存在某个中间节点。
- 任务书希望删除任务时提示下游影响，实现是立即删除并清理入边依赖，且不进撤销栈——删除会丢任务身份与依赖，属于「想清楚再点」的操作。

这三处都记在 `docs/编排工作台-迭代记录.md` 与 README 的已知限制里，不是遗漏。
