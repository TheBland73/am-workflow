# 分布式执行模式设计（封存）

> **⚠ 状态：仅设计、暂不实现（封存）。** 2026-11-22 决策：项目设想里的"部署在 git 服务器、各 PC 担任角色、定时轮询"的分布式设想**只做设计留档，课程周期内不实现**。当前主线是纯本地单机模式（单进程 FastAPI 编排核），不考虑与其他 PC 或服务器的产品级交互。
> **解封条件**（满足其一再评估）：① 团队明确要求分布式演示；② 单机模式质量体系（[评审与测试体系设计](./评审与测试体系设计.md)）稳定后仍有排期余量；③ 课程后续学期需要。解封时从 §4 执行器接口抽象开始，本文的 §5/§6 两方案可独立选型。
> 上游调研：[前沿技术调研 §11.5](./research/前沿技术调研与技术选型.md)（2026-11-21 专项，关键结论"没有现成等价物，但所有零件都有先例"）。

---

## 1 背景与目标

项目设想（转述）：平台部署在 git 服务器（例如 GitHub），各 PC 担任不同角色，可设置定时任务；某角色完成任务后，**严格遵循提前规定好的格式撰写报告并提交服务器，更新任务面板**；后续角色（运行在其他 PC）在定时轮询时检测到该文件和任务面板更新，自动确认前置是否完成可开工，随后读取文件了解前置完成情况后开工；项目推进到特定节点**自动触发评审测试**（也在对应角色 PC 上）。本质是分布式开发：把 PC 当人，模拟真人团队。

定位：这是产品**受众分歧点**——单机模式面向单人完成全项目开发；分布式模式面向团队使用（各成员的 PC 扮演不同角色）。设计目标是**双模式兼容、用户可配置选择**，且两种模式共享同一套流程模板、质量体系与人工介入点。

## 2 设计总览：双模式共账本

```
                    ┌──────────────────────────────────────────┐
                    │   任务账本（唯一事实源 Task Ledger）        │
                    │   task 行: uid/deps/status/owner/         │
                    │   lease_until/report_path/quality hooks   │
                    └───────────────┬──────────────────────────┘
              单机模式               │                分布式模式
   ┌────────────────┴───────┐       ┌──────────────┴──────────────┐
   │ 账本=SQLite（进程内）    │       │ 方案 A：中心化多 worker       │
   │ 调度=进程内 asyncio      │       │  账本=平台 API+DB（租约认领）  │
   │ 执行=本地 Executor 直调  │       │ 方案 B：纯 git 模式           │
   │ 人介入=网页门禁（现状）   │       │  账本=git 仓库文件（report/   │
   └────────────────────────┘       │  claim/面板 JSON），轮询认领  │
                                    │ 人介入=面板 waiting_human 态  │
                                    └─────────────────────────────┘
```

关键原则：**编排核（状态机/事件溯源/门禁/质量钩子）两种模式完全同一套**，差异只在"账本放哪、任务怎么被认领、产出怎么回写"。这正是 AutoGen v0.4"单线程 runtime 与分布式 gRPC runtime 同构切换"的先例路径。

## 3 单机模式（现状，主线）

- 账本：SQLite（WAL + 单连接池），节点即账本行，事件 append-only。
- 调度：进程内调度 + 全局信号量（`AM_NODE_CONCURRENCY`）。**现状为按最小波次批量 `gather`（存在批内屏障，README §4.1 已勘误）**；解封实施时随[评审与测试体系设计 §7](./评审与测试体系设计.md) 的调度改造一并改为"依赖就绪即跑"。
- 执行：本地 Executor——AGENT/VERIFY/GATES/REVIEW_MEETING 全部在编排核进程内执行，子进程做命令隔离。
- 人介入：网页人工门（approve/reject+feedback/edit），SSE 事件驱动 UI。
- 该模式已实现并持续演进，**本文不动它**；只有 §4 的接口化重构是解封时的前置改造。

## 4 执行器接口抽象（解封时的第一步改造）

把"节点执行"从编排核中抽出为接口（当前 `runners.py` 已按类型分发，改造量约一天）：

```python
class Executor(Protocol):
    async def submit(self, node: NodeRow, task: TaskRow | None) -> AttemptTicket: ...
    async def heartbeat(self, ticket: AttemptTicket) -> None: ...
    async def result(self, ticket: AttemptTicket) -> NodeResult: ...   # 回执双 ID（node_id+attempt_id）
    async def cancel(self, ticket: AttemptTicket) -> None: ...
```

- `LocalExecutor`：现状直调（默认）。
- `RemoteExecutor`（方案 A）或 `GitExecutor`（方案 B）：同一接口的两个实现。
- 编排核其余部分（调度/门禁/事件/恢复）零改动——恢复语义仍以"账本状态+未回执 attempt 作废"为准。

## 5 方案 A：中心化多 worker（推荐的第一档）

**形态**：平台（FastAPI+DB）部署在一台主机；各 PC 跑一个轻量 `am-worker` 进程（复用 Agent 运行时+工具层），通过 REST 轮询认领任务。评审/测试节点与其他节点无差别地被某台 worker 认领执行；人工门仍由网页统一呈现（A2A 协议 `input-required` 状态的同构实现）。

| 机制 | 设计 | 出处 |
|---|---|---|
| 认领 | `POST /tasks/{id}/claim`：`UPDATE ... SET owner=?, lease_until=now+60s WHERE status='ready' AND (lease_until IS NULL OR lease_until<now) FOR UPDATE SKIP LOCKED` 短事务，失败即他人已认领（注：当前栈为 SQLite，无 `SKIP LOCKED`；解封实施时账本迁 PostgreSQL，或用租约列+条件更新在单写者下等效实现） | Encore/Prisma SKIP LOCKED 配方；Temporal/Airflow 同源 |
| 心跳 | worker 每 60s 续租（heartbeat API）；平台 reaper 把过期租约任务打回 ready 并写事件（Airflow `adopt_or_reset_orphaned_tasks` 等价物） | Temporal Heartbeat Timeout |
| 报告契约 | 节点完成回执=结构化 `REPORT`（node_id/attempt_id/status/artifacts[]/evidence[]，JSON Schema 校验拒收）——对应设想里的"严格遵循提前规定好的格式撰写报告" | A2A Artifact 不可变 + typed task contract |
| 轮询节奏 | worker 空闲 5-15s 指数退避轮询认领 API；有任务即打。不依赖 GitHub Actions schedule（cron 最小 5 分钟+60 天禁用陷阱） | GitHub community #213232 |
| 竞争兜底 | worker 侧按 `task_uid` 防重入（GitHub Actions `concurrency group` 语义移植） | 同上 |
| 隔离 | 每任务一个 `git worktree`（或目录拷贝）独立工作区，产物由编排核合并回 run workspace | Claude Code worktree 模式；vibe-kanban 实证 |
| 事件 | worker 上报节点事件到平台事件总线，前端 UI 与单机完全一致（SSE 消费方无感） | — |

**工作量估算（解封时参考）**：Executor 接口化 1 天；认领/租约/reaper API 1-2 天；am-worker 打包 1 天；联调 1 天 ≈ **一周内可演示两台 PC**。

## 6 方案 B：纯 git 模式（设想完整落地版）

**形态**：无中心服务。一个 git 仓库（GitHub/自建）承担：任务面板 + 工件总线 + 报告归档。每台 PC 一个「角色 worker」，内容：

```
<repo>/
├─ ledger/
│  ├─ tasks.json            # 任务账本（唯一权威；JSON Schema 校验）
│  ├─ panels/
│  │  ├─ board.md           # 人读任务面板（由 tasks.json 渲染，CI 生成）
│  │  └─ gates.json         # 待决人工门（waiting_human 态）
├─ runs/<run_id>/
│  ├─ artifacts/            # 工件链（md+front-matter，与单机一致）
│  ├─ reports/<node_id>/    # 各角色报告：REPORT.md（格式契约见下）
│  └─ events.jsonl          # append-only 事件日志（各 worker 追加行）
└─ claims/<task_uid>.json   # 认领凭据（worker_id/time/lease_until）
```

| 机制 | 设计 | 出处 |
|---|---|---|
| 认领 | **git 分支原子认领**：`git push origin HEAD:refs/heads/claim/<task_uid>`——ref 创建是原子的，push 失败=他人已认领；认领信息写 `claims/<task_uid>.json` 后合回主干 | git ref 原子性（调研 §1） |
| 轮询 | worker `git fetch` 每 15-60s（可配）；比对 `tasks.json` 的 hash 判断账本是否变化，变化才做全量状态对账 | — |
| 前置确认 | worker 开工前校验：任务 deps 全部 `done` 且 `reports/` 有对应 REPORT.md 且 schema 校验通过——即设想里的"自动确认前置是否都已完成" | — |
| 报告契约 | `REPORT.md` 带 YAML front-matter（task_uid/worker/role/attempt/status/artifacts[]/evidence[]/next_actions）+ **JSON Schema 校验拒收**；正文自由叙述——"强头弱身"兼顾机器可读与人审 | cellcog/AGENTS.md 实践；A2A Artifact |
| 评审/测试触发 | `tasks.json` 中节点带 `on_done` 钩子（如 `review: ftr`）；执行评审的角色 worker 在轮询时发现钩子节点 ready 即开工——与单机质量钩子同一字段语义 | 与[评审与测试体系设计 §6](./评审与测试体系设计.md) 共享 |
| 人介入点 | 门禁状态机不变：任务/节点进 `waiting_human` 态写入 `gates.json`，任何 PC 的网页（读仓库渲染）看到待审面板；人批准=改 JSON+commit（或任何一台 PC 的本地 UI 代理操作） | A2A `input-required` 同构 |
| 冲突与回滚 | 事件与报告只追加（各自文件，无覆盖冲突）；账本修改走"读-改-写-重试"（push 冲突则 rebase 重放）；任务回滚=RESTORE 语义改账本+新 REPORT 标记 | 文件协议惯性 |
| 安全 | 仓库分权限：worker 用细粒度 token（只许写 `runs/`/`claims/` 路径）；高自主 agent 用独立 API key | 书 ch10（循环失控） |

**已知短板（为何不先做）**：轮询粒度受 git 操作延迟（本地 15s 可用，GitHub 上 30-60s 更稳）；账本写竞争需要 rebase 重放逻辑（复杂度集中在这里）；事件流无实时性（SSE 不可用，UI 靠轮询刷新）。工作量 ≈ 2-3 周，其中"账本写冲突"与"面板渲染"占一半。

## 7 两方案对比与推荐

| 维度 | A 中心化多 worker | B 纯 git |
|---|---|---|
| 实时事件流（SSE/画布动画） | ✅ 完整保留 | ❌ 轮询刷新 |
| 实现工作量 | ~1 周 | ~2-3 周 |
| 对现有代码复用 | 高（Executor 接口+现有 API） | 中（账本/面板/校验大半重写） |
| 贴合设想 | 部分（中心服务器） | ✅ 完整 |
| 运维复杂度 | 需一台常开主机 | 无（只要 git 托管） |
| 演示效果 | 两台 PC 协作流畅 | 更"分布式叙事"，但交互迟钝 |

**解封时推荐**：先 A 后 B。A 是 B 的子集练习（认领/租约/报告契约全链路先通），B 在 A 稳定后作为 M3 加分演示。若评审只认 B 的叙事，可做"混合演示"：一台 PC 跑平台（A 的中心），另一台跑 worker——对外讲述时按 B 的格式契约解释报告机制。

## 8 决策记录（为何封存）

- 2026-11-22 团队决策：**单机模式完全实现是主线**；分布式仅设计留档，未来看情况解封；不做与其他 PC/服务器的产品级交互。
- 理由：剩余排期（5 周）应优先保质量体系（评审/测试/缺陷闭环）与记忆/可视化等 M2 项落地；分布式不改变流程与质量设计，封存零损失——本文与账本 schema 已经把解封路径铺好。
- 解封动作清单：① 按 §4 抽 Executor 接口；② 选 A 或 B；③ 按 §5/§6 对应表实现；④ 质量钩子/门禁/报告契约字段与本文核对一遍。
