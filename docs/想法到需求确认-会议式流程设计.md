## 1 目标与背景

### 1.1 要解决的问题

前半段把一句想法变成一份被确认的需求规格。它的质量取决于两件事：

- **方案里的每个决定是否经过真正不同视角的检验。** 同一个模型换个角色提示重复采样，得到的意见往往高度相似，看起来达成了一致，其实没有经过质疑。
- **两次转换是否忠实。** 想法到方案、方案到需求，每一步都可能走样、遗漏或凭空新增，而模型读一遍自己参与产出的东西时倾向于说"没问题"。

### 1.2 引擎基线与本文的差距

| 本文依赖的能力 | 引擎基线 | 本文新增 |
|---|---|---|
| 多角色多轮讨论，能挂起、续开 | 节点是无状态单发调用，节点之间只靠工件传值 | 会议节点类型与会议运行时（§6） |
| 讨论到收敛、评审后回修这类轮数不定的循环 | 依赖图是无环的；返工靠节点把自己和上游重置，仅代码评审节点内置了一条回退路径 | 通用的定点回流（§6.4） |
| 由人或模型判定的确认点 | 门只能由人裁决 | 确认点机制与裁决模型（§5） |
| 跨调用的上下文管理 | 每个节点自行拼装提示词；工具循环里的历史只增不减 | 会话与上下文模块（§10） |

### 1.3 目标

| # | 目标 |
|---|---|
| G1 | 每个决策点被全体参会者知悉，并达到用户定义的共识口径（默认全体一致） |
| G2 | 两次转换可核对：方案经过独立评审与回修闭环；需求与决策点之间有可机械核对的追踪矩阵 |
| G3 | 人工与自动并进：每个确认点可以选由人或模型判定；模型能做的配置都开放给用户；全自动模式下尽量少打断 |
| G4 | 自由度有护栏：数值参数只设防崩溃的硬限，配建议提示，默认给范围而不是定值 |
| G5 | 可恢复、可审计：挂起、重启、回流都不丢上下文；每个决定记录谁做的、依据、保留的异议 |
| G6 | 成本可控：缓存友好的上下文布局；程序能判的不调模型；占用到阈值才压缩 |

## 2 范围与约束

### 2.1 明确不做

| 不做的事 | 取舍理由 |
|---|---|
| 按主题拆分的多场并行讨论与跨会议整合 | 主题拆分和整合需要另一套编排；单场会议内的决策点清单已能承载多个议题。数据模型与模板可以表达多个会议节点，留作扩展 |
| 复杂可视化（工件侧栏实时渲染、群聊式流式发言界面、账本与评审意见的可视化编辑） | 归前端。本文提供接口与事件（§12.4、§13） |
| 向量记忆与记忆面板 | 与本段目标无关，另行规划 |
| 改动设计之后的节点行为 | 只提供通用钩子（定点回流、压缩、确认点），供后续环节按需采用 |
| 代码侧的正式评审会议 | 见[评审与测试体系设计](./评审与测试体系设计.md)；本期不实现，后续再评估是否复用会议运行时。前半段只新增 `MEETING`，不新增 `REVIEW_MEETING` |

### 2.2 红线

| 红线 | 来源 |
|---|---|
| 引擎掌控控制流：模型不决定流程走向，不决定何时终止 | 设计规格说明书 §2 决策表 |
| 模型可以提议，不能批准自己的产出；确认点默认由人判定 | 设计规格说明书 §2 |
| 模型判定无效时一律转人工，此行为不可配置关闭 | 本设计 |
| 存储永远是全文，压缩只改发给模型的视图 | 本设计 |
| 单连接池：事务内不做网络 IO、不再开会话 | 设计规格说明书 §5.1 |

## 3 设计依据与主张边界

证据档位：**强**＝有直接对比实验且多篇方向一致；**中**＝有直接实验但来源单一，或多篇间接证据一致；**标准**＝标准、专著或同行评议综述；**源码**＝读源码得到的事实；**文档**＝官方产品文档。

### 3.1 已证实

| # | 结论 | 依据 | 档位 |
|---|---|---|---|
| E1 | 本次调研范围内唯一直接对比"轮流 vs 同时发言"的实验里轮流略优；但并非所有有效协议都采用轮流，Du 为每轮同时、ReConcile 为圆桌同时更新 | [ChatEval](https://arxiv.org/abs/2308.07201) 表 4：轮流 60.0，同时 55.0，同时加总结者 55.0；[Du 等](https://arxiv.org/abs/2305.14325)；[ReConcile](https://arxiv.org/abs/2309.13007) | 中 |
| E2 | 讨论的收益集中在前 1–3 轮，之后饱和 | ReConcile 各轮 74.3→77.0→79.0→78.7；Du 等四轮以上不再提升；ChatEval 增加轮数无显著提升 | 强 |
| E3 | 要求全员一致会卡死；由裁判每轮判定会引入裁判偏差；终止由程序按规则判定更稳 | ReConcile 基线中 13% 的样本第 4 轮仍未收敛；[Liang 等](https://arxiv.org/abs/2305.19118) 表 6 中 GPT-4 裁判偏向 GPT-4 辩手（136:52）；[DyLAN](https://arxiv.org/abs/2310.02170) 超过三分之二一致即停，调用减少 45.0%/66.2%/11.3%/54.2%（AR/GR/CG/DM，任务差异大） | 强（卡死、偏差）；中（停止条件） |
| E4 | 模型容易被错误意见带偏，且相当"随和" | [AgentVerse](https://arxiv.org/abs/2308.10848)：约 10% 的 MGSM 错误可归因于被带偏；[Wang 等](https://arxiv.org/abs/2402.18272)：错误传播是最常见的错误 | 中 |
| E5 | 等生成预算下，同质多智能体讨论不优于单模型 + 自洽/多数投票；收益主要来自参与者异构（不同模型或不同角色），现有实验未给出人数阈值 | [Huang 等](https://arxiv.org/abs/2310.01798) 表 7：等生成次数下辩论 83.0 低于自洽 88.2；ReConcile 异构三模型 79.0、同模型三实例 72.2；ChatEval 同角色提示 53.8、异构角色 60.0 | 中 |
| E6 | 同一模型自审在需要客观正确性的任务上不可靠；评审者有位置、冗长、自我偏好三类偏差，自我偏好来自底座模型而非提示词 | Huang 等表 3：内在自纠后 GPT-4 在 GSM8K 上 95.5→89.0；[Kamoi 等](https://arxiv.org/abs/2406.01297)；[Zheng 等](https://arxiv.org/abs/2306.05685)；[Panickssery 等](https://arxiv.org/abs/2404.13076) | 强 |
| E7 | 给评审者参考答案能大幅减少误判；仅让评审者先自行推理（CoT）的效果弱得多 | Zheng 等：默认 14/20，仅 CoT 6/20，参考答案式评审 3/20 | 中 |
| E8 | 验证应当分解成逐条可判定的检查，并让校验者能定位、读取被校验的工件 | [Chain-of-Verification](https://arxiv.org/abs/2309.11495)；[Agent-as-a-Judge](https://arxiv.org/abs/2410.10934) 表 4：对齐率 65.03%→90.44%；[MAST](https://arxiv.org/abs/2503.13657) 中"验证缺失或验证出错"合计约 17% | 中 |
| E9 | "作者修改 → 再审"的循环有益，但并非每轮都提升 | [Corex](https://arxiv.org/abs/2310.00280)；AgentVerse 纵向协作；MAST 中 ChatDev 改为该形态后成功率 25.0→40.6 | 中 |
| E10 | 评审意见越具体越有用 | [Self-Refine](https://arxiv.org/abs/2303.17651) 表 2：具体反馈 43.2，泛泛反馈 31.2，无反馈 0 | 中 |
| E11 | 信息分散在多轮里给出会明显退化 | [Laban 等](https://arxiv.org/abs/2505.06120)：多轮平均降 39%，合并为单轮达到单轮性能的 95.1%；[Liu 等](https://arxiv.org/abs/2307.03172) | 中 |
| E12 | 正式评审的形态：评审者会前独立准备并提交书面意见；会上限制争论、只记录问题不现场解决；结论三分（接受 / 有条件接受 / 退回）；作者修改，重大项才再审 | Pressman《软件工程：实践者的研究方法》7/e 第 15 章 §15.6（讲义见 [RIT SE361](https://www.se.rit.edu/~se361/Slides/se361_Chapter_15.pdf)）；[Aurum 等](https://www.wohlin.eu/stvr02-2.pdf) | 标准 |
| E13 | 共识不等于全体一致；看的是有没有未被处理的议题而不是人头；裁决须给理由且可上诉 | [RFC 7282](https://www.rfc-editor.org/rfc/rfc7282)；Kaner 等《Facilitator's Guide to Participatory Decision-Making》第 2 版，Wiley，2007 | 标准 |
| E14 | 先各自独立生成、再交互，能避免被先发言者带偏 | 名义小组法与德尔菲法，[McMillan 等](https://pmc.ncbi.nlm.nih.gov/articles/PMC4909789/) | 标准 |
| E15 | 需求的八项质量特性；其中"正确"没有工具能保证，须由用户判断 | [IEEE Std 830-1998](https://standards.ieee.org/standard/830-1998.html) §4.3 | 标准 |
| E16 | AutoGen 0.2 群聊：默认每次发送全部历史；没有"判断是否收敛"的步骤；续开即带新输入再发起且不清历史；多场群聊默认隔离、只靠摘要文本互通；压缩只改发给模型的副本，达到 token 阈值才触发 | 源码，见 §16 | 源码 |
| E17 | 前缀缓存要求从开头到某位置完全相同，之后的全部按全价计 | [智谱](https://docs.bigmodel.cn/cn/guide/capabilities/cache)、[DeepSeek](https://api-docs.deepseek.com/guides/kv_cache)、[Azure OpenAI](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/prompt-caching) | 文档 |
| E18 | 成熟产品把"是否需要人"做成按动作粒度的策略；规则失效时回落到人工 | [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[OpenAI Agents SDK](https://openai.github.io/openai-agents-python/human_in_the_loop/)、[Claude Code 权限模式](https://code.claude.com/docs/en/permission-modes) | 文档 |

### 3.2 推断

以下判断依据上面的证据和软件评审的标准做法做出，没有直接实验支持。

| # | 推断 | 所依据的证据 |
|---|---|---|
| I1 | 围绕决策点而不是整份方案迭代，成本更低，且改变立场的理由可见 | E2、E4、E11 |
| I2 | 评审者不改方案：文字级问题由执笔者修订，决策级问题回讨论会议复议 | E12、E6 |
| I3 | 冻结在前、变化在后的上下文布局，费用不高于全量历史 | E16、E17 |
| I4 | 需求规格的语义忠实性由"先凭账本写预期、再对照实际条目"的分解式检查来核对，优于整体性自审 | E6、E8 |
| I5 | 程序按表态矩阵计算共识状态，比让模型判断更可靠 | E3、E8 |

### 3.3 计划验证

| # | 待验证的主张 | 验证方式 |
|---|---|---|
| H1 | 缓存友好布局的费用不高于全量历史 | 同一想法两种布局各跑一场，比较输入量、命中率与费用（§14.2） |

## 4 总体流程

### 4.1 节点图

```
想法 ──→ 讨论会议 ──→ 方案确认 ──→ 评审会议 ──→ 评审裁决 ──→ 需求分析师 ──→ 需求确认会议 ──→ 需求确认 ──→ 设计
          ↑                           │                               ↑                        │
          └────── 决策级问题回流 ───────┘                               └────── 问题清单回流 ──────┘
```

阶段依次是想法、讨论、方案、多方评价、需求，之后接设计。模板文件是 `templates/sdlc_workflow.json`。模板替换后，新建运行使用新流程；已有运行保留历史查看，但依赖退役讨论角色的节点不能续跑。切换前应结束或归档旧运行；开发库可以直接清空（产品未公开）。

### 4.2 节点一览

| 节点 | 类型 | 做什么 | 产出 |
|---|---|---|---|
| 想法 | 入口 | 记录想法原文，可附背景材料 | 想法 |
| 讨论会议 | 会议 | 会前准备 → 独立立场 → 议题提炼 → 全员表态 → 交锋轮次 → 整合成稿 → 全员复核 | 想法简报、会议纪要、建设方案 |
| 方案确认 | 确认点 | 送评审（默认）、直接通过、驳回 | — |
| 评审会议 | 会议 | 独立评审 → 汇总分级 → 作者回应 → 会议讨论 → 裁决；文字级问题由执笔者修订并验证 | 评审报告 |
| 评审裁决 | 确认点 | 通过、编辑后通过、驳回 | — |
| 需求分析师 | 单角色 | 从已确认的方案和决策点账本拆出需求规格，含追踪矩阵 | 需求规格 |
| 需求确认会议 | 会议 | 程序核对 → 语义忠实性核对 → 质量评审 → 汇总裁决 | 确认报告 |
| 需求确认 | 确认点 | 通过、编辑后通过、驳回 | — |
| 设计及之后 | 不变 | 入口依赖已确认的需求规格 | — |

### 4.3 三类循环

决策级问题回流、问题清单回流、用户的人工驳回，都走同一个机制：带反馈定点重开目标节点（§6.4）。回流轮次有上限，由用户配置；到上限转人工。

### 4.4 两条约定

- 会议内的确认点（澄清、名单、共识）是挂在会议节点上的门，复用现有门卡片的渲染与接口。
- 带着反馈回来（回流、驳回）一律续开，不丢上下文；只有不带反馈的重置或重试才清空纪要重开（§6.2）。

### 4.5 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 每轮全员重写整份方案，交换后再写，直到趋同 | 同质角色首轮产出就相似，容易假趋同；每人各写一份，改变立场的理由不可见；成本随人数、轮数、篇幅三者相乘增长 |
| 把各步写成固定的节点串 | 表达不了"讨论到收敛为止"和"评审后回修再复审"这类轮数不定的循环 |
| 内嵌现成框架的群聊当会议执行器 | 该框架没有挂起等审批和持久化续开的原语，人工确认点、崩溃恢复、缓存友好的拼装都要绕开它另做；且与自研编排核的既定决策冲突 |

## 5 确认点与人工/自动模式

### 5.1 确认点清单

| 编号 | 确认点 | 位置 | 判定内容 |
|---|---|---|---|
| K1 | 想法澄清 | 讨论会议内 | 回答就绪检查提出的澄清问题；没有未答问题时跳过 |
| K2 | 参会名单 | 讨论会议内 | 确认或编辑主持人提议的名单 |
| K3 | 轮次共识 | 讨论会议内 | 停滞或到轮次上限时：带着分歧整合、给指导语继续、授权主持人裁决 |
| K4 | 方案确认 | 工件确认点 | 送评审、直接通过、驳回 |
| K5 | 评审裁决 | 工件确认点 | 通过、编辑后通过、驳回 |
| K6 | 需求确认 | 工件确认点 | 通过、编辑后通过、驳回 |
| — | 升级 | 任意 | 轮次耗尽、预算耗尽、模型判定无效、执行失败达到上限；始终由人处理 |

### 5.2 自动化等级预设

| 确认点 | L1 全程人审 | L2 关键点人审（默认） | L3 仅兜底 |
|---|---|---|---|
| K1 想法澄清 | 人回答 | 人回答 | 需求方代理回答；答不了的记为假设 |
| K2 参会名单 | 人确认或编辑 | 人确认或编辑 | 主持人提议即生效 |
| K3 轮次共识 | 每轮暂停由人判 | 程序按闭合规则判；停滞或到上限转人 | 程序判；到上限自动退到"无反对即可"，仍不一致的记为待确认 |
| K4 方案确认 | 人 | 人 | 直接送评审 |
| K5 评审裁决 | 人 | 人 | 裁决模型 |
| K6 需求确认 | 人 | 人 | 裁决模型 |
| 升级 | 人 | 人 | 人 |

每个确认点可以单独覆盖，配置入口是"模板默认 → 新建运行时覆盖 → 运行中修改"。设计之后的门沿用原有等级语义；它们可以按同一格式启用模型判定（§5.3）。

### 5.3 模型判定的规则

| 规则 | 说明 |
|---|---|
| 判据显式 | 每类确认点有一份判据文本，放在模板里，可编辑。工件确认点之外提供一份通用的工件判据，设计之后的门可以直接套用 |
| 先判后读 | 裁决模型先写出自己的判断要点，再读被审内容和证据 |
| 程序前置检查 | 调用裁决模型之前，程序先核对前置条件。评审裁决点要求评审结论为接受或有条件接受且修订已验证；需求确认点要求确认结论为通过。前置条件不满足时不调用模型，直接按驳回路由 |
| 无效转人工 | 裁决模型的输出无法解析或自相矛盾时，转为人工确认点。此规则不可关闭 |
| 驳回有上限 | 模型驳回时，反馈进入负责回修的环节；连续驳回达到上限（默认 2 次）后转人工 |
| 可否决 | 每次模型判定都记录谁判的、依据、保留的异议。用户随时可以通过重置节点否决 |
| 异构默认 | L3 的 K5/K6 优先选择与全部参会者不同家族的裁决模型；同家族时在确认点上标注并提示用户复核，不静默通过 |

异构默认的实现：`judge` 角色没有显式绑定模型时，在可用模型里优先取与全部参会者都不同家族的；用户绑定过模型就照用。裁决模型与全部参会者同家族时判定照常生效、不阻断，但门的决定（`data.heterogeneity`）、`checkpoint_decided` 事件与节点日志都标注"同家族，请复核"，确认点列表与事件流显示提示，用户可以重置节点否决。

方案确认点在模型模式下不调用裁决模型，直接送评审。

### 5.4 人工/自动模式矩阵

| 类别 | 事项 |
|---|---|
| 必须由用户 | 提供想法与背景材料；预算耗尽或模型判定无效时的兜底 |
| 用户或模型均可，每项能单独选 | 澄清问题的回答（用户或需求方代理）；人数与名单（用户指定或主持人提议）；每轮共识（每轮暂停给用户看，或程序按规则判）；未决议题的处置（用户裁，或授权主持人裁）；方案确认；评审裁决；需求确认；评审意见的处置（作者处置，或用户改判） |
| 运行中随时可做 | 改名单；改决策点账本；编辑任何工件；增补评审意见；把已挂起的确认点交给模型判；修改运行级配置；停止、重置、重试 |
| 仅程序处理，不开放 | 调度与状态机、挂起与恢复、崩溃恢复、并发与预算扣减、重试；共识状态的计算（规则可配，计算本身不开放）；结构校验和追踪矩阵的机械核对；缓存与压缩的执行（阈值可配）；模型判定失败转人工 |

全自动模式下有两处不会全自动：预算耗尽，以及模型判定无效。这两件事没有安全的自动出路，运行会停下等待。

### 5.5 参数配置原则

每个数值参数分三层：

- **硬上下限**：程序校验，超出即拒绝并给出提示。硬限只为防止崩溃或超出框架能承载的范围。
- **建议范围**：以文字提示显示在界面上。
- **默认值**：人数这类"由主持人决定更合适"的参数，默认给范围而不是定值。

| 参数 | 硬上下限 | 初始默认 | 提示 |
|---|---|---|---|
| 参会人数 | 1–99 | 范围 3–5，范围内由主持人定；也可以设成固定人数或指定名单 | 建议 3–5；超过 10 收益很小，耗时线性增长 |
| 讨论轮次上限 | 1–99 | 20 | 通常 2–5 轮内收敛 |
| 每个决策点每轮交锋次数 | 1–9 | 2 | — |
| 停滞判定（连续几轮无人改立场） | 1–9 | 2 | — |
| 方案复核轮次上限 | 1–9 | 2 | — |
| 评审复审轮次上限 | 1–9 | 3 | — |
| 需求复核轮次上限 | 1–9 | 3 | — |
| 模型连续驳回上限 | 1–9 | 2 | — |
| 评审者人数或名单 | 1–99 | 沿用讨论的角色 | 建议至少一名绑定不同家族的模型；0 表示不限制（下限为 0 时仍要求至少一名评审者） |
| 压缩触发阈值 | 50%–95% | 80% | — |
| 压缩后目标占用 | 20%–60% | 50% | 须比触发值至少低 20 个百分点 |
| 全量历史（对照实验） | 布尔 | 关 | 打开时讨论协议每轮带上此前所有轮次的逐字发言，仅供 §3.3 H1 的对照实验，不用于日常 |

硬上限取 99 的依据：每多一个角色，提示词体积和耗时都线性增长，并发受供应商并发数限制，再多没有实际意义。

### 5.6 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 只设三个固定的自动化等级 | 满足不了"想多介入时有足够接口"的要求 |
| 每个确认点必须单独配置 | 默认全甩给产品时配置负担太重；所以预设作底、逐点覆盖 |
| 模型判定无效时按通过处理 | 违反"模型不能批准自己"的红线 |
| 讨论轮次上限默认取小值以省费用 | 产品的目标是收敛；费用由停滞保护、token 预算和压缩控制，不靠压低轮次 |

## 6 会议运行时

### 6.1 节点与协议

引擎新增节点类型 `MEETING`。节点配置里的 `protocol` 取 `discussion`、`review`、`confirm` 三者之一，分别对应讨论、评审、确认协议。每种协议是一串有序的步骤；运行器逐步执行，一步的结果落盘之后才推进到下一步。同一份运行时代码承载三种协议，差别只在步骤序列和提示词。

### 6.2 状态与续开、重开

```
新建 ──→ 进行中 ──┬─→ 步骤全部完成 ──────────────→ 已完成
                  ├─→ 遇到人工确认点 ─→ 挂起 ──(确认)──→ 进行中
                  └─→ 判定需要回流 ──→ 等待返工 ─(上游改完)→ 进行中（下一轮）
已完成 ──(带着反馈)──→ 进行中（复议）
已完成，或挂起但确认点被重置 ──(不带反馈)──→ 旧会议归档，新建一场
```

运行器进入一个会议节点时，先看有没有反馈，再看已有会议的状态：

| 条件 | 行为 |
|---|---|
| 该节点还没有会议 | 新建 |
| 节点带着反馈 | 续开。反馈作为一条用户发言进入纪要；已完成的会议由此进入复议 |
| 没有反馈，会议在进行中 | 从当前步骤续开（崩溃、超时、停止后恢复，或失败重试） |
| 没有反馈，会议在挂起，且确认点已有决定 | 读取决定后续开 |
| 没有反馈，会议在等待返工 | 续开，进入下一轮复核 |
| 没有反馈，会议已完成 | 旧会议归档，新建一场 |
| 没有反馈，会议在挂起，但确认点已被重置关闭 | 旧会议归档，新建一场 |

判断"带不带反馈"的依据是节点配置里的反馈字段：回流、驳回、带反馈的重试都会写入它。

### 6.3 挂起与确认点

- 会议内的确认点是一条挂在会议节点上的门记录，带所属会议（`meeting_id`，可空）、确认点类型（`kind`）、载荷（`payload_json`）和决定（`decision_json`）。它复用现有的挂起、持久化和唤醒机制：不占协程，进程重启后原样保留。
- **不走 reject 的级联分支**：现有 reject 强制 `target_node` 并级联重置下游，语义与会议确认点不同。`decide_gate` 识别出会议内确认点（节点类型是 `MEETING` 且门带类型）后，只把决定写进 `decision_json`，不要求 `target_node`，也不重置下游。节点回到待调度，会议运行器续开时读取决定，由确认点类型映射到续开、定点回流或结束，只影响本次会议及其目标节点。
- 用户或模型做出决定后，节点回到待调度；运行器读取决定，从挂起处继续。
- 挂起原因是一个可扩展的集合，目前只有确认点一种。插话不造成挂起（§6.5）。

### 6.4 定点回流

节点执行结果可以带一条回流指令，写明把哪些节点定点重开、带什么反馈、自己记第几轮。编排器收到后：

1. 把指令里的目标节点置回待调度，写入反馈；**不级联重置下游**。
2. 把当前节点置回待调度，轮次加一。
3. 超过轮次上限时，转为人工确认点。

评审会议同时依赖方案确认和讨论会议，需求确认会议依赖需求分析师。顺序由依赖关系保证：目标节点重跑完成之前，发起回流的节点不会被调度。现有代码评审节点的回退逻辑保持不变。

实现上有四点收窄：编排器不校验回流目标是否为发起节点的直接依赖，顺序只由模板依赖保证；回流轮次用尽的保底门是不带确认点类型的普通门，批准后按工件门处理，没有"再给一轮 / 接受现状"的闭环；评审协议在返回回流指令之前就把 `rework_pending` 写进会议状态，进程在编排器接受回流前中断时，会议会按"已回流"加一轮而目标节点没有重开（§15.3）；回流不作废依赖目标旧版本的下游门——评审退回讨论后，方案确认点保持已通过，修订后的方案仍要经过评审裁决点（K5），由人过目（是否改为自动作废下游门，见 §15.2）。

### 6.5 插话

用户可以随时提交一条插话。运行器在每次发起模型调用之前检查插话队列：有排队中的插话时不再发起新调用，把插话作为一条"用户发言"写进纪要并推送事件。主持人在下一步必须回应它，然后继续。挂起期间提交的插话在恢复后首先处理。

### 6.6 恢复与超时

- 每一步的结果先落盘再推进。并行的步骤（如全员表态）只补做还没有结果的角色。
- 会议节点的默认超时是 1 小时，可配置，0 表示不限。一场无人介入的会议是许多次模型调用串起来的。单次调用的超时仍由供应商配置约束。
- 超时或取消后，未回执的那一次调用会在重入时重做，已完成的调用不重复。
- 会议内确认点每次续开都新建一条执行记录，因此失败重试预算按尝试总数计，指标会把续开计成重试。
- 恢复流程 `recover()` 目前是全局操作：扫描并重新拉起库里所有 `created`、`running`、`waiting_human` 的运行。单机单实例是主线；多实例同时在线时会重复拉起，需要按运行过滤或加心跳防护（§15.3）。

### 6.7 与节点动作的衔接

| 动作 | 对会议节点的含义 |
|---|---|
| 带反馈的重试 | 续开并复议 |
| 不带反馈的重置或重试 | 重开 |
| 注入反馈 | 同带反馈的重试 |
| 跳过 | 产出工件已存在才允许，否则拒绝 |

实现口径（2026-11-27）：

- **跳过**：会议节点按"该节点自己写过产出工件"判断（任意版本，`artifacts.created_by_node` 等于节点键），没写过就拒绝，`can_skip` 也显示为否；其他节点写的同名工件不算。人工门节点仍一律不可跳过。
- **反馈动作**：带反馈的重试与注入反馈都经 `with_feedback` 写入，带 `feedback_kind="user"` 并把 `feedback_seq` 加一；会议的进入判定同时看"来路属于要复议的集合、序号与已处理序号不同、内容非空"，所以这两种人工动作都会让会议按复议续开。不带反馈的重试/重置会清掉反馈与来路，但保留序号（只增不减）。
- **续开与重开**：会议仍由运行器按 §6.2 判定续开还是重开；节点动作只把节点放回待调度，不改会议状态。

### 6.9 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 把每一步展开成依赖图上的子节点 | 轮数不固定，无环的依赖图表达不了循环；节点数量随轮数膨胀；运行图上的血缘与门阻挡逻辑都假设节点集合基本稳定 |
| 每个步骤占一次执行记录 | 尝试次数、重试指标会失真，一个正常的会议看起来像失败了很多次 |
| 评审会议在自己的执行过程中直接调用讨论会议 | 讨论会议内部的人工确认点无法挂起，人工模式下走不通 |
| 人工驳回也清空纪要重开 | 评审回修和用户的驳回意见都需要在已有讨论的基础上处理，重开会丢掉全部上下文 |

## 7 讨论协议

### 7.1 参会者

| 角色 | 说明 |
|---|---|
| 主持人 | 组织流程、提炼决策点、维护账本、整合成稿。不提出内容上的立场，不替用户裁决 |
| 参会者 | 各持一个视角。人数与名单见 §11 |
| 需求方代理 | 可选。只回答事实问题，不提方案，不参与表态，不计入了结条件（§7.6） |

只有一名参会者时，跳过全员表态和交锋，立场即共识。

### 7.2 步骤

| 步骤 | 执行者 | 做什么 | 落盘 |
|---|---|---|---|
| 会前准备 | 主持人 | 从想法与背景材料提炼简报：目标、用户、约束、假设、待澄清。想法过于笼统时列出澄清问题 | 简报写入想法工件的新版本 |
| 澄清 | 需求方代理或用户 | 逐条回答待澄清问题 | 回答作为发言 |
| 名单 | 主持人提议，用户确认或自动生效 | 在人数范围内挑选角色并写明理由，必要时提临时角色 | 参会者 |
| 独立立场 | 全体并行，互不可见 | 写立场简报：必须保证的事项、主要风险、建议路线、疑问 | 发言 |
| 议题提炼 | 主持人 | 把立场合并成决策点清单。每个决策点有一个问题和候选项，记录提出者 | 决策点 |
| 全员表态 | 全体并行 | 读全部立场和完整清单，对每个决策点表态并写理由；可以补充遗漏的决策点 | 表态矩阵 |
| 交锋轮次 | 主持人组织 | 见 §7.4 | 发言、交锋摘要、表态矩阵 |
| 共识确认点 | 用户或规则 | 停滞或到轮次上限时处理未决议题（§7.4） | 决定 |
| 整合成稿 | 主持人 | 按账本写建设方案。待定的决策点写进"待确认问题"，连同各方理由 | 建设方案 |
| 全员复核 | 全体并行 | 读初稿，逐个确认已了结的决策点被如实反映；有问题的由主持人改稿，只复核被标记的 | 复核结论 |

### 7.3 表态与账本

**表态分五级。**

| 等级 | 名称 | 含义 | 附加要求 |
|---|---|---|---|
| 1 | 支持 | 认同 | — |
| 2 | 有保留支持 | 有顾虑，但能接受 | 写明顾虑 |
| 3 | 弃权 | 不表态支持，也不反对 | 写明原因 |
| 4 | 需更多信息 | 信息不足以判断 | 写明缺什么 |
| 5 | 反对 | 不能接受 | 写理由和替代建议 |

**决策点账本**是全部决策点的集合，由程序落盘，每个决策点包含：

- 编号、问题、候选项、提出者。
- 状态：讨论中、已一致、主持人裁决、待定、复议中。
- 结论、理由摘要、交锋摘要。
- 表态矩阵：每个参会者在每个决策点上的最新等级、理由、表态轮次；改过立场的保留历史。
- 来源轮次、了结轮次；复议时指向它的前身。

账本 JSON 留有 `superseded_by` 字段，但当前实现从未写入复议前身关系；复议是重置同一决策点的表态，不新建前身（§15.2 第 3 条）。

账本是会议的进度账本：每次发言的上下文里带着它，中断或压缩之后靠它续上。

### 7.4 交锋轮次与闭合

**每一轮：**

1. 主持人确定本轮要讨论的决策点，有反对的排在前面。
2. 逐个决策点交锋：立场不同的参会者依次"主张 → 质疑 → 回应"，其余人旁听。主持人可以点名需求方代理回答事实问题，可以要求展开或纠偏。每个决策点每轮的交锋次数有上限。
3. 主持人为每个仍未了结的决策点写一段交锋摘要。
4. **全员重新表态**（并行）。改立场必须写理由。
5. 程序按闭合规则计算每个决策点是否了结，并判断是否停滞。

全部了结即停，进入整合成稿。

**闭合规则**由用户配置：

| 规则 | 一个决策点算"了结"的条件 |
|---|---|
| 全体一致（默认） | 所有参会者都是支持或有保留支持 |
| 无反对即可 | 无人反对，且无人需要更多信息；弃权不阻塞 |
| 主持人裁决 | 交锋达到规定次数后仍未了结的，由主持人裁决并写理由；反对意见记入异议 |

**实现的收窄**：交锋目前按决策点的创建顺序进行，没有按反对强度排序；主持人在交锋中还不能点名需求方代理回答事实问题，`question`/`answer` 两类发言从未产生。现行交锋形态是"主张 → 质疑 → 回应"（§15.2 第 2 条）。

**停滞**指连续若干轮没有任何参会者改变任何未了结决策点上的表态等级。停滞或到达轮次上限时进入共识确认点：

- 由人判定时，三个选择：带着分歧整合（未了结的记为待定）、给指导语继续讨论、授权主持人裁决。
- 由规则判定时，默认转人工；全自动预设下先退到"无反对即可"，仍未了结的记为待定。

待定的决策点不会从账本里消失：它们写进建设方案的"待确认问题"，在方案确认点上呈现给用户。

### 7.5 复议

带着反馈续开时，讨论会议走复议：主持人把反馈或评审意见转成要重开的决策点（已有的置为复议中，缺的新建）→ 对重开的决策点全员表态 → 交锋轮次 → 必要时进入共识确认点 → 整合成稿，方案出新版本并逐条写修改说明 → 全员复核。

### 7.6 需求方代理

- 只依据背景材料和用户给出过的回答作答。
- 每条回答标注出处：引用材料片段，或指向某条用户回答。
- 没有出处的回答标为假设。
- 遇到材料回答不了的问题：由人判定时挂起问用户；全自动时记为假设，并进入方案的待确认问题。

### 7.7 每次发言的上下文

| 区 | 内容 | 变化方式 |
|---|---|---|
| 冻结区 | 平台规则与会议章程（想法原文、简报、名单、闭合规则），所有角色共用 | 整场会议不变 |
| 冻结区 | 角色人设 | 整场会议不变 |
| 冻结区 | 决策点清单、已了解决策点的摘要、本轮开始时的表态矩阵与交锋摘要 | 每轮开始时更新一次 |
| 追加区 | 本轮交锋的逐字发言 | 只追加 |
| 尾部 | 主持人这次的指令，轮次等状态信息 | 每次不同，很短 |

每轮切换时，上一轮的逐字交锋被新的表态矩阵和交锋摘要取代；全文纪要始终落盘。这样排的原因见 §10.1。

### 7.8 产出

**会议纪要**（`discussion` 工件）依次包含：会议信息（想法摘要、参会者、轮次、闭合规则）、决策点账本、表态矩阵、各角色立场摘要、各决策点的交锋记录摘要、未决议题。同目录另存一份账本的 JSON 文件，供后续节点读取。

**建设方案**（`proposal` 工件）依次包含：目标与成功标准、范围、总体方案（逐个决策点写结论和依据，标注决策点编号）、关键流程、里程碑与验收、风险与缓解、待确认问题、决策点索引。

### 7.9 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 自由发言，不设独立立场环节 | 先发言者会带偏后面的人 |
| 主持人输出自己的观点 | 没有证据支持主持人应当持有内容立场；裁判自身的偏差有实验支持 |
| 方案由独立的方案架构师角色执笔 | 多一次有损交接；账本的维护者和方案的执笔者分离，好处不足以抵消 |
| 表态只有同意和反对两档 | 一旦只有是非，小顾虑也只能表达成反对，或者被压成同意 |
| 轮末只让交锋双方更新表态 | 其余参会者就不必对全部决策点负责，与"全员知悉、全体同意"的口径矛盾 |
| 未决议题由主持人默认裁决 | 用户明确要求共识是全体同意；裁决只作为授权后的选项 |

## 8 评审协议

### 8.1 参与者

| 角色 | 说明 |
|---|---|
| 评审主席 | 组织流程、汇总分级、主持讨论、验证修订。对有分歧的条目定夺分类与级别，并记录异议。整体结论由程序按规则得出（§8.4） |
| 评审者 | 默认沿用讨论会议的参会角色模板，开新上下文，用评审模式的提示词。用户可以另行指定名单或人数范围。讨论会议的主持人和需求方代理不做评审者 |
| 执笔者 | 讨论会议的主持人，只在回应和修订环节出场 |
| 需求方代理 | 可以被咨询，回答关于用户意图的问题 |

程序检查是否至少有一名评审者绑定了与讨论会议的参会者不同家族的模型，没有就在确认点上提示。

### 8.2 步骤

| 步骤 | 执行者 | 做什么 |
|---|---|---|
| 准备 | 评审主席 | 确认方案和账本齐全；确定评审者与检查单 |
| 先写要点 | 评审者并行 | 只读想法、简报、账本，写下"我会重点查什么" |
| 独立评审 | 评审者并行 | 对照方案和自己写的要点，输出优点和问题清单 |
| 汇总分级 | 评审主席 | 去重，确认级别，确认分类。没有位置或没有建议的问题降为提示级 |
| 作者回应 | 执笔者 | 逐条回应：采纳，或说明不采纳的理由 |
| 会议讨论 | 评审主席组织 | 只讨论评审者之间有分歧的条目和被执笔者反驳的条目，限一轮。评审者不必一致，由主席定夺这些条目的分类与级别，并记录异议 |
| 裁决 | 程序 | 按各条意见的分类和级别得出整体结论（§8.4） |
| 文字级修订 | 执笔者 | 按文字级问题清单修订方案，出新版本 |
| 验证修订 | 评审主席 | 逐条确认已改好；未改好的退回修订，至多再一轮 |
| 写报告 | 评审主席 | 报告作为评审工件的新版本 |
| 回流 | 程序 | 有决策级问题时定点回流讨论会议，之后增量复审 |

"先写要点""会议讨论"可以各自关闭。

### 8.3 评审意见的结构

每条意见包含：编号、级别（阻塞、重要、提示）、分类（决策级或文字级）、位置（决策点编号或方案章节）、问题、修改建议、执笔者回应、处置状态、用户的改判。

- 决策级指要改动已了结的决策点；文字级指表述、完整性、一致性方面的修改，不动决策。
- 级别达到阻塞线且缺少位置或建议的，自动降为提示级。阻塞线默认是"重要"及以上，可配置。

### 8.4 裁决规则

| 条件 | 结论 | 后续 |
|---|---|---|
| 存在达到阻塞线的决策级意见 | 退回 | 回流讨论会议复议；方案出新版本后增量复审 |
| 没有决策级意见，但有达到阻塞线的文字级意见 | 有条件接受 | 执笔者修订，主席验证 |
| 其余 | 接受 | 写报告 |

结论由程序根据意见的分类和级别得出。评审主席负责的是归类，以及对有分歧条目的定夺。

### 8.5 增量复审

回流之后评审会议进入下一轮，只核对两样：

- 上一轮每条决策级意见的处理结果。
- 改动过的决策点和对应的章节。

复审轮次有上限（§5.5）。到上限仍有决策级意见时，转为人工确认点：接受现有方案、给反馈再评一轮、或停止。

### 8.6 用户介入

- **评审裁决确认点**：通过；编辑方案后通过；驳回。驳回反馈作为用户提出的评审意见进入评审会议，由主席分类后按同一规则流转。
- **逐条改判**：通过接口改写执笔者对某条意见的处置，下一轮按改判执行。只改采纳与否，不改意见本身是否成立。
- **交给模型判**：已挂起的确认点可以转交裁决模型。会议节点上的确认点不调裁决模型：按"仅兜底"等级的做法落一个决定（澄清记为假设、共识授权主持人裁决、轮次用尽接受现状）。会议节点上不带类型的安全网确认点不能转交，接口直接拒绝，只能人工处理。

### 8.7 报告

评审报告依次包含：评了什么、谁评的、轮次、结论、问题清单及处置状态、优点、保留的异议。优点跨轮累积；`reviewed_round` 目前只写不读（§15.3）。

### 8.8 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 评审者沿用讨论会议的上下文 | 参与过讨论的角色带着既有立场，且模型偏好自己产出的内容 |
| 由评审主席的模型给出裁决 | 结论应当能由程序核对；模型只负责归类 |
| 评审者原地修改方案 | 改过的版本没有经过讨论会议同意，共识的链条断了；正式评审的原则是会上只澄清问题 |
| 要求评审者达成一致后才有结论 | 同行评审的通行做法是允许分歧，由主席归纳并记录异议 |
| 回修后不复审 | 执笔者可以口头接受、实际不改；增量复审的成本有限 |

## 9 需求确认协议

### 9.1 需求规格与追踪矩阵

需求分析师依据已确认的方案和账本拆出需求规格：每条需求有唯一编号、EARS 句式、验收标准、优先级。规格末尾有两张表：

| 表 | 列 | 用途 |
|---|---|---|
| 需求追踪矩阵 | 需求编号、来源决策点、方案章节、优先级 | 程序核对覆盖率 |
| 非需求类决策 | 决策点、不产出需求的理由 | 让过程性的决策点有明确的交代 |

每条修改附一句修改说明，对应一条核对意见。

### 9.2 参与者与步骤

确认会议有三类角色：

- **语义核对者**：讨论会议的参会者，加上需求方代理。核对需求是否忠实于决策点、是否偏离用户意图。
- **质量评审者**：默认与评审会议的评审者相同，用户可以另行指定；建议至少一名绑定不同家族的模型。按需求质量特性检查。
- **评审主席**：把各方的意见去重归类。整体结论由程序得出。

全部开新上下文。依据是账本——账本记着每个决策点的结论和理由，不需要回放整场讨论。

| 步骤 | 执行者 | 做什么 |
|---|---|---|
| 程序核对 | 程序 | 解析追踪矩阵，检查：每条需求编号唯一且引用了决策点；每个已了结的决策点有需求落点，或被列为非需求类决策；没有"待定"字样；EARS 句式和验收标准齐全；优先级齐全 |
| 写预期 | 讨论会议的参会者与需求方代理并行 | 只读账本，逐个决策点写出"需求里必须出现什么内容" |
| 忠实性核对 | 同上，第二步 | 对照实际的需求条目，逐个决策点给出：忠实、走样、遗漏、凭空新增，附理由 |
| 质量评审 | 质量评审者并行 | 按需求质量特性逐项检查，问题定位到需求编号 |
| 汇总裁决 | 评审主席归类，程序裁决 | 合并成给分析师的结构化清单，得出通过或不通过 |

### 9.3 覆盖方式

| 方式 | 含义 | 默认 |
|---|---|---|
| 全员核对全部 | 每个角色核对每个决策点 | 是 |
| 分区核对 | 每个决策点由参与过它的角色核对，需求方代理核对全部 | 否 |

默认取全员，和讨论阶段"全员知悉"的口径一致。所有角色读的是同一份需求规格，这部分在它们之间共享缓存。

### 9.4 裁决、回流与复核

以下任一情况为不通过：已了结决策点上出现走样或遗漏；出现追溯不到任何决策点的需求；程序核对未通过；质量评审有达到阻塞线的意见。

**机械核对不过时不调模型**：准备步骤先跑程序核对，有任何一条不通过就直接把机械问题整理成回流清单，跳过"写预期、忠实性核对、质量评审"这些模型步骤，直接进入回流与修订。这样语法或追踪层面的错误不必花一遍模型调用的代价，也不会掩盖真正需要语义判断的问题。

不通过时定点回流需求分析师，带着结构化清单修改。之后确认会议进入下一轮：程序核对全量重做，忠实性核对和质量评审只看被标记的条目和改动过的需求。到上限转人工。

### 9.5 用户介入

需求确认确认点：通过；编辑后通过；驳回。驳回反馈作为用户提出的意见进入确认会议，分类后交分析师修改。

### 9.6 报告

确认报告作为评审工件的新版本，依次包含：程序核对结果、逐决策点的忠实性结论、质量评审意见、结论、问题清单。

报告只含本轮的忠实性与质量结果。机械核对失败后重跑的轮次里，语义核对整类被跳过，最终仍可能通过——这是"只报本轮"的字面结果；是否接受、以及上一轮没有任何忠实性结果时是否回退全量核对，列在 §15.2（第 10 条）。

### 9.7 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 回到讨论会议，由参会者整体读一遍确认 | 整体性的自审不可靠；账本已经承载了全部决策和理由，不需要回放讨论 |
| 只由主持人确认 | 单一判断不如分解后的多点核对；也无法体现"全员确认" |
| 不通过时把需求规格作为输入交给会议迭代出新版本 | 需求规格是单一作者的产物，由会议迭代会模糊作者责任；清单交给作者修改更直接 |
| 由主持人或评审主席代为修改需求规格 | 修改的责任归作者；核对的责任归核对者 |

## 10 上下文策略与通用上下文模块

### 10.1 布局

每次调用的上下文分三区，顺序固定：冻结区、追加区、尾部。这样排的原因是前缀缓存：两次请求从开头到某位置完全相同，这部分命中；之后的全部按全价计。冻结区在前，追加区只追加，那么每次调用里未命中的只有新增的内容。如果让会变的内容（比如每次都更新的账本）排在前面，从它往后整段失效，能命中的只剩几百个 token 的角色提示，不够起缓存的门槛。

### 10.2 运行时约束

| # | 约束 |
|---|---|
| R1 | 系统提示、工具定义、会议章程在一次执行内逐字节不变；轮次号、时间戳这类动态信息一律放尾部 |
| R2 | 冻结区之后只追加；每轮切换时才更新冻结区里的账本快照 |
| R3 | 压缩有滞后：占用到阈值才触发，一次压到目标占用以下，保证两次压缩之间隔足够多轮 |
| R4 | 工具结果进入历史之前先裁剪：长输出只留相关片段和文件清单 |
| R5 | 隔离优先于压缩：每个节点、每个角色、每场会议的上下文彼此独立。带工具的角色在自己的循环里处理中间过程，只把结论作为一条发言写进纪要 |
| R6 | 结构化状态代替逐字历史：账本是会议的进度账本 |
| R7 | 程序能判的不调模型：共识状态由程序计算；轮次推进、公平性检查由代码做 |
| R8 | 调用结果先落盘再推进：恢复时最多重做被中断的那一次调用 |

### 10.3 压缩

- 触发条件：估算占用达到可用窗口的阈值（可用窗口＝上下文窗口减去输出预留）。
- 压缩结果作为一条摘要消息追加进日志，原文不删；之后的视图从最近一条摘要开始。
- 逐块压缩最旧的内容，直到估算占用降到目标占用以下。
- 预算不足时按段降级。例如表态矩阵只留等级，去掉已了结决策点的理由。

### 10.4 已知限制

- 用户挂起期间缓存可能过期，恢复后的第一次调用要重新处理整个前缀。这与布局无关。
- 缓存命中是否折扣计费取决于供应商的计费方式。
- 单次压缩的摘要调用最多 8 次（`compact.MAX_SUMMARY_CALLS`）：块数超出时只压最近的几块，更早的内容在摘要里注明没有纳入；合并保留部分的整组也计入上限，因此极端情况下可能停在触发线之上。块间发 `node_log`，`context_compacted` 记调用次数与送入的 token 量。
- 压完仍在触发线之上时冷却 3 步再试（`agent_loop._COMPACT_COOLDOWN_STEPS`）；可压内容只剩上一版摘要时直接跳过，不再把摘要摘要一遍。
- 工具循环的第一条用户消息（任务提示）在第一次压缩时会被并入摘要，摘要提示词没有要求保留原始指令。
- 会议压缩的摘要按"会议 + 轮次"存进会议状态（覆盖条数、覆盖前缀的指纹与正文）：同一轮的并行发言与后续发言在前缀未变时直接复用，轮次切换或前面迟到的发言改变了覆盖前缀时重算。
- 装配器的边界：每段下限 256 token，段多而小时一段也缩不动；`truncate_to_tokens` 不是硬上限；占用估算与适配器的 `count_tokens_estimate` 是两套口径；空文本段已过滤。
- JSON 降级路径（`_run_json_protocol`）没有压缩钩子；工具循环的全文仍写旧的 `messages` 表，新的会话日志里只有摘要。§10.2 的 R4（工具结果进历史前先裁剪）与 §10.5（有状态的工具循环记录每一步）没有任务承接；工具结果目前只有工具注册表的头尾截断。
- 会话日志的并发安全依赖连接池 size=1：`conversations` 没有唯一约束；`load_messages` 的默认 `limit=500` 取的是最早的一段。

### 10.5 模块边界与布局

| 管 | 不管 |
|---|---|
| 会话存储：只追加的消息日志 | 记忆检索（沿用现有记忆模块） |
| 视图装配：分段、预算、阈值压缩 | 各家协议的适配（只在适配器里补一个缓存命中数的解析） |
| 用量与缓存命中统计 | — |

```
backend/app/conversation/
  store.py          会话与消息日志的落盘与读取
  builder.py        视图装配：分段、预算、阈值压缩
  policy.py         策略与默认值
  telemetry.py      用量与缓存命中统计
```

**给使用方的接口**（设计层面）：

| 接口 | 用途 |
|---|---|
| 追加与读取会话消息 | 有状态的工具循环记录每一步 |
| 按段装配 | 调用方提供带标记的若干段（冻结、追加、尾部），得到发给模型的消息列表和占用统计 |
| 冻结段校验 | 比对冻结段内容，发现变化时推送告警事件 |
| 条件压缩 | 占用达到阈值时压缩，否则原样返回 |

### 10.6 使用方

| 使用方 | 用法 |
|---|---|
| 会议运行时 | 每次发言的上下文都经装配器拼出 |
| 现有的工具循环 | 每次请求模型之前调用条件压缩。占用不到阈值时原样返回 |

### 10.7 可观测

- 适配器解析缓存命中的 token 数，记到执行记录上。现状：只有 OpenAI 兼容的流式路径与 Anthropic 的回复解析真实用量与缓存命中；Gemini 与 JSON 降级路径按估算。
- 每次压缩推送事件，带上压缩前后的占用。
- 运行指标增加上下文一段：压缩次数、命中率。

### 10.8 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 每次调用拼接全部历史 | 发送量随轮数平方增长；信息散落在多轮里时模型会漏掉中间的内容 |
| 每轮固定清空上下文 | 模型不再记得此前轮次的理由，账本要足够完整才能补上 |
| 每轮固定压缩 | 每次压缩都让前缀缓存失效，等于放弃缓存 |
| 清空存储以缩短上下文 | 违反"存储永远是全文"的红线；审计与恢复都需要全文 |
| 只为会议做一套专用的拼装逻辑 | 后半段的工具循环同样需要阈值压缩；做成通用模块两边都能用 |

## 11 角色库与名单

### 11.1 内置角色

| 角色 | 用途 |
|---|---|
| 主持人 | 讨论会议的主持与整合执笔 |
| 评审主席 | 评审会议和确认会议的主席 |
| 架构、用户体验、测试与质量、安全与合规、运维与成本、业务价值 | 参会角色。讨论时各持视角，评审时按各自专长做评审者，确认时做语义核对 |
| 需求方代理 | 只回答事实问题的受限角色 |
| 需求分析师 | 产出需求规格与追踪矩阵 |
| 裁决模型（judge） | 只在确认点的模型判定模式中使用；不参加讨论/评审会议，先写判断要点再读工件，输出无效转人工 |

设计之后的角色不变。记录员不设模型角色：结构化的记录由程序落盘。

### 11.2 名单怎么定

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | 用户指定 | 指定了具体角色或固定人数，就按用户的来。可以在新建运行时指定，也可以在名单确认点上编辑 |
| 2 | 主持人提议 | 用户没有指定时，主持人读想法、简报和角色库里每个角色的一句话简介，在人数范围内挑选并写明理由 |
| 3 | 临时角色 | 角色库里没有合适的视角时，主持人可以提临时角色，只在本场有效。用户可以把它保存进角色库 |

评审者的名单同理：用户指定优先，否则沿用讨论会议的参会角色。

### 11.3 自定义角色

- 自定义角色可以新建、编辑、删除。启动时的内置角色同步不碰它们。
- 内置角色只能编辑，不能删除；退役的讨论角色是唯一例外（见下条）。
- 旧的讨论角色如果被用户改过，保留为自定义角色；没改过的在启动时清理。`discuss_pro` / `discuss_con` / `discuss_mod` / `proposal` 按此规则处理。清理只做一次启动同步，没有迁移：升级前已在飞的运行如果仍引用被清理的旧角色，恢复后会致命失败（§15.3）。
- 新旧 key 的对应：`facilitator` 接管主持与汇总（原 `discuss_mod` 的蒸馏职责），参会角色接管 `discuss_pro`/`discuss_con`；原 `proposal` 不再单独设角色，由 `facilitator` 汇总成方案。退役 key 不新建，依赖它们的旧运行不能续跑（§4.1）。

### 11.4 角色模板的元数据

每个角色模板带一段元数据：一句话简介、专长标签、适合担任的会议角色。主持人挑选名单时读的就是一句话简介。

### 11.5 提示词的写法

人设写具体的偏好，不写标签。例如"优先保证可验证性，对没有验收标准的条目一律反对"比"你是测试专家"更能拉开角色之间的差异（依据见 §3.1 的 E5）。

### 11.6 备选与取舍

| 备选 | 不采纳的原因 |
|---|---|
| 每场会议由主持人临时生成全部角色 | 角色没有持续的记忆，不能复用，质量不稳 |
| 只能从固定的角色库里选 | 用户无法按自己的需要配置参会角色 |
| 主持人和评审主席合并为一个角色 | 评审的主持者应当独立于方案的执笔者 |

## 12 数据模型、工件、接口与事件

实现之后，字段与路径的权威定义以代码为准；本节是设计层面的约定。

### 12.1 新增表

| 表 | 内容 |
|---|---|
| 会议 | 所属运行与节点、协议、状态、当前步骤、轮次、会议章程快照、生效参数、协议的中间状态 |
| 参会者 | 角色模板或临时人设、模式、模型、来源、专长标签 |
| 发言 | 序号、轮次、步骤、发言人、类型、所属决策点、内容、结构化载荷、用量与缓存命中数 |
| 决策点 | §7.3 |
| 插话请求 | 内容、状态 |
| 会话、会话消息 | 上下文模块的只追加日志；摘要消息标记压缩边界 |

### 12.2 加列

沿用启动时补列的机制：

| 表 | 新列 |
|---|---|
| 门 | `meeting_id`（可空，会议内确认点所属的会议）、确认点类型 `kind`、载荷 `payload_json`、决定 `decision_json` |
| 执行记录 | 缓存命中的 token 数 |
| 角色模板 | 元数据 |
| 运行 | 运行级配置 |

门的几个字段按实现约定如下（与字段名对照的设计稿写法见本表之后的说明）：

- `kind` 标识确认点。会议内确认点与兜底转人工的门取 `clarify`（K1）、`roster`（K2）、`consensus`（K3）、`escalation`（回流轮次用尽）；K4–K6 是模板里的人工门节点，门上 `kind` 为空、按人工门处理，确认点用键标识——节点配置的 `check` 或节点键，即 `proposal`、`review`、`requirement`——自动通过时把键写进 `kind`。旧门 `kind` 为空按人工门处理。
- `meeting_id` 区分同一节点上归档、重开前后的新旧门；人工门与兜底门为空。
- `payload_json` 存确认点的标题、描述和附加内容（如提议的名单、轮次与上限）。
- `decision_json` 存 `action`（`approve` / `reject`）、`feedback` 与 `data`（选项、回答、判定依据等）。判定者是门上的 `decided_by` 列，取值 `human`、`model:模型名`、`program`、`proxy` 或 `user-delegated`；模型判定的依据与保留的疑点在 `data` 的 `reasons` / `concerns` 里。

> 设计稿评审时曾按另一套名字写下这几个字段：K4–K6 写成 `proposal_confirm` / `review_verdict` / `requirement_confirm`，载荷写成 `meeting_id` / `checkpoint` / `round` / `summary`，决定写成 `choice` / `edits`、`decided_by` 取 `user|model` 并带 `model_id`。实现沿用的是模板与配置接口已经使用的确认点键和上表的字段名；本节按实现写成，含义一一对应。

### 12.3 工件

| 工件 | 变化 |
|---|---|
| 想法 | 首个版本是用户原文；会前准备追加一个版本，包含原文与简报 |
| 会议纪要 | `discussion`，结构见 §7.8；同目录另存账本的 JSON 文件 |
| 建设方案 | `proposal`，结构见 §7.8；复议和修订各出新版本 |
| 评审报告 | `review`，评审会议与确认会议都往这个工件写新版本 |
| 需求规格 | `requirement`，增加追踪矩阵与非需求类决策两张表 |

背景材料不是工件，是一组文本：

- 来源是新建运行时粘贴的文本，以及之后上传的文本文件。
- 存放在运行目录下的专用子目录里，有接口可以提交、列出、读取。
- 总量有硬上限，防止撑爆上下文；超出上限的拒绝提交。总量检查与自动编号在同一把进程内锁里完成，写文件先临时文件再原子替换；多 worker 部署时锁不跨进程，上限仍可被并发绕过（§15.3）。
- 会议运行时把背景材料拼进冻结区的会议章程，占用受预算约束；放不下的部分截断，并写明"仅提供了部分材料"。需求方代理被告知它只能依据被提供的部分作答。

### 14.2 真实模型验收

| # | 内容 |
|---|---|
| 1 | 用一个真实模型跑完整前半段，检查各产物的质量；记录收敛轮数、待定决策点数、评审发现数与被采纳的比例 |
| 2 | 同一想法分别用全量历史和拼装视图各跑一场，记录输入量、命中率与费用，数字回填到 §3.3 |

执行步骤（接好真实供应商后照做，结论与数字回填 §3.3）：

1. **准备**：用 `scripts/setup_real_model.py` 配好一个真实供应商。有余力时给 `judge` 角色绑定一个与参会者不同家族的模型；只有一个模型家族时，模型判定的确认点会标注"同家族，请复核"。

3. **记录**：每个运行从 `GET /api/runs/{id}/metrics` 取输入与输出的 token、缓存命中率、压缩次数、费用（按模型单价估算）、墙钟时间；从会议详情取讨论收敛的轮数、待定决策点数、评审发现数与被采纳数、确认会议发现的问题数。两次想法 A 的运行比较输入量、命中率与费用（H1）。
4. **核对主张并回填 §3.3**：H2，默认口径下讨论是否在轮次上限内收敛；H4，换新上下文的评审是否发现了真问题（记下发现数与被采纳的比例）；H3，先写预期再核对能不能检出偏差——拿想法 A 的需求规格改出三个已知偏差（去掉一条来源决策点、把一条结论写反、加一条没有来源的需求），从需求确认会议起跑，确认三类偏差都被列出。H5 已由自动化测试覆盖，在表里注明。

6. **记问题**：属于实现缺陷的修掉并补测试；属于设计本身的写进 §15。

## 15 已知风险与未决事项

### 15.1 风险

| 风险 | 应对 |
|---|---|
| 默认口径要求全体一致，可能经常到达轮次上限 | 停滞保护提前转人工；闭合规则可切换；待定的决策点带进方案，不会丢失 |
| 所有角色绑定同一个模型时，评审和核对受自我偏好影响 | 提示绑定不同家族的模型；先写要点再评；裁决由程序得出 |
| 结构化输出不稳定 | 解析失败有限重试；仍失败则该步失败重试，达到上限转人工 |
| 参会人数很大时提示词体积膨胀 | 按段降级；并发受供应商并发数约束 |
| 与并行开发分支的合并冲突 | 对共享文件的改动集中在 §6.8 列出的五处；压缩钩子单独成提交 |
| 文档节点 Mock 按提示词关键词路由，提示词一改路由就失效 | 会议调用改用 `【调用类型：xxx】` 标识路由；文档节点关键词与提示词放在同一处维护；端到端测试兜底 |
| 模板原地替换后，旧运行不能续跑 | 保留历史查看；切换前结束或归档旧运行，开发库可清空；不做迁移 |
| 真实模型验收尚未完成，参数默认值未经校准 | 用 Mock 保证流程正确性；真实供应商接入后按 §3.3 回填数字并校准（§15.2 第 1 条） |

### 15.3 实现现状与设计的差异

以下为实现已确认的行为，按"字段与路径以代码为准"记录；不影响对外接口的部分只注明去处。

| 事项 | 现状 | 影响 / 去处 |
|---|---|---|
| `GET /runs/{id}/review` | 仍只找 `Node.type == "REVIEW"`，新模板的评审节点是 `MEETING` | 对前半段运行返回不可用；改为读取 review 工件的最新版本之前，前端评审页对前半段不生效 |
| JSON 降级路径与工具循环的落盘 | JSON 降级没有压缩钩子；工具循环全文仍写旧的 `messages` 表，新会话日志只有摘要 | 会议把 `toolbox` 设为 `None`，不经过这两条路径（§10.4） |
| 用量与缓存命中的解析范围 | 只有 OpenAI 兼容的流式路径与 Anthropic 的回复解析真实值；Gemini 与 JSON 降级按估算 | 真实模型验收记录数字时注明口径（§10.7） |
| 上下文装配器的边界 | 每段下限 256 token；`truncate_to_tokens` 非硬上限；占用估算与适配器估算两套口径；空文本段已过滤 | §10.4；不影响正确性 |
| 会议压缩的摘要 | 按"会议 + 轮次"存进会议状态，前缀未变时复用；轮次切换或前缀变化时重算 | 并行发言与后续发言不再重复摘要（§10.4）；覆盖条数与前缀指纹对不上就作废，宁可重算也不漏掉迟到的发言 |
| 首条用户消息 | 工具循环第一次压缩时被并入摘要，摘要提示词不要求保留原始指令 | 压缩后智能体可能忘记任务；真实模型验收时留意（§15.2 第 5 条） |
| `conversations` 的并发安全 | 无唯一约束，靠连接池 size=1；`load_messages` 默认 `limit=500` 取最早一段 | 放宽连接池之前必须先处理（§10.4） |
| 背景材料的锁 | 总量检查与自动编号只在进程内有效 | 多 worker 之前改文件锁或数据库原子预留 |
| `seed_defaults` | 查不到再插入，无并发保护 | 两个进程同时启动会撞唯一约束；多 worker 之前处理 |
| `PATCH /runs/{id}/config` | 先应用节点参数、再写运行配置 | 第二次写库失败会留下"节点新、配置旧"；多进程或可观测之前处理 |
| `recover()` | 全局扫描 `created`/`running`/`waiting_human` | 多实例同时在线会重复拉起；按运行过滤或心跳防护 |
| 会议确认点的 attempt | 每次续开新建 attempt，失败重试按尝试总数计 | 指标把续开计成重试；长会议可能提前用尽重试预算 |
| 空发言行 | 被取消的模型调用留下 `content` 为空的发言行；`list_turns`/`count_turns` 计入 | 会议详情与指标会多一条空发言；不要直接改 store 语义（诊断与既有测试依赖） |
| 回流状态与编排器的顺序 | 协议在返回回流指令之前写 `rework_pending` | 中断窗口内会议按"已回流"加一轮而目标未重开（§6.4） |
| 回流目标的校验 | 不校验是否为直接依赖；轮次用尽的保底门不带确认点类型 | 顺序只由模板依赖保证；保底门批准按工件门处理（§6.4） |
| 纪要接口的 review 分支 | 确认会议还没写报告时按协议取 `review` 工件的最新版本 | 可能返回评审会议的纪要；按会议记录的报告版本可解 |
| 评审的重试复用 | 修订、验证、主席定夺按"步骤 + 轮次 + 意见处置状态/方案版本"复用已落盘的发言；修订稿与最新方案相同时不再写新版本 | 崩溃重试不再重复调用，也不会写出一版内容相同的方案；`review_defend` 与代理问答的第二次回应仍未逐条标记（下一行） |
| 评审的二次回应 | `review_defend` 与代理问答的第二次回应没有逐条落盘标记 | 崩溃重试可能重复发言 |
| 评审报告的累积 | strengths 跨轮累积；`reviewed_round` 只写不读 | 不影响正确性（§8.7） |
| 判定提示的截断 | 被审工件按模型可用窗口动态分配（至少 1000 token）；章程与背景材料按会议内最小参会者窗口的 50%/25% 放大，原固定值 8000/6000 作为下限 | 大窗口下规格、方案与背景材料能全文进入；截断仍会显式注明 |
| 异构默认 | `judge` 角色未显式绑定模型时优先选与全部参会者不同家族的模型，用户绑定过就照用；同家族时决定照常生效，但在决定、`checkpoint_decided` 事件与节点日志里标注 | §5.3；"不静默通过"落实为标注、提示与否决权，不是转人工 |
| 回流时的下游门 | 只重开目标节点，不作废依赖目标旧版本的下游门；评审退回讨论后方案确认点保持已通过 | 修订后的方案仍经评审裁决点（K5）过目；是否改为自动作废见 §15.2 |
| 评审报告的类型 | 评审报告与需求确认报告共用 `review` 工件，靠 front-matter 的 `review_type` 区分（`proposal` / `requirement`）；方案评审的结论取值为 `accept` / `conditional` / `return` | §8.7、§9.6；设计规格说明书里写的 `reject` 对应实现里的 `return` |
| 退役角色的迁移 | 启动时清理未改过的旧角色，不做迁移 | 升级前在飞的运行若仍引用旧角色，恢复后会致命失败（§11.3） |
| `run_recovered` 的发送条件 | 被取消后重新拉起的运行也发（`reset_nodes` 可能为 0），载荷带 `status` | 下游用它定位恢复；事件白名单与前端文案按此对齐 |
| 名单卡的编辑范围 | 支持增删角色与改人设；模型不在卡片上编辑；替换参会者不传 `model_id` | 会议按角色默认或第一个可用模型回落（§13.1） |
| 演示脚本的确认点映射 | `e2e_demo.py`、`drive_run.py` 与 `api/gates.py` 的 `_delegate_checkpoint` 各有一份 kind → 决定映射 | 新增确认点类型要改三处；后续抽共享映射 |

## 17 术语表

| 术语 | 含义 |
|---|---|
| 会议 | 一个会议节点的一次实例，有独立的状态、纪要和账本 |
| 协议 | 会议的步骤序列与提示词：讨论、评审、确认 |
| 主持人 | 讨论会议的组织者与方案执笔；不持内容立场 |
| 评审主席 | 评审会议和确认会议的组织者；不做裁决 |
| 参会者 | 讨论会议里持某一视角的角色 |
| 需求方代理 | 只回答事实问题、不提方案、不表态的受限角色 |
| 执笔者 | 建设方案的作者，即讨论会议的主持人 |
| 决策点 | 讨论要了结的一个问题；带编号、候选项、表态矩阵和结论 |
| 账本 | 全部决策点的集合，由程序落盘 |
| 表态 | 参会者对一个决策点的五级立场 |
| 交锋 | 围绕一个决策点的"主张 → 质疑 → 回应" |
| 轮 | 交锋轮次里的一次完整循环：逐个决策点交锋，然后全员重新表态 |
| 闭合规则 | 判定一个决策点是否了结的规则：全体一致、无反对即可、主持人裁决 |
| 停滞 | 连续若干轮无人改变任何未了结决策点上的表态 |
| 复议 | 讨论会议带着反馈续开，重开若干决策点 |
| 复审 | 评审会议在回流之后的下一轮，只看改动和处理结果 |
| 续开 | 保留已有纪要和账本继续 |
| 重开 | 旧会议归档，新建一场 |
| 确认点 | 需要由人或模型确认的位置；分会议内确认点和工件确认点 |
| 裁决模型 | 在模型判定模式下给确认点做判断的模型 |
| 自动化等级 | L1 全程人审、L2 关键点人审、L3 仅兜底 |
| 运行级配置 | 新建运行时填写的、覆盖模板默认值的配置 |
| 回流 | 把某个节点定点重开并带上反馈 |
| 插话 | 用户在会议进行中提交的发言 |
| 视图 | 某一次调用实际发给模型的内容，分冻结区、追加区、尾部 |
| 压缩 | 占用达到阈值时，把较旧的内容改写成摘要放进视图 |
