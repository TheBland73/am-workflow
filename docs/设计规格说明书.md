## 1 引言

### 1.1 目的与范围

本文件是 AM-Workflow 的实现级设计基线：网页端多智能体软件开发工作流平台——以 Agent 为节点，覆盖"想法 → 多体讨论 → 建设方案 → 多方评价 → 需求规格 → 设计规格 → 任务分解 → 编排执行 → 交付"全流程；人工介入是一等公民（默认人工审批门、可配置自动）；角色化记忆；节点可手动增删查改。

范围：本文覆盖总体架构、数据、模块、接口、关键流程与最小原型计划。算法与选型论证见调研报告，模型接入细节见配套文档。

### 1.2 读者

组长（主刀实现）、组员（分工实现）、老师（评审）。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 编排核 | TaskGraph Engine：解析流程定义、按依赖调度节点、管控制流/上下文/状态的程序（模型只是节点之一） |
| 工件（Artifact） | 各节点产出的 markdown 文件（需求/设计/任务…），节点间传引用不传全文 |
| 门禁（Gate） | 阻塞流程等待判定的人工审批点或自动检查点 |
| 回流 | 校验/评审失败后自动路由回产出该工件的节点重做（带反馈、有轮次上限） |
| Wave | 依赖图中同一批可并行执行的任务波次（同波并发、波间串行） |
| 角色模板 | Agent 的身份配置=系统提示词+工具权限+记忆作用域+默认模型+停止条件 |
| 记忆作用域 | 记忆条目的可见范围：session / agent（角色私有）/ project（项目黑板）/ global（平台规范） |

### 4.2 工件规范

**工件链**（每 run 一个目录 `runs/<run_id>/artifacts/`；格式约定来源：[spec-kit](https://github.com/github/spec-kit)、[Kiro specs](https://kiro.dev/docs/specs/)、[OpenSpec](https://github.com/Fission-AI/OpenSpec)，并与老师产品 task.md 内联元数据互证——本地课件与截图，见 §11）：

| # | kind | 文件 | 产出节点 | 格式要点 |
|---|---|---|---|---|
| 1 | idea | idea-brief.md | 需求启发师 | 目标/用户/约束/未决问题 |
| 2 | discussion | discussion.md | 主持人 | 共识 / **分歧（必须引用发言原文）** / 证据 / 未决项 |
| 3 | proposal | proposal.md | 方案架构师 | 方案+技术选型+证据+未决项 |
| 4 | review | review.md | 评审团（并行） | 统一 lens schema：对抗/边界/验证缺口…；**零发现也是合法结果**；修改清单逐条编号 |
| 5 | requirement | requirement.md | 需求分析师 | 用户故事 P1/P2/P3；**EARS**：`WHEN <触发> THE SYSTEM SHALL <行为>`；AC=Given/When/Then |
| 6 | design | design.md | 设计师 | 固定章节：架构/模块/数据/接口/错误处理/测试策略；引用需求编号 |
| 7 | task | task.md | 任务分解器 | 见下行格式 |
| 8 | test | test.md | 测试工程师 | AC→可执行测试映射 |
| 9 | changelog | changelog.md | 集成交付 | 变更记录+产物索引 |

> 注：W1 最小原型产 **7 类子集**（idea/discussion/proposal/requirement/design/task/changelog）；review/test 两类随 M1 的评审团与 QA 节点补齐。

**front-matter 规范**（所有工件）：

```yaml
---
id: req-v1            # 工件 id
kind: requirement
status: draft|reviewed|approved|superseded
version: 1
inputs: [proposal-v1, discussion-v1]   # 上游工件引用
created: 2026-11-14
---
```

**task.md 行格式**（与老师产品一致，编排器直接解析）：

```markdown
- [ ] 实现用户注册 API <!-- id: T2.1; deps: T1.2; design-section: 3.2; test-cases: TC-01,TC-02; assignee: dev(glm-4.7); wave: 2; status: pending -->
```

字段语义：`deps` 依赖任务 id 列表；`design-section` 关联 design.md 章节；`test-cases` 关联 test.md 用例；`assignee` 角色模板+模型；`wave` 并行波次；`status` pending/running/done/failed/blocked。**人工在画布/表格增删查改任务=直接编辑该结构化清单（API 校验 deps 无环）。**

### 4.3 事件协议（SSE，命名借鉴 [AG-UI](https://github.com/ag-ui-protocol/ag-ui) 风格的自定义事件集）

| type | 载荷要点 | 触发者 |
|---|---|---|
| run_created / run_finished / run_error | run 概要 | 编排核 |
| phase_entered | phase 名 | 编排核 |
| node_started / node_finished / node_failed | node_id, attempt_no, 摘要 | 编排核 |
| node_log | node_id, 级别, 文本 | Agent 运行时 |
| node_token | node_id, 增量文本 | 模型流式回调 |
| node_tool_call / node_tool_result | 工具名+入参摘要 / 结果摘要+耗时 | 工具层 |
| artifact_written | kind, path, version | ArtifactStore |
| task_created / task_updated | task_uid, 变更 | 分解器/人工编辑 |
| gate_requested / gate_decided | gate_id, node_id / 决定+反馈 | 编排核/人 |
| memory_written | scope, subject | MemoryService |

规则：`GET /runs/:id/events` 为 SSE 流，事件 id=events.seq；断线重连先 `GET /runs/:id` 快照对齐 store，再按 `Last-Event-ID` 补发。前端**只由事件驱动**节点状态动画，不做本地模拟。

> **与 AG-UI 的关系**：本事件集为自定义、仅借鉴其命名风格，**非 AG-UI 协议兼容，勿引入 AG-UI SDK 解析**。AG-UI 标准事件见 [AG-UI events](https://docs.ag-ui.com/concepts/events)（不含门禁/日志类事件）。
> - **直接对应**：run_created↔RunStarted、run_finished↔RunFinished、run_error↔RunError、node_started↔StepStarted、node_finished↔StepFinished、node_token↔TextMessageContent、node_tool_call↔ToolCallStart/Args、node_tool_result↔**ToolCallResult**（End 只是收尾帧，Result 才带结果载荷）。
> - **本产品扩展（无对应）**：phase_entered、node_log、gate_requested/gate_decided、artifact_written、task_created/task_updated、memory_written。
>
> 实现注：`node_token` **内存直推 SSE、不逐条落 events 表**（单连接+WAL 下高频 fsync 是真实吞吐瓶颈）；断线重连后节点文本以 messages/artifact 快照对齐——events 不含 token 只影响"重连后看不到半截流式文本"，前端以节点终态为准。

## 5 模块设计

### 5.1 编排核 TaskGraph Engine

**节点类型**（引擎层，与老师产品演示对齐；Task/Attempt 分离参考 [Orca 编排协议](https://onorca.dev/docs/cli/orchestration)，课件实证）：

| type | 语义 | 进入→退出 | 失败/异常 |
|---|---|---|---|
| PASS | 起/止 | — | — |
| AGENT | 运行一个角色模板 agent，产出工件 | 上游 done → 工件写入+回执 | attempt+1 重试≤max_attempts，超限转人工 |
| VERIFY | 程序/小模型校验（schema、规格一致性、字段齐全） | 上游 done → 通过/失败 | 失败即触发回流 |
| GATES | 自动门禁（lint/test/构建），**退出码判定** | 命令执行 → exit 0 | 失败回流 |
| HUMAN_GATE | 人工审批（默认开启） | 建 gate 记录→挂起 | 驳回=回流到指定节点 |
| DECISION | 条件分支，**条件由程序判定**（字段/退出码/状态） | — | 无匹配分支→转人工 |
| RESTORE | 回滚到 CHECKPOINT（回退受影响节点为 pending） | — | — |
| CHECKPOINT | 存档（快照 run 状态摘要） | — | — |
| TASKGRAPH | 嵌套子图（阶段分组；分解后的任务图即其实例） | — | — |

**状态机**：节点 `pending→ready(依赖满足)→running→waiting_human→done|failed|skipped`；run `created→running→waiting_human→finished|failed|stopped`。所有迁移写 events（append-only），**重启恢复=扫描 DB 状态续跑**，节点执行幂等（attempt 号+工件版本）。

**调度**：deps 拓扑排序→Waves；同波内 asyncio 并发（信号量限并发）；汇合=屏障（等最慢一支）；并行度由依赖图宽度决定。

**DB 并发（M0 开发期配置）**：SQLAlchemy 连接池 **size=1**（单连接天然串行写，等效自建单写队列且少一条代码路径）+ `connect_args={"check_same_thread": False}`（FastAPI 线程池跨线程借还连接，缺此必抛 ProgrammingError）+ `busy_timeout=5000` + WAL（`synchronous=NORMAL` 保留）；QueuePool `pool_timeout` 调大（默认 30s，多线程等单连接易偶发超时）。**三条红线**：① SSE 生成器**绝不持有 session**——`/runs/:id/events` 每 tick 短借还连接、查 `seq > last_seq` 后立即归还，否则单连接被长流占用、全场请求冻结；② `node_token` 不逐条落库（§4.3）；③ 迁 PostgreSQL 时恢复正常连接池。

**门禁**：HUMAN_GATE 不占执行线程（挂起，SSE 推 gate_requested）；审批动作三选一：`approve`（续跑）/ `reject+feedback`（回流到指定节点，其后受影响节点重置 pending，反馈写入事件与目标工件）/ `edit`（人直接改工件后 approve）。

**回流规则**（一等公民）：VERIFY/GATES/评审失败 → 按 `artifact.created_by_node` 定位负责人节点 → 自动重开（attempt+1，携带结构化反馈）→ 上限 3 次转人工。

**预算**：run 级 token 预算、节点 max_attempts、agent max_steps；超限停机转人工。

### 5.2 Agent 运行时与工具层

**角色模板 schema**（`agent_templates`）：role_key、system_prompt（角色+纪律+边界+"只负责 X"）、tools_json（允许工具白名单）、memory_scope、default_model_id、max_steps、stop_condition（产出工件 kind 列表）。

**上下文构建顺序**（每节点每 attempt）：
1. 系统提示 = 角色模板 + 全局纪律（工件只读引用、完成判据、禁止私传）
2. 记忆注入 = L3 规范（小，全文）+ L1 该角色经验卡摘要（≤10 条 active）+ L2 相关工件（**引用+摘要**，按需读全文）
3. 任务五要素：目标 / 输出格式（工件 kind+schema）/ 工具指引 / 边界 / 停止条件（[Anthropic Building effective agents](https://www.anthropic.com/research/building-effective-agents) + 课件交接五要素）
4. 上游工件正文（需要时工具读取，不整段塞提示）

**工具循环**（伪代码）：

```python
while steps < max_steps:
    msg = adapter.chat(context, tools=allowed_tools)     # 流式
    if msg.tool_calls:
        for tc in msg.tool_calls:
            result = execute_tool(tc)                     # 权限白名单+隔离+超时+截断
            context.append(tool_result(tc.id, result))
        steps += 1
    else:
        artifact = parse_output(msg, stop_condition)      # 结构化产物校验
        submit(artifact); return receipt(node_id, attempt_id)
```

**工具清单**：

| 工具 | 来源 | 说明 |
|---|---|---|
| read_file / write_file / list_dir | 自研（薄） | 限定 workspace 内；write 落盘即写 events |
| run_command | 自研（薄） | cwd=任务 workspace；超时；输出截断；**退出码即证据** |
| submit_artifact | 自研 | 结构化产物提交+校验+版本化 |
| web_search | **可配置 provider** | duckduckgo（免 key，默认）/ tavily / brave / 供应商内置搜索；结果带 URL 引用落盘（搜索能力主要来自 API 方，harness 只做暴露与结果格式化） |
| 生态工具 | **MCP 接入** | 官方 `mcp` python-sdk 做 client，接 filesystem/git/fetch 等现成 server；工具统一注册为 name/description/inputSchema |

工具接口设计遵循 SWE-agent（[arXiv 2405.15793](https://arxiv.org/abs/2405.15793)）的 ACI 结论：工具描述写清、错误信息可读、输出截断可控。

**执行隔离**：每任务 workspace=`runs/<run_id>/workspace/<task_uid>/`；M0/M1 用子进程+目录隔离+超时，M2 评估 docker 沙箱。

**澄清强制门**：PM/讨论节点输出中含 `questions[]` 时，自动转为 HUMAN_GATE 内容（对应 MAST "不主动澄清"失败模式）。

### 5.3 记忆系统 MemoryService

四层作用域、schema、检索、门禁见调研报告 §6.4；机制来源：[Mem0](https://github.com/mem0ai/mem0)（ADD-only+作用域）、[Hindsight](https://github.com/vectorize-io/hindsight)（判决模型+observations）、[Letta 共享块](https://docs.letta.com/v1-sdk/memory/shared-memory)（权限结论）、[Graphiti 命名空间](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)、[LangMem](https://langchain-ai.github.io/langmem/)（hot/background）、[BMAD sanctum](https://github.com/bmad-code-org/BMAD-METHOD)（记忆文件夹约定）。实现要点：

## 6 关键流程

### 6.1 端到端主流程（SDLC 模板，默认自动化等级 L2）

| 步 | 节点 | 输入 | 输出工件 | 人工介入（默认） |
|---|---|---|---|---|
| 1 | 需求启发师 | 用户一句话想法 | idea-brief（含 questions[]） | ★澄清对话（questions 转门禁） |
| 2 | 多体讨论（主持人+3 立场×1–2 轮，轮次依据 [Du et al. 2305.14325](https://arxiv.org/abs/2305.14325)、[ChatEval 2308.07201](https://arxiv.org/abs/2308.07201)） | idea-brief | discussion（共识/分歧/证据） | 可旁听/插话 |
| 3 | 方案架构师 | discussion | proposal | — |
| 4 | ★方案确认门 | — | — | 采纳 / 驳回 / 编辑 |
| 5 | 评审团（3 lens 并行，[Agent-as-a-Judge](https://arxiv.org/abs/2410.10934) 式过程性反馈） | proposal | review（逐条修改清单） | ★评审裁决门 |
| 6 | 需求分析师 | proposal+review | requirement（EARS+AC） | ★需求审查门 |
| 7 | 设计师 | requirement | design（固定章节） | ★设计审查门（可配置"产出后自动放行"） |
| 8 | 任务分解器 | design | task.md（DAG+assignee） | ★任务图人工编辑（增删查改） |
| 9 | 编排执行（Waves） | task.md | 代码+测试+运行证据 | 抽查门（可选） |
| 10 | VERIFY/GATES | 产物 | 校验/测试结果 | 失败自动回流 |
| 11 | ★验收门 | 全部产物 | — | 通过/驳回 |
| 12 | 集成交付 | — | changelog+工件归档+记忆沉淀 | — |

不变量：**Agent 可以提议变更，不能批准自己的补丁**；讨论/评审最多 N 轮，不收敛交人。

### 6.2 人工门时序

```
编排核 → 建 gate(open) → 事件 gate_requested → SSE → 前端节点变琥珀+卡片
人：approve → gate(approved) → 编排核续跑
人：reject+feedback+target_node → gate(rejected) → 目标节点 attempt+1 重开（携带反馈）→ 其后受影响节点重置 pending
人：edit → 直接 PATCH 工件 → approve
```

### 6.3 返工回流时序

```
VERIFY/GATES 失败 → 事件 node_failed(原因=结构化反馈) → 按 artifact.created_by_node 定位负责人
→ 自动重开该节点（attempt+1, 上下文附反馈） → ≤3 次 → 超限转 HUMAN_GATE
```

### 6.4 断点恢复时序（两级）

- **挂起态恢复（W1 必做，约 2-3 小时）**：杀在 waiting_human（人工门挂起）→ 重启 → 重启扫描不动 gate（原样保留）→ ready 节点重排队 → 通过续跑 → SSE 快照对齐。门本来就是 DB 态，几乎是 D2 恢复骨架的免费副产品。
- **运行态恢复（加分）**：并行执行中杀 → running 节点未回执 attempt 作废重跑（需处理流式中断与部分写回，这是那 1 天的工作量）。
- 共同基础：全部状态在 DB+事件表，节点执行幂等（attempt 号+工件版本）。

## 8 安全与边界

- **命令执行**：workspace 目录隔离+超时+输出截断；M2 评估 docker；禁止 run_command 逃逸出 run 目录（路径校验）。
- **密钥**：api_key 加密存储（Fernet+本机密钥文件）、响应脱敏、日志/工件/trace 中强制脱敏。
- **注入防护**：记忆与搜索结果只作背景信息，不进系统指令位；工件中"忽略之前指令"类文本不提权。
- **成本**：run 预算+节点上限+分级用模（小模型抽取/判决、强模型评审）；node_attempts 记账。
