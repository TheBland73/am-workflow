## 1 引言

### 1.1 目的与范围

本文件是 AM-Workflow 的实现级设计基线：网页端多智能体软件开发工作流平台——以 Agent 为节点，覆盖"想法 → 多体讨论 → 建设方案 → 多方评价 → 需求规格 → 设计规格 → 任务分解 → 编排执行（评审与测试穿插其中）→ 验收 → 部署交付"全流程；人工介入是一等公民（默认人工审批门、可配置自动）；角色化记忆；节点可手动增删查改。想法到需求确认这一段的流程、会议运行时、确认点机制与会话上下文模块，详细设计在[会议式流程设计](./想法到需求确认-会议式流程设计.md)。

范围：本文覆盖总体架构、数据、模块、接口、关键流程与分期计划。算法与选型论证见调研报告（含 §11 增补），模型接入细节与评审/测试体系细节见配套文档。**分布式执行（多 PC 协作）仅设计封存，暂不实现**（见[分布式执行模式设计](./分布式执行模式设计.md)）。

### 1.2 读者

组长（主刀实现）、组员（分工实现）、指导教师（评审）。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| 编排核 | TaskGraph Engine：解析流程定义、按依赖调度节点、管控制流/上下文/状态的程序（模型只是节点之一） |
| 工件（Artifact） | 各节点产出的 markdown 文件（需求/设计/任务…），节点间传引用不传全文 |
| 门禁（Gate） | 阻塞流程等待判定的人工审批点或自动检查点 |
| 回流 | 校验/评审失败后自动路由回产出该工件的节点重做（带反馈、有轮次上限） |
| Wave | 依赖图中同一批可并行执行的任务波次（同波并发、波间串行） |
| 角色模板 | Agent 的身份配置=系统提示词+工具权限+记忆作用域+默认模型+停止条件 |
| 记忆作用域 | 记忆条目的可见范围：session / agent（角色私有）/ project（项目黑板）/ global（平台规范） |
| 质量钩子 | 挂在任务/波次上的评审与测试插桩（`review` 等级、`verify` 范围），分解器提议、程序固化、人可改 |
| 三级评审 | 桌检 desk-check（单评审员快审）→ 波次走查 walkthrough（每波后 2 lens 并行+记录员聚合）→ 正式评审 FTR（会议式，主席+评审员×N+记录员） |
| lens | 评审视角分工（正确性/安全/性能/规范…），差异化上下文与模型，视为独立证据 |
| FTR | Formal Technical Review，正式评审会议（3~5 参与者、checklist 驱动、限轮限争论，方法论出自 SEPA《软件工程：实践者的研究方法》第 15 章） |
| QA | 独立测试角色：产测试计划（test.md）、执行集成/系统/回归测试、报告缺陷；与 dev 分离 |
| 缺陷闭环 | bug 报告→triage 定级→修复→代码评审→回归→关闭的状态机，由编排核驱动 |
| 部署交付 | 验收通过后的可选节点：产出 deployment.md（部署步骤/回滚）+ 打包产物 + 证据回传 |
| 会议、决策点账本、确认点、裁决模型、续开与重开 | 前半段术语，定义见[会议式流程设计 §17](./想法到需求确认-会议式流程设计.md)，此处不复制 |

## 2 设计基线（已确认决策）

| 决策点 | 结论 | 备注 |
|---|---|---|
| 产品定位 | **通用可定制工作流引擎 + 预置"SE 全流程"模板** | 引擎管机制，模板管流程；满足"可定制"要求 |
| 编排 | **自研轻量编排核**（任务账本+事件溯源+门禁挂起），LangGraph 仅作概念对照（[interrupts/checkpointer 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)） | 理由见调研 §6.2 |
| 记忆 | **自研 MemoryService**（四层作用域+五步写入）；引擎自研最简起步，**[Hindsight](https://github.com/vectorize-io/hindsight) 作为可插拔升级**（M2 评估） | 无框架内建按角色写权限，产品层必须自研（论据见调研 §4.3） |
| 工件 | [spec-kit](https://github.com/github/spec-kit)/[Kiro specs](https://kiro.dev/docs/specs/) 式 markdown 工件链 + YAML front-matter；需求用 EARS 句式 | 与参考产品 task.md 元数据互证 |
| 前端 | Vite + React 18 + TS + [@xyflow/react v12](https://github.com/xyflow/xyflow) + Ant Design 5 + [zustand](https://github.com/pmndrs/zustand) + [TanStack Query](https://tanstack.com/query/latest) | n8n/Dify/Langflow 同栈 |
| 实时 | SSE 事件流（对齐 [AG-UI](https://github.com/ag-ui-protocol/ag-ui) 事件命名）+ REST 动作 | WebSocket 仅协同编辑时再上 |
| 模型层 | **全量用户可配置**：供应商/base_url/api_key/接口协议/上下文窗口/能力标记；无本地模型假设 | 详见配套文档 |
| 工具层 | 自研薄核心工具（6 个）+ MCP 生态接入（[官方 python-sdk](https://github.com/modelcontextprotocol/python-sdk)）+ 可配置搜索 | 详见 §5.2 |
| 排期 | **6 周**：W1 最小原型（11-17 验收 ✅）→ W2–W4 M1 核心闭环 → W5–W6 M2 + 优化评估 | 全组 agent 辅助开发，产能按上限估 |
| 质量体系 | **三级评审 + 四级测试 + 缺陷闭环**，通过质量钩子穿插进执行依赖图（非末端单点）；模板 Run 与 Plan Run 共用同一套机制 | 方法论基线：SEPA 评审技术、微软 PCM 测试实践；详设见 [评审与测试体系设计](./评审与测试体系设计.md) |
| 部署交付 | 验收门后增加可选 DEPLOY 节点：deployment.md + 打包产物 + 证据回传 | 2026-11-22 确认纳入；默认不执行真实部署命令，仅产出部署物 |
| 前半段流程 | **会议式流程**：讨论会议（全员知悉，默认全体一致）→ 方案确认 → 评审会议 → 需求规格 → 需求确认；由会议节点类型承载；每个确认点可选人工或模型判定；会话与上下文做成通用模块 | 设计与取舍见[会议式流程设计](./想法到需求确认-会议式流程设计.md)；已实现，真实模型验收待补 |
| 分布式执行 | **仅设计封存**：单机单进程是当前唯一实现形态；多 PC 协作（中心化多 worker / 纯 git 模式）的完整设计见专项文档，解封另行评估 | 2026-11-22 决策：分布式设想只留档，不强求实现 |
| 许可 | 仅课程作业内部使用，第三方许可（含 Commons Clause）基本不约束；仍以"借鉴设计+自研核心+生态集成"为主 | 出于学术诚信与答辩"可讲性"，不整段复制第三方代码 |

## 3 总体设计

### 3.1 架构分层

```
前端 (Vite + React18 + TS)                      后端 (Python FastAPI, 单体)
┌────────────────────────────┐    SSE 事件流   ┌──────────────────────────────────┐
│ 画布 @xyflow/react（M1 只读）│◄──────────────│ ① 编排核 TaskGraph Engine          │
│ 阶段管道视图 / 执行看板(M2)   │                │    任务账本·Waves·门禁挂起·回流      │
│ 日志/对话抽屉 · 审批卡片      │───────────────►│ ② Agent 运行时（角色模板×工具循环）  │
│ Providers 配置页 · 记忆面板(M2)│   REST 动作    │ ③ MemoryService（四层作用域）       │
└────────────────────────────┘                │ ④ Models Pool（协议适配层）         │
                                              │ ⑤ ArtifactStore（工件链, markdown） │
                                              │ ⑥ 工具层（自研核心 6 + MCP client）  │
                                              └──────────────────────────────────┘
存储：SQLite（M0/M1）→ PostgreSQL（部署）；runs/<run_id>/{artifacts, workspace, logs} 为文件区
```

## 4 数据设计

### 4.1 核心表（SQLite 起步，字段为最小集）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `provider_configs` | id, name, **protocol**(openai_chat/anthropic_messages/gemini_generate/custom), base_url, api_key_enc, extra_headers, timeout_s, max_concurrency, enabled | 供应商连接，详见配套文档 |
| `model_entries` | id, provider_id, model_name, display_name, **context_window**, max_output_tokens, cap_tools, cap_vision, cap_json, price_in, price_out, enabled | 模型条目 |
| `agent_templates` | id, role_key, name, system_prompt, tools_json, memory_scope, default_model_id, max_steps, stop_condition, **meta_json**（一句话简介、专长标签、适合的会议角色） | 角色模板（Agent Factory 的单元） |
| `workflows` | id, name, template_key, definition_json | 流程定义：nodes[] + edges[]（声明式） |
| `runs` | id, workflow_id, status, current_phase, idea_text, created_at, budget_tokens, **config_json**（运行级配置） | 一次执行实例 |
| `nodes` | id, run_id, node_key, **type**, name, phase, status, assignee_json(role_key, model_id), deps_json, max_attempts, **config_json**（节点级会议协议/名单/参数） | 节点=账本行 |
| `node_attempts` | id, node_id, attempt_no, model_id, status, started_at, finished_at, tokens_in, tokens_out | Task/Attempt 分离：旧尝试迟到回执不误完成 |
| `tasks` | id, run_id, task_uid, title, deps_json, design_section, test_cases_json, assignee_json, wave, status, **review_level**(off/desk/walk/ftr，可空=默认推断), **verify_cmd**(可空) | 任务分解产物即账本；人工可 CRUD；质量钩子元数据由分解器提议、程序固化、人工可改 |
| `events` | id, run_id, seq, ts, **type**, node_id, payload_json | **append-only**；seq 即 SSE Last-Event-ID |
| `artifacts` | id, run_id, kind, path, version, created_by_node, status(active/superseded) | 元数据；正文在文件区 |
| `gates` | id, run_id, node_id, **meeting_id**（可空）, status(open/approved/rejected), feedback, decided_by, decided_at, **kind / payload_json / decision_json**（确认点类型、载荷、决定） | 确认点记录；会议内的确认点挂在会议节点上，`meeting_id` 区分归档/重开后的新旧门 |
| `defects` | id, run_id, task_uid, bug_uid, severity(1/2/3), status(open/assigned/fixed/retested/closed/reopened), symptom, fault_hypo, root_cause, steps_json, expected, actual, report_node_id, fix_node_id, opened_at, closed_at | 缺陷账本（bug 状态机由编排核驱动）；同时聚合产出 `bugs` 工件（md+sidecar JSON）供人读 |
| `messages` | id, node_id, attempt_id, role, content_json | Agent 对话 trace（可观测） |
| 会议与上下文相关表 | meetings、meeting_participants、meeting_turns、decision_points、meeting_interventions、conversations、conversation_messages | 内容见[会议式流程设计 §12](./想法到需求确认-会议式流程设计.md) |
| `memories` | id, **scope_type**(session/agent/project/global), scope_id, kind(semantic/episodic/procedural), subject, content, source_event, status(active/superseded), valid_from, valid_until, evidence_json, created_by | 记忆条目；正文资产另存 markdown |

### 4.2 工件规范

**工件链**（每 run 一个目录 `runs/<run_id>/artifacts/`；格式约定来源：[spec-kit](https://github.com/github/spec-kit)、[Kiro specs](https://kiro.dev/docs/specs/)、[OpenSpec](https://github.com/Fission-AI/OpenSpec)，并与参考产品 task.md 内联元数据互证）：

| # | kind | 文件 | 产出节点 | 格式要点 |
|---|---|---|---|---|
| 1 | idea | idea-brief.md | 用户（原文）、讨论会议的会前准备（简报） | 首个版本是用户原文；其后追加一个版本：原文 + 简报（目标/用户/约束/假设/待澄清） |
| 2 | discussion | discussion.md | 讨论会议（程序落盘） | 会议纪要：会议信息、**决策点账本**、表态矩阵、立场摘要、交锋摘要、未决议题；同目录另存账本 JSON |
| 3 | proposal | proposal.md | 讨论会议的主持人（整合执笔） | 逐决策点写结论与依据；待确认问题；决策点索引 |
| 4 | review | review.md | 评审会议与需求确认会议（前半段）；评审团、FTR 会议（代码侧） | 统一外壳：front-matter 里的 `review_type`（proposal/requirement/code）；`verdict` 按类型取值（proposal: accept/conditional/return；requirement: pass/fail；code: pass/block）；`issues[]`（severity/位置/message/suggestion/处置状态；代码侧另有 task/file/verify_hint）+ checklist 结果；**零发现也是合法结果**；修改清单逐条编号。三类报告是同一工件的不同 `review_type`，不共用 verdict 枚举。前半段的两种已实现；`code` 与其 verdict 随代码侧评审后续落地 |
| 5 | requirement | requirement.md | 需求分析师 | 用户故事 P1/P2/P3；**EARS**：`WHEN <触发> THE SYSTEM SHALL <行为>`；AC=Given/When/Then |
| 6 | design | design.md | 设计师 | 固定章节：架构/模块/数据/接口/错误处理/测试策略；引用需求编号 |
| 7 | task | task.md | 任务分解器 | 见下行格式 |
| 8 | test | test.md | QA（测试计划前置，与开发并行） | TC 行内联元数据：`maps`(关联 AC/需求) / `type`(unit/integration/system/acceptance) / `status`；AC→TC 全覆盖 |
| 9 | bugs | bugs.md（+ sidecar bugs.json） | QA（缺陷闭环） | bug 条目：symptom/fault 假设/root cause 假设/severity/steps/expected/actual/关联 TC；状态机见缺陷闭环 |
| 10 | changelog | changelog.md | 集成交付 | 变更记录+产物索引+缺陷统计 |
| 11 | deployment | deployment.md | 部署交付 | 部署步骤/环境要求/回滚说明/打包产物清单；证据（命令退出码）回传 changelog |

> 注：W1 已产出 8 类（idea/discussion/proposal/requirement/design/task/review/changelog）；`test`/`bugs` 随 M1 的 QA 角色补齐，`deployment` 在 M2。

**front-matter 规范**（所有工件）：

```yaml
---
id: req-v1            # 工件 id
kind: requirement
status: draft|reviewed|approved|superseded
version: 1
inputs: [proposal-v1, discussion-v1]   # 上游工件引用
created: 2026-11-14
---
```

**task.md 行格式**（与参考产品一致，编排器直接解析）：

```markdown
- [ ] 实现用户注册 API <!-- id: T2.1; deps: T1.2; design-section: 3.2; test-cases: TC-01,TC-02; assignee: dev(glm-4.7); wave: 2; status: pending; review: desk; verify: -->
```

字段语义：`deps` 依赖任务 id 列表；`design-section` 关联 design.md 章节；`test-cases` 关联 test.md 用例；`assignee` 角色模板+模型；`wave` 并行波次；`status` pending/running/done/failed/blocked；**`review` 质量钩子等级**（off/desk/walk/ftr，缺省=程序按任务规模与波次位置推断）；`verify` 任务级验证命令覆盖（缺省=继承波次/全局 verify）。**人工在画布/表格增删查改任务=直接编辑该结构化清单（API 校验 deps 无环）。**

**test.md 行格式**（QA 产出，与 task.md 同构）：

```markdown
- [ ] 注册接口边界值校验 <!-- id: TC-05; maps: R2/AC-2.3; type: unit; status: pending -->
```

字段语义：`maps` 关联需求编号/AC；`type` unit/integration/system/acceptance；`status` pending/passed/failed/blocked。AC→TC 必须全覆盖（分解器与 QA 联合校验）。

规则：`GET /runs/:id/events` 为 SSE 流，事件 id=events.seq；断线重连先 `GET /runs/:id` 快照对齐 store，再按 `Last-Event-ID` 补发。前端**只由事件驱动**节点状态动画，不做本地模拟。

> **与 AG-UI 的关系**：本事件集为自定义、仅借鉴其命名风格，**非 AG-UI 协议兼容，勿引入 AG-UI SDK 解析**。AG-UI 标准事件见 [AG-UI events](https://docs.ag-ui.com/concepts/events)（不含门禁/日志类事件）。

> - **本产品扩展（无对应）**：phase_entered、node_log、gate_requested/gate_decided、artifact_written、task_created/task_updated、memory_written。
>
> 实现注：`node_token` **内存直推 SSE、不逐条落 events 表**（单连接+WAL 下高频 fsync 是真实吞吐瓶颈）；断线重连后节点文本以 messages/artifact 快照对齐——events 不含 token 只影响"重连后看不到半截流式文本"，前端以节点终态为准。

## 5 模块设计

### 5.1 编排核 TaskGraph Engine

**节点类型**（引擎层，与参考产品 ASF 演示对齐；Task/Attempt 分离参考 [Orca 编排协议](https://onorca.dev/docs/cli/orchestration)）：

| type | 语义 | 进入→退出 | 失败/异常 |
|---|---|---|---|
| PASS | 起/止 | — | — |
| AGENT | 运行一个角色模板 agent，产出工件 | 上游 done → 工件写入+回执 | attempt+1 重试≤max_attempts，超限转人工 |
| VERIFY | 程序/小模型校验（schema、规格一致性、字段齐全） | 上游 done → 通过/失败 | 失败即触发回流 |
| GATES | 自动门禁（lint/test/构建），**退出码判定** | 命令执行 → exit 0 | 失败回流 |
| MEETING | 会议：一个节点内运行一套多角色协议（讨论 / 评审 / 确认），内部是可持久化、可挂起续开的状态机 | 上游 done → 逐步执行，遇人工确认点挂起 → 工件写入 + 回执 | 步骤失败按 attempt 重试；回流轮次超限转人工 |
| REVIEW | 单 lens 评审节点：一个评审员按指定 lens 读上游工件并产出 review 工件；desk/walk 的单 lens 特例复用此类型 | 上游 done → review 工件 + verdict | 阻塞项定向回流；轮次超限转人工 |
| REVIEW_MEETING | FTR 正式评审会议：主席就绪检查 → lens×N 并行独立审（拿独立证据）→ 记录员聚合定级 → 统一 review 工件；blocker/major 定向回流 | 上游 done → review 工件 + verdict | 阻塞回流目标节点（≤N 轮→升级人工门） |
| HUMAN_GATE | 确认点：人工审批（默认开启），可配置为由裁决模型判定 | 建 gate 记录→挂起；或调用裁决模型 | 驳回=回流到指定节点；模型判定无效转人工 |
| DECISION | 条件分支，**条件由程序判定**（字段/退出码/状态） | — | 无匹配分支→转人工 |
| RESTORE | 回滚到 CHECKPOINT（回退受影响节点为 pending） | — | — |
| CHECKPOINT | 存档（快照 run 状态摘要） | — | — |
| DEPLOY | 部署交付（AGENT 变体，qa/dev 角色可执行）：产出 deployment.md+打包产物，可选执行部署命令并回传退出码证据 | 上游 done → deployment 工件 + 证据 | 命令失败→回流或转人工 |
| TASKGRAPH | 嵌套子图（阶段分组；分解后的任务图即其实例） | — | — |

> `REVIEW_MEETING` 是评审体系后续迭代的设计，本期不实现；前半段只新增 `MEETING`，代码侧正式评审会议是否迁移见[会议式流程设计 §15.2](./想法到需求确认-会议式流程设计.md)。

**状态机**：节点 `pending→ready(依赖满足)→running→waiting_human→done|failed|skipped`；run `created→running→waiting_human→finished|failed|stopped`。所有迁移写 events（append-only），**重启恢复=扫描 DB 状态续跑**，节点执行幂等（attempt 号+工件版本）。

**调度**：deps 拓扑排序→Waves（仅用于画布分列与并行度估算）；执行采用**依赖就绪即跑、单节点完成即触发下一轮调度**的事件驱动解锁——**v0.2 勘误**：W1 实现的 `gather(min-wave batch)` 存在隐式批内屏障（README §4.1 此前表述有误），下游节点必须等同批最慢者结束才进 ready；评审/测试钩子要穿插进依赖图，必须拆除该屏障改为完成即解锁（[评审与测试体系设计](./评审与测试体系设计.md) §7）。并行度由进程级信号量（`AM_NODE_CONCURRENCY`）控制。

**DB 并发（M0 开发期配置）**：SQLAlchemy 连接池 **size=1**（单连接天然串行写，等效自建单写队列且少一条代码路径）+ `connect_args={"check_same_thread": False}`（FastAPI 线程池跨线程借还连接，缺此必抛 ProgrammingError）+ `busy_timeout=5000` + WAL（`synchronous=NORMAL` 保留）；QueuePool `pool_timeout` 调大（默认 30s，多线程等单连接易偶发超时）。**三条红线**：① SSE 生成器**绝不持有 session**——`/runs/:id/events` 每 tick 短借还连接、查 `seq > last_seq` 后立即归还，否则单连接被长流占用、全场请求冻结；② `node_token` 不逐条落库（§4.3）；③ 迁 PostgreSQL 时恢复正常连接池。

**门禁**：HUMAN_GATE 不占执行线程（挂起，SSE 推 gate_requested）；审批动作三选一：`approve`（续跑）/ `reject+feedback`（回流到指定节点，其后受影响节点重置 pending，反馈写入事件与目标工件）/ `edit`（人直接改工件后 approve）。确认点配置为模型判定时，由裁决模型给出结论，规则见[会议式流程设计 §5.3](./想法到需求确认-会议式流程设计.md)；会议内的确认点挂在会议节点上，复用同一套门记录与审批接口；它的驳回只把决定写进 `decision_json`，不要求 `target_node`，也不重置下游（规则见[会议式流程设计 §6.3](./想法到需求确认-会议式流程设计.md)）。旧 gate 的 `kind` 为空时按人工确认点处理；新确认点写入 `kind` / `payload_json` / `decision_json`。

**回流规则**（一等公民）：VERIFY/GATES/评审失败 → 按 `artifact.created_by_node` 定位负责人节点 → 自动重开（attempt+1，携带结构化反馈）→ 上限 3 次转人工。另有一条**定点回流**：节点的执行结果携带回流指令时，编排器把指定的节点定点重开并带上反馈，不级联重置下游，当前节点轮次加一，超限转人工。讨论、评审、确认之间的循环靠它承载，见[会议式流程设计 §6.4](./想法到需求确认-会议式流程设计.md)。

**预算**：run 级 token 预算、节点 max_attempts、agent max_steps；超限停机转人工。

### 5.2 Agent 运行时与工具层

**角色模板 schema**（`agent_templates`）：role_key、system_prompt（角色+纪律+边界+"只负责 X"）、tools_json（允许工具白名单）、memory_scope、default_model_id、max_steps、stop_condition（产出工件 kind 列表）、meta_json（一句话简介、专长标签、适合的会议角色）。

**v0.2 新增角色**：`qa`（独立测试：写测试计划与可执行测试、执行集成/回归、报告缺陷；工具=read/write/run_command；纪律=不改实现）、`review_leader`（FTR 主席：就绪检查、分发 checklist、组织轮次；裁决聚合）、`recorder`（FTR 专用，可由 facilitator 兼任：聚合 lens 发现、去重定级、产出统一 review 工件；不参加前半段会议运行时）、`judge`（只在确认点的模型判定模式中使用；先写判断要点再读工件，输出无效转人工，不参加讨论/评审会议）。lens 评审员复用 `review` 角色模板按 lens 变体化（差异化上下文与模型，同质评审意见不视为独立证据）。完整角色清单与职责见[评审与测试体系设计](./评审与测试体系设计.md) §3/§4。前半段的角色（主持人、评审主席、参会角色、需求方代理）与名单规则见[会议式流程设计 §11](./想法到需求确认-会议式流程设计.md)。

**上下文构建顺序**（每节点每 attempt）：
1. 系统提示 = 角色模板 + 全局纪律（工件只读引用、完成判据、禁止私传）
2. 记忆注入 = L3 规范（小，全文）+ L1 该角色经验卡摘要（≤10 条 active）+ L2 相关工件（**引用+摘要**，按需读全文）
3. 任务五要素：目标 / 输出格式（工件 kind+schema）/ 工具指引 / 边界 / 停止条件（[Anthropic Building effective agents](https://www.anthropic.com/research/building-effective-agents)）
4. 上游工件正文（需要时工具读取，不整段塞提示）
5. 多角色会议与工具循环的上下文装配、阈值压缩与前缀缓存规则，由会话与上下文模块统一处理，见[会议式流程设计 §10](./想法到需求确认-会议式流程设计.md)

**工具循环**（伪代码）：

```python
while steps < max_steps:
    msg = adapter.chat(context, tools=allowed_tools)     # 流式
    if msg.tool_calls:
        for tc in msg.tool_calls:
            result = execute_tool(tc)                     # 权限白名单+隔离+超时+截断
            context.append(tool_result(tc.id, result))
        steps += 1
    else:
        artifact = parse_output(msg, stop_condition)      # 结构化产物校验
        submit(artifact); return receipt(node_id, attempt_id)
```

**工具清单**：

| 工具 | 来源 | 说明 |
|---|---|---|
| read_file / write_file / list_dir | 自研（薄） | 限定 workspace 内；write 落盘即写 events |
| run_command | 自研（薄） | cwd=任务 workspace；超时；输出截断；**退出码即证据** |
| submit_artifact | 自研 | 结构化产物提交+校验+版本化 |
| web_search | **可配置 provider** | duckduckgo（免 key，默认）/ tavily / brave / 供应商内置搜索；结果带 URL 引用落盘（搜索能力主要来自 API 方，harness 只做暴露与结果格式化） |
| 生态工具 | **MCP 接入** | 官方 `mcp` python-sdk 做 client，接 filesystem/git/fetch 等现成 server；工具统一注册为 name/description/inputSchema |

工具接口设计遵循 SWE-agent（[arXiv 2405.15793](https://arxiv.org/abs/2405.15793)）的 ACI 结论：工具描述写清、错误信息可读、输出截断可控。

**执行隔离**：每任务 workspace=`runs/<run_id>/workspace/<task_uid>/`；M0/M1 用子进程+目录隔离+超时，M2 评估 docker 沙箱。

**澄清强制门**：PM/讨论节点输出中含 `questions[]` 时，自动转为 HUMAN_GATE 内容（对应 MAST "不主动澄清"失败模式）。讨论会议的澄清确认点（由需求方代理或用户回答）见[会议式流程设计 §7.2](./想法到需求确认-会议式流程设计.md)。

### 5.3 记忆系统 MemoryService

| 引擎 | 自研最简（零新依赖） | 同左 | 可切换 Hindsight（接口已预留） |

## 6 关键流程

### 6.1 端到端主流程（SDLC 模板，默认自动化等级 L2）

| 步 | 节点 | 输入 | 输出工件 | 人工介入（默认） |
|---|---|---|---|---|
| 1 | 想法录入，以及讨论会议的会前准备（就绪检查、澄清、名单） | 用户一句话想法 + 背景材料 | idea（原文 + 简报） | ★澄清确认点、★名单确认点（均可配置由人或模型判定） |
| 2 | 讨论会议：独立立场 → 议题提炼 → 全员表态 → 交锋轮次 → 整合成稿 → 全员复核 | idea + 背景材料 | discussion（纪要 + 决策点账本）、proposal（草稿） | ★轮次共识确认点（停滞或到轮次上限时；可配置每轮暂停） |
| 3 | ★方案确认点 | proposal | — | 送评审（默认）/ 直接通过 / 驳回；模型模式下直接送评审 |
| 4 | 评审会议：独立评审 → 汇总分级 → 作者回应 → 会议讨论 → 裁决 → 文字级修订与验证 | proposal + 账本 + idea | review（评审报告） | 决策级问题定点回流讨论会议；复审轮次超限转人工 |
| 5 | ★评审裁决点 | proposal + review | — | 通过 / 编辑后通过 / 驳回（反馈并入评审） |
| 6 | 需求分析师 | proposal + 账本 | requirement（EARS + AC + 追踪矩阵） | — |
| 7 | 需求确认会议：程序核对 → 语义忠实性核对 → 质量评审 → 汇总裁决 | requirement + 账本 | review（确认报告） | 不通过定点回流分析师；复核轮次超限转人工 |
| 8 | ★需求确认点 | requirement | — | 通过 / 编辑后通过 / 驳回 |
| 9 | 设计师 | requirement | design（固定章节+测试策略章） | ★设计审查门（可配置"产出后自动放行"） |
| 10 | 任务分解器 | design | task.md（DAG+assignee+**质量钩子提议**） | ★任务图人工编辑（增删查改钩子） |
| 11 | QA 测试计划 | requirement+design+task | test.md（AC→TC 全覆盖），**与开发波次并行** | ★测试计划评审（可选，test plan 也要评审） |
| 12 | 编排执行 Wave i（dev₁…devₙ 并行） | task 行+handoff 信封 | 代码+单元测试+运行证据 | 任务级桌检评审（按钩子/抽查） |
| 13 | Wave i 集成 | 该波 dev 产物 | 集成 VERIFY/GATES 结果 + 走查意见 | 失败→缺陷闭环或回流 |
| 14 | 全波完成 → 系统 VERIFY（**全量回归**）→ FTR 正式评审（主席+lens×2-3+记录员，生产者=原 dev 节点） | 全部产物+test.md+执行证据 | 回归结果 + review（FTR 版） | ★FTR 裁决门（阻塞轮次用尽时） |
| 15 | 缺陷闭环（穿插于 12–14）：QA 报告 bug → triage 定级 → dev 修复 → 代码评审 → **QA 回归** → close | test.md+workspace | bugs 工件 | Sev1/2 自动派回；重大缺陷★人工裁决 |
| 16 | ★验收门 | 全部产物+回归证据 | AC 逐条勾选记录 | 通过 / 驳回（批量返工走评审面板） |
| 17 | 部署交付（DEPLOY，可选） | 验收证据 | deployment.md+打包产物+部署证据 | 默认不执行真实部署命令 |
| 18 | 集成交付 | — | changelog+工件归档+记忆沉淀 | — |

不变量：**Agent 可以提议变更，不能批准自己的补丁**；讨论/评审/缺陷轮次均有上限，不收敛交人。步骤 12–15 在依赖图上穿插执行（质量钩子），非严格串行——QA 测试计划与开发并行、集成验证随波触发、回归只在返工/修复后重跑受影响面。

### 6.2 人工门时序

```
编排核 → 建 gate(open) → 事件 gate_requested → SSE → 前端节点变琥珀+卡片
人：approve → gate(approved) → 编排核续跑
人：reject+feedback+target_node → gate(rejected) → 目标节点 attempt+1 重开（携带反馈）→ 其后受影响节点重置 pending
人：edit → 直接 PATCH 工件 → approve
```

### 6.3 返工回流时序

```
VERIFY/GATES 失败 → 事件 node_failed(原因=结构化反馈) → 按 artifact.created_by_node 定位负责人
→ 自动重开该节点（attempt+1, 上下文附反馈） → ≤3 次 → 超限转 HUMAN_GATE
```

### 6.4 断点恢复时序（两级）

- **挂起态恢复（W1 必做，约 2-3 小时）**：杀在 waiting_human（人工门挂起）→ 重启 → 重启扫描不动 gate（原样保留）→ ready 节点重排队 → 通过续跑 → SSE 快照对齐。门本来就是 DB 态，几乎是 D2 恢复骨架的免费副产品。
- **运行态恢复（加分）**：并行执行中杀 → running 节点未回执 attempt 作废重跑（需处理流式中断与部分写回，这是那 1 天的工作量）。
- 共同基础：全部状态在 DB+事件表，节点执行幂等（attempt 号+工件版本）。

### 6.5 会议的挂起、续开与定点回流时序

```
会议运行器 → 遇到人工确认点 → 建门(open) → 事件 gate_requested → 运行器返回，节点 waiting_human
人/模型：做出决定 → 门(decided) → 节点回 pending → 编排器续调度 → 运行器读取决定，从挂起处继续
评审会议 → 结论为退回 → 执行结果带回流指令 → 编排器定点重开讨论会议（带反馈），评审会议轮次+1
讨论会议：带着反馈续开并复议 → 方案出新版本 → 评审会议增量复审 → …… → 轮次超限转人工
```

续开与重开的判定、插话、恢复见[会议式流程设计 §6](./想法到需求确认-会议式流程设计.md)。

## 8 安全与边界

- **命令执行**：workspace 目录隔离+超时+输出截断；M2 评估 docker；禁止 run_command 逃逸出 run 目录（路径校验）。
- **密钥**：api_key 加密存储（Fernet+本机密钥文件）、响应脱敏、日志/工件/trace 中强制脱敏。
- **注入防护**：记忆与搜索结果只作背景信息，不进系统指令位；工件中"忽略之前指令"类文本不提权。
- **成本**：run 预算+节点上限+分级用模（小模型抽取/判决、强模型评审）；node_attempts 记账。
