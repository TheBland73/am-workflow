## 1 目标与现状缺口

产品愿景是"自动化覆盖软件开发从 idea 到测试通过、部署落地的全流程"。现状（W1 末）：

| 已有 | 缺口 |
|---|---|
| Plan Run 的单视角静态评审（REVIEW 节点）+ 阻塞回退 + 验收门 + 评审指标 | 末端单点：`verify → review → gate_accept`，评审不穿插；单 lens：一个评审 agent 拿 workspace 文本摘要 |
| 模板 Run 的 5 个人工门 | 无任何 agent 评审节点；需求/设计/方案只有人审 |
| `test` 工件类型已注册，task.md 有 `test-cases` 元数据 | 没有任何节点产出 test.md；无 QA 角色；测试=dev 自写 unittest |
| verify 节点（退出码判定）+ 返工回退 | 无缺陷概念（只有 pass/fail）；无回归策略；无 bug 状态机 |
| 依赖调度（`gather(min-wave batch)`） | 隐式批内屏障：下游不等"依赖就绪"而等同批最慢者，穿插钩子无法及时触发 |

设计依据一句话概括：**SEPA《软件工程：实践者的研究方法》第 15 章给出"评审必须前置、分级、有 checklist、有角色分工"，微软产品周期的测试实践给出"测试从设计期介入、QA 独立于 dev、bug 走状态机"，《深入理解 AI Agent》第 10 章给出"评审方必须拿独立证据、同质意见不算独立证据、模型不能批准自己的完成"**。三者合并成下文体系。

## 3 三级评审体系

### 3.1 分级定义

| 级别 | 名称 | 参与者 | 触发 | 成本 | 对应方法论（SEPA） |
|---|---|---|---|---|---|
| desk | 桌检 desk-check | 1 个 lens 评审员 | 任务完成即触发（按质量钩子或抽查率） | 低（1 次非工具调用） | 非正式评审 |
| walk | 波次走查 walkthrough | 2 个 lens 并行 + 记录员聚合 | 每波集成 VERIFY 通过后触发 | 中 | 走查 |
| ftr | 正式评审 FTR | 主席 + lens×2-3 + 记录员；生产者=原 dev 节点 | 全部波次完成、系统回归通过后触发 | 高（会议式多轮） | FTR/inspection |

**工件类评审**：方案（proposal）与需求规格（requirement）的评审由前半段的评审会议与需求确认会议承担，设计见[会议式流程设计](./想法到需求确认-会议式流程设计.md) §8、§9。设计规格（design）进入人工门前的评审沿用本文的 lens 评审（lens×3 并行 + 主席聚合，产出统一 review 工件），**裁决动作并入设计审查门**：默认评审意见与人工裁决同卡呈现、不新增独立门；L1（全程人审）下可拆为独立裁决门。模板 Run 与 Plan Run 共用同一套分级机制（双轨统一，钩子字段一致）。

**实现载体**：desk/walk 用 `REVIEW` 节点（单 lens / 2 lens + 聚合），design 的 lens×3 也用 `REVIEW` + 主席聚合，三者都不套 FTR 五步；只有 ftr 用 `REVIEW_MEETING`（后续迁移到 `MEETING` 的 ftr 协议）。

**分级推断规则**（分解器提议、程序固化、人工可改）：

```
默认 review 等级 =
  核心路径任务（关键路径上 / 波次 1）→ walk
  高风险（改动共享文件数 > 2 / 无依赖下游多）→ ftr（进入最终 FTR 而非独立会议）
  其余 → desk
  抽查模式（L3 自动化等级）→ 按抽查率 p（默认 0.3）随机升级 desk→walk
```

### 3.2 FTR 评审会议（REVIEW_MEETING 节点执行器）

后续迭代新增节点类型 `REVIEW_MEETING`，执行器按 SEPA 五步协议编排（planning→preparation→meeting→rework→followup；轮次上限 `max_rounds` 默认 2，用尽升级 HUMAN_GATE）：

```
① planning   主席：读工件就绪检查（规模/依赖齐否）→ 选 lens 组合 → 给每个 lens 分发 checklist + 独立证据包
② preparation lens×N 并行独立评审（互不可见发言，防锚定），各产出结构化发现（issues[]）
③ meeting    记录员：聚合 N 份发现 → 去重（按 file+message 相似）→ 定级 → 主席 1-2 轮复核发言
             （每轮主席可追问具体 lens，限制争论：只阐明问题不现场解决）
④ rework     blocker/major 按 task_uid 定向回流目标 dev 节点（attempt+1 + 反馈注入），复用现有 reject 机制
⑤ followup   增量重审：只读该轮 delta（改动文件+上轮 issues 清单），verdict 更新为工件状态（approved/draft）
```

**参与者身份与上下文**：

| 角色 | 实现 | 上下文注入 | 纪律（系统提示词硬约束） |
|---|---|---|---|
| 生产者 Producer | **复用原 dev 节点**（不新建 agent）：回流时 attempt+1，反馈注入 | 原任务上下文完整保留（messages 表续聊） | 收到评审反馈后修订，不自评通过 |
| 评审主席 Leader | `review_leader` 角色模板 | 工件清单+规模+AC 摘要+lens 组合配置 | 只组织与裁决，不亲自评审；最强可用模型（书 ch10：Manager 是瓶颈） |
| lens 评审员 ×2-3 | `review` 模板 + lens 变体 | checklist + **独立证据包**（见 §3.3） | 只读不改；每条 issue 必须带定位（task_uid/file）与 verify_hint；不见证据不下结论 |
| 记录员 Recorder | `recorder` 模板（或 facilitator 兼任） | N 份 lens 发现原文 | 聚合去重定级，保留分歧不抹平；产出统一工件 |

**关键取舍——生产者是否复用原节点**：复用。理由：① 上下文经济（书 ch10 移交包三要素：传引用不传内容，原节点上下文最厚）；② 现有 reject/feedback 注入机制直接可用；③ 评审反馈直达负责人，不沿管道回传。评审员不复用任何节点（独立性，CodeRabbit 原则）。

**实现载体**：`REVIEW_MEETING` 后续可以建在前半段设计的会议节点类型上（`MEETING`，见[会议式流程设计 §6](./想法到需求确认-会议式流程设计.md)），FTR 的五步协议作为一种会议协议；本期不迁移，前半段只交付 `MEETING`，代码侧正式评审会议仍按本文的 FTR 设计，迁移评估见该文 §15.2。

### 3.3 独立证据包（P9 的落地）

每个 lens 的证据包按 lens 类型差异化（防止趋同，P10）：

| lens | 证据包 | checklist 重点 |
|---|---|---|
| correctness 正确性 | 任务的 AC 清单 + verify 退出码与输出 + 相关源文件 | AC 逐条对照；边界条件；空值与资源释放 |
| test_coverage 测试面 | test.md 相关 TC + 测试代码 + 测试运行输出 | 是否存在"只写断言不验证行为"；负例覆盖（网络/超时/非法输入/权限不足——微软测试员三件事之负例） |
| security_safety | 文件清单（限协议/密钥/注入相关）+ run_command 历史 | 输入验证；密钥脱敏；路径逃逸 |
| consistency 一致性 | design.md 对应章节 + 需求条目 | 实现与规格偏差；命名与接口一致 |
| performance（可选，仅 ftr） | 运行耗时 metrics | 明显低效模式；复杂度异常 |

证据包构造规则：文本文件最多 16 个 / 单文件 5000 字 / 总 26000 字（沿用现有 review 执行器约束），**但每个 lens 的文件子集按其 checklist 相关性筛选，而非同一份摘要**——这是与迭代二期评审的本质区别（单一摘要=单一视角=趋同）。

### 3.4 统一 review 工件 schema

沿用并扩展现有 review 工件（`status: approved|draft`；零发现合法）：

```json
{
  "verdict": "pass | block",
  "level": "desk | walk | ftr",
  "round": 1,
  "summary": "一句话结论",
  "checklist": {"AC-1": "pass", "AC-2": "fail", "...": "..."},
  "issues": [
    {"severity": "blocker|major|minor", "task_uid": "T3", "file": "src/foo.py",
     "message": "问题", "suggestion": "怎么改", "verify_hint": "如何验证修复",
     "lens": "correctness", "status": "open|fixed|wontfix"}
  ],
  "participants": {"leader": "review_leader", "lens": ["correctness", "test_coverage"], "recorder": "recorder"}
}
```

阻塞判定沿用迭代二期：`severity ∈ {blocker, major}` 且带合法 task_uid 才阻塞；`min_blocking_severity` 为节点配置（ftr 默认 major，walk 默认 blocker）。**评审意见质量自检**：major 以上 issue 的 `suggestion` 为空或不可定位时降级为 minor（c-CRAB：不可执行的意见没有价值）。

### 3.5 lens 组合默认值

- 方案与需求规格：评审者与检查单见[会议式流程设计](./想法到需求确认-会议式流程设计.md) §8、§9
- design 评审：`completeness 完整性 / testability 可测性 / consistency 一致性`
- 代码 FTR：`correctness / test_coverage / security_safety`（+performance 可选）

lens 数量、组合、每 lens 模型绑定均为节点/模板配置；L1/L2/L3 自动化等级联动 lens 数量与 `min_blocking_severity`（W4 实现前在[设计规格 §10 第 4 条](./设计规格说明书.md)拍板默认值）。

### 3.6 评审指标与规则沉淀

指标（扩展 `metrics.review`）：缺陷密度 `DD = Errtot / WPS`（WPS=评审文件数或代码行数）、一次通过率、平均返工轮次、**低发现率告警**（按历史 DD 预估应发现数，实际 <40% 时提示"评审可能不彻底"——SEPA Example I 的用法）、每 lens 发现分布（识别趋同或空转 lens）。

**规则沉淀（Self-Improving）**：人工门裁决"采纳"的 issue，自动写入 L3 平台规范记忆（scope=global，kind=procedural，subject=`review-rule/<checklist 项>`，evidence=原 issue）；下次评审 checklist 动态拼入这些规则。人工可在记忆面板下架规则——写入走人审，符合"越能长期影响 agent 的信息写入门禁越严"。

## 4 测试体系

### 4.1 QA 角色与职责

新增 `qa` 角色模板（与 dev 严格分离，P7）：工具白名单 `read_file / list_files / write_file / run_command / finish`（write 限 `tests/` 目录与工件提交，不改实现代码）。职责：① 任务分解后产出 test.md（测试计划）；② 把 TC 转成可执行测试骨架（`workspace/tests/test_*.py`）；③ 波次集成时执行集成测试；④ 系统回归执行与报告；⑤ 发现失败→走缺陷闭环（§5）。

### 4.2 test.md 格式

见[设计规格 §4.2](./设计规格说明书.md)：TC 行内联元数据 `id / maps(需求|AC) / type / status`。硬校验：**AC→TC 全覆盖**（校验器比对 requirement.md 的 AC 集合与 test.md 的 maps 集合，缺失即 `tc_uncovered` 警告，不阻断提交但进覆盖率指标）。AC 写法支持 Given/When/Then 或 Gherkin（`GIVEN/WHEN/THEN` 场景块）——为 M3 的 BDD 化（Hercules 式"Gherkin in, results out"）留接口，本期不强制。

### 4.3 分层测试映射

| 层 | 执行者 | 挂点 | 判定 |
|---|---|---|---|
| 单元测试 unit | dev（自写自跑，现状保留） | 任务内（dev 提示词已要求） | unittest 退出码 |
| 测试骨架 | qa | test.md 产出后，写 `tests/` 骨架（strict-TDD 模式下先于 dev 完成） | 骨架可运行（预期 fail 或 skip） |
| 集成测试 integration | VERIFY/GATES 节点（`dynamic: true`） | 每波完成后（质量钩子 `verify: wave`） | 退出码 |
| 系统回归 regression | VERIFY（全量 TC） | 全部波次完成后；任何返工/修复后重跑受影响面+全量冒烟 | 退出码 + TC 状态 |
| 验收测试 acceptance | ★验收门（人工）+ AC 勾选记录 | 验收门卡片展示 AC→TC→执行证据三级追溯 | 人工 |

### 4.4 测试计划前置与并行（依赖图）

```
design ──▶ tasks(分解器) ──▶ test.md(qa) ─┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┈┐
                │                      └─(可选) tests/ 骨架     │
                └─▶ expand_exec ──▶ dev₁…devₙ（各波）──▶ 波集成 VERIFY ──▶ 系统回归 VERIFY ──▶ FTR
                                          (默认不依赖 test.md；strict-TDD 时 dev deps 含 tests/ 骨架)
```

默认（并行模式）：qa 的 test.md 节点与首个 dev 波同时就绪并行执行；波集成 VERIFY 依赖 test.md + 该波 dev。strict-TDD（任务级开关 `tdd: true`）：qa 先产该任务相关 TC 的失败测试骨架，dev 的 deps 指向骨架节点——红→绿进事件流。**TDD 是任务级选项不是全局强制**（开源实践共识：AI 常写"永远为真"的测试，独立验收不可省）。

### 4.5 变异测试（M3 加分项）

测试质量门禁：对 `tests/` 目录跑 mutmut（Python 生态现成），**新测试须杀死 ≥N 个种子 mutant**（N 默认 3，可配）；变异得分进评测面板。只看覆盖率不够——"覆盖率只证明执行到，变异杀死率才证明测得对"（Meta 2501.12862）。实现形态：独立 VERIFY 节点变体（`verify_type: mutation`），不进默认流程。

### 4.6 回归策略

- 触发：任何 dev 节点因评审/缺陷回流重跑后，其所在波集成 VERIFY 重跑；FTR 阻塞回退后系统回归全量重跑。
- 范围分级：受影响任务直系 TC（按 task-cases 映射）全跑 + 其余 TC 跑冒烟子集（`type=acceptance` 或标记 `smoke` 的 TC）——避免每轮全量导致循环超限。
- 回归失败即重开对应缺陷（§5.2），不允许静默通过。

## 5 缺陷闭环

### 5.1 数据

`defects` 表（[设计规格 §4.1](./设计规格说明书.md)）+ `bugs` 工件（人读汇总，QA 在回归轮末统一写出；sidecar `bugs.json` 供前端面板）。bug 条目字段对齐微软 Bug 报告规范：symptom / fault 假设 / root cause 假设 / severity(1/2/3) / steps[] / expected / actual / 关联 task_uid 与 TC。

### 5.2 状态机与 triage

```
QA 发现 verify/TC 失败 → bug_opened(severity 由失败面推断: 崩溃/数据=1, 功能错=2, 轻微=3; QA 可改)
  → triage（程序规则，非 LLM）:
      Sev1/2 → 自动派回对应 dev 节点（attempt+1, 反馈=bug 条目）      [bug_assigned]
      Sev3   → 记录不阻塞，进 changelog 已知限制
  → dev 修复（bug_fixed）→ 波集成 VERIFY 重跑 → QA 回归（bug_retested）
      通过 → bug_closed；回归失败 → bug_reopened（轮次 +1，≤3 轮→升级人工门）
```

**双 agent 分工**（微软 Auto Triage 模式）：报告=qa；复测=qa（同一角色不同 attempt，独立证据=新退出码）；修复=dev。**PM 角色在 bug 上不做 triage**——课程规模用程序规则（severity→路由）比 LLM triage 可靠且零成本；severity 模型自报仅作参考，以失败面客观特征校准（Sev1=崩溃/数据丢失/安全问题，Sev2=部分功能阻塞，Sev3=轻微）。

### 5.3 指标

缺陷密度（bug 数/千行）、修复均值时长、回归重开率、缺陷逃逸率（验收门后发现=escape，交付前发现=error 的经典区分）——进 `metrics.defects`，优化评估直接取数。

## 6 质量钩子（穿插机制）

### 6.1 字段与解析

task.md 行新增 `review: off|desk|walk|ftr`（可空）与 `verify: <命令>`（可空）两个可选元数据；`engine/tasks.py` 解析进 Task 行（缺省=推断规则 §3.1）。plan_tasks 同步加列，PM 提案 JSON 增加可选字段 `review_level`（模型可提议，程序按 §3.1 覆盖，人可改）——保持"模型提案，程序判定，人确认"纪律：**钩子的执行形态（节点生成）永远由程序决定**。

### 6.2 节点物化（提交运行时）

按钩子展开执行图：

```
dev_Ti done ──▶ [review=desk] desk_review_Ti（VERIFY 变体: 1 lens 非工具调用）
            └─▶ [verify=cmd]   task_verify_Ti（GATES 变体）
Wave 完成且波内任务均含 walk/ftr 钩子或波配置 walk ──▶ wave_walk_Wi（lens×2+recorder）
全部波完成 ──▶ system_verify(全量回归) ──▶ ftr_review(如存在 ftr 钩子或 run 配置开启) ──▶ gate_accept
```

钩子节点复用现有节点类型实现（desk/walk/design=REVIEW、ftr=REVIEW_MEETING、task_verify=VERIFY/GATES），不新增执行器骨架——**机制收敛，等级只是参数**。

### 6.3 双轨统一

模板 Run（sdlc_v1）与 Plan Run 共用 §6.1/6.2：模板在 `templates/sdlc_workflow.json` 的 verify/review 节点配置即钩子默认值；Plan Run 从 plan_tasks 钩子列物化。迭代二期文档中"模板 Run 与计划 Run 相互独立"的边界就此消除。

## 7 调度改造

### 7.1 拆批内屏障（M1 必做）

`orchestrator` 调度循环从「每轮取 min-wave 批 gather」改为「**依赖就绪即跑**：就绪集合逐个经全局信号量派发，节点完成回调唤醒调度迭代（`asyncio.Event`）；波次分层仅保留为画布列与并行度估算」。验收标准：同波两任务 T1/T2，T3(deps=T1) 必须在 T2 未完成时即可启动（新增 `test_no_batch_barrier` 用例：T2 设长超时、断言 T3 先于 T2 完成进入 running）。同步修正 README §4.1 表述。

### 7.2 RESTORE / CHECKPOINT 落地（M1 收口）

W1 中两者为存根。落地最小实现：CHECKPOINT 写 `run_state_snapshots`（受影响节点集合+状态摘要，一个 JSON 行）；RESTORE 按快照把受影响节点回 pending、attempt 保留审计。用于：需求变更回流（老师"扩展考虑(1)"的前置）与大规模缺陷批回退。

### 7.3 与可靠性机制的关系

钩子节点继承现有 attempt 心跳/超时/退避/预算（无特例）；REVIEW_MEETING 内部多 agent 调用受同一 attempt 超时约束（`timeout_s` 默认 900 不变，ftr 建议 1200）。

## 9 分期排期（对齐 6 周计划剩余 5 周）

| 周 | 内容 | 验收 |
|---|---|---|
| W2–W3 | QA 角色+test.md 节点（AC→TC 校验）、defects 表+triage+回归重开、**调度拆屏障**、钩子字段解析与物化 | mock 模型跑通"分解→test.md 与 dev 并行→波集成→缺陷闭环一轮"；`test_no_batch_barrier` 通过 |
| W4 | 三级评审落地（desk/walk/ftr）+ 需求/设计 lens 评审 + lens 差异化证据包 + FTR 裁决门 | 真实模型一次 run：FTR 发现≥1 个真问题并定向回流成功 |
| W5 | 评审规则沉淀入 L3、DEPLOY 节点、指标面板（DD/一次通过/回归轮次/缺陷逃逸）、AC 追溯视图 | 规则注入前后评审发现率对比有数据 |

## 10 验收清单（本体系整体）

- [ ] 测试计划前置：test.md 在首个 dev 波运行期间产出（事件时间戳交叉）
- [ ] AC→TC 覆盖校验：缺 TC 的 AC 产生 `tc_uncovered` 警告
- [ ] 缺陷闭环：注入一个必挂任务（反馈故意误导），观察 Sev1 自动派回→修复→回归→close 全链事件
- [ ] 三级评审各演示一次：desk（抽查触发）/ walk（波后）/ ftr（终审），review 工件 level/round 字段正确
- [ ] lens 证据差异化：三个 lens 的输入文件子集不相同（事件或日志可证）
- [ ] 阻塞阈值：`min_blocking_severity=blocker` 时 major 不触发回流
- [ ] 回归：返工后只重跑受影响面+冒烟，事件 `regression_started` 带原因
- [ ] 规则沉淀：采纳的 issue 出现在 L3 记忆并在下次评审提示词可见
