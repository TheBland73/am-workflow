# 评审与验收门（迭代二期）

> 目标：让「计划 → 提交运行」这条链路具备可解释、可回退、可度量的质量关口。
> 范围：代码评审 Agent（REVIEW 节点）、阻塞自动回退、验收人工门、运行页评审面板、评审指标。
> 不包含：可配置评审关卡（每任务后 / 每波后）、真实 diff/AST 分析、跨 worktree 评审。

## 1. 为什么补这一层

计划 Run 原先的终态是 `verify` 通过即结束：

- 没有人工确认，测试通过不等于交付可接受；
- 没有代码级评审，任务完成度靠 `finish` 自述；
- 失败只能整节点重跑，缺少“按问题定向返工”的能力；
- 运行指标只有耗时/Token，没有质量维度。

因此追加 `review` → `gate_accept` 两段，并把评审结果结构化到运行页与 metrics。

## 2. 节点编排

```text
dev_T1 … dev_Tn ──▶ verify ──▶ review ──▶ gate_accept ──▶ finished
                        │          │
                        │          └─ 阻塞：对应 dev_*/verify/review 回 pending，最多 2 轮
                        └─ 失败：沿用原有重试/升级人工门
```

提交计划（`POST /plans/{id}/commit`，`mode=run`）时新增两个开关，默认开启：

| 字段 | 默认 | 作用 |
| --- | --- | --- |
| `review` | `true` | 追加 `review`（REVIEW）节点 |
| `accept_gate` | `true` | 追加 `gate_accept`（HUMAN_GATE）节点 |

REVIEW 节点配置：

```json
{
  "task_uids": ["T1", "T2"],
  "max_rounds": 2,
  "round": 1,
  "artifact": "review",
  "kind": "plan_review",
  "timeout_s": 600
}
```

## 3. 评审执行器

`backend/app/engine/runners.py::_run_review`：

1. 读 run 的 `Task`（uid / 标题 / 验收项 / 角色）与派发时写入的 `description`；
2. 读 workspace 摘要：文本文件最多 16 个、单文件 5,000 字、总计 26,000 字；跳过 `.git`、`node_modules`、
   虚拟环境、`dist/build`、`__pycache__` 与二进制；
3. 拼提示词：idea、轮次、任务验收表、verify 已通过、workspace 摘要、上一轮 feedback；
4. 用 `review` 角色模型（未绑定回退 `dev`）做一次非工具调用，温度 0.2；要求只输出：

```json
{
  "verdict": "pass | block",
  "summary": "一句话结论",
  "issues": [
    {"severity": "blocker | major | minor", "task_uid": "T3",
     "file": "src/foo.py", "message": "问题", "suggestion": "怎么改"}
  ]
}
```

5. 规范化：severity 白名单；`task_uid` 必须存在于本 run；文本截断；`blocker/major` 且带合法 `task_uid`
   记为 blocking；
6. 写 `review` 工件：通过 `status=approved`，阻塞 `status=draft`；同时把结构化报告写入
   `Node.config_json.review`，历史追加到 `review_history`（保留 8 条）。

## 4. 阻塞回退

`backend/app/engine/orchestrator.py::_handle_review_block`：

- `targets = 报告 targets ∩ run 内 dev_* 节点`；为空时退回所有已完成的 dev 节点；
- 未超轮次：`review` 回 `pending`、`round += 1`、feedback=评审摘要；目标 `dev_*`、`verify`
  回 `pending` 并写 feedback；`Task.status = pending`；发 `review_blocked` 事件；
- 轮次用尽：`review` 置 `waiting_human` + escalation，开人工门，发 `review_blocked(escalated=true)`
  与 `gate_requested`。

人工可在运行页勾选问题涉及的任务，追加返工说明，调用
`POST /runs/{id}/review/rework`（仅 `waiting_human` / `failed` 可用）：

```json
{"task_uids": ["T3", "T5"], "feedback": "先修分页上限，再补导出用例"}
```

服务端把选中 dev 节点与 `verify` 回 `pending`，评审 `round += 1` 并注入 feedback，然后唤醒调度器。

## 5. API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/runs/{id}/review` | 结论 / 轮次 / 问题 / targets / can_rework / 报告正文 |
| POST | `/api/runs/{id}/review/rework` | 人工回退选中任务 |
| GET | `/api/runs/{id}/metrics` | 新增 `review` 段：一次通过、返工次数、问题分布、评审均值、逐节点历史 |

`metrics.review` 形状：

```json
{
  "total": 1,
  "verdict": "block",
  "round": 2,
  "max_rounds": 2,
  "first_pass": false,
  "rework_count": 1,
  "blocks": 1,
  "issues": 3,
  "blocking": 2,
  "severities": {"blocker": 1, "major": 1, "minor": 1},
  "avg_review_ms": 85000,
  "nodes": []
}
```

## 6. 运行页

`frontend/src/pages/RunPage.tsx` 在执行图下面增加 `CODE REVIEW` 面板：

- PASS / BLOCK、第 n/m 轮、阻塞数、一次通过、返工次数；
- 问题清单：严重级别 Tag、任务 uid、文件、说明、建议；阻塞项默认勾选（仅 `verdict=block`）；
- 操作：返工说明、查看报告（`review.md` 正文）、回退选中任务；
- 指标行：问题数、阻塞/重要/建议分布、评审均值。

评审节点与验收门也会出现在执行图、运行账本与 STATE 面板中；验收门的卡片标题为「验收确认」。

## 8. 已知边界

- 评审是静态摘要，不做真实 diff/AST/覆盖率分析；
- workspace 摘要按文件名排序取前 16 个文件，超大项目可能漏掉关键文件；
- 阻塞必须带 `task_uid`，模型漏标会放行；
- `max_rounds` 是节点配置（默认 2），暂未暴露为环境变量；
- 验收门是单点门，驳回只重置一个 `target_node`；批量返工走评审面板；
- 与固定 SDLC 模板的 5 道门相互独立：模板 Run 仍走模板门，计划 Run 走 `review → gate_accept`。
