# 迭代记录 · 可靠执行与运行可观测

> 本轮目标：参考高星 workflow / 编排项目，补齐 AM-Workflow 在「节点执行可靠性」与「运行可观测」上的短板。
> 基线：`pytest backend\tests -q` → 26 passed；本轮结束：33 passed；前端 `typecheck` / `build` 通过。

## 1. 参考资料与借鉴点

| 项目 | 参考的机制 | 在本项目中的落地 |
| --- | --- | --- |
| Temporal | `Start-To-Close` 单次 Activity 超时；Activity Heartbeat + Heartbeat Timeout；`RetryPolicy` 指数退避 | 节点 attempt 超时、`heartbeat_at` 心跳列、退避 + 抖动 |
| Airflow | Task 的 `retries` / `retry_delay` / `execution_timeout`；`up_for_retry` 状态 | `max_attempts` + `retry_at` + `config.timeout_s` |
| Prefect | 任务超时与取消语义 | `stop` 时对进行中 attempt 写「未回执」失败收据 |
| LangGraph | Checkpoint / interrupt / resume | 复用现有 SQLite 状态 + `recover()`，未做事件重放 |
| Inngest / Trigger.dev / Hatchet | step 级 checkpoint、幂等重跑、崩溃后续跑 | 列为后续项（需要 attempt 级幂等键与产物校验） |
| Dify / n8n | 节点级可视化配置 | 节点 `config.timeout_s` 覆盖全局超时 |

不照搬的部分：

- **Schedule-To-Start**：单进程、无独立任务队列，节点调度就是内存里的 `ready` 集合，该超时没有落点。
- **事件历史重放**：SQLite + 单进程已能靠节点状态恢复，重放收益低、复杂度高。
- **跨进程租约**：M1 是单 worker 模型；多 worker 需要外部锁或 DB 租约，留给 M2。

## 2. 已实现

### 2.1 并发闸门真正生效

- 原实现每波新建 `asyncio.Semaphore(AM_NODE_CONCURRENCY)`，且配置从未被读取。
- 现为进程级闸门：挂在当前 event loop 上（`orchestrator._slots()`），同一进程内多个 run 共享；
  设置变更后按新上限重建。闸门在创建 attempt **之前**获取，排队节点不会显示 `running`，也不吃超时预算。

### 2.2 节点级超时

- `AM_NODE_TIMEOUT_S`（默认 900，0 表示不限制）；节点 `config.timeout_s` 可覆盖。
- 通过 `asyncio.wait_for` 包住 `execute_node`；超时按可重试失败处理，反馈里写明超时值与覆盖方式。
- 影响面：`AGENT`（含开发任务）、`VERIFY`、`TASKGRAPH` 等所有节点类型；`HUMAN_GATE` 不设超时。

### 2.3 指数退避 + 抖动

- `AM_RETRY_BASE_S`（默认 3）、`AM_RETRY_MAX_S`（默认 60）。
- 第 n 次失败：`ceiling = min(base * 2^(n-1), max(base, max_s))`，实际延迟取 `uniform(ceiling/2, ceiling)`。
- `retry_at` 写入节点 `config_json`，调度循环在等待期间每 5s 重读状态；等待不占并发槽，也不阻塞事件循环。
- 新增事件 `node_retry_scheduled`（`node_key` / `attempt` / `delay_s` / `next_attempt`），前端事件流与快照刷新已接入。

### 2.4 attempt 心跳

- `node_attempts.heartbeat_at` 新列；执行期间每 `AM_HEARTBEAT_S`（默认 15s）刷新一次（仅 `running` 状态）。
- 用途：区分「节点长时间执行」与「进程已死」；`AM_ATTEMPT_STALE_S`（默认 120s）是陈旧阈值，
  `GET /metrics` 用它统计 `stale_attempts`（仍为 running 但心跳早于阈值）。
- 迁移：`init_db()` 发现旧库缺列时执行一次 `ALTER TABLE ... ADD COLUMN`（幂等，只加列）。

### 2.5 取消与停止的收据

- `stop` 取消调度协程时，进行中的 `_run_attempt` 捕获 `CancelledError`：
  当前 attempt 置 `failed`（“运行被取消，attempt 未回执”），节点回 `pending`，再向上抛出。
- 不再出现「进程已退出但节点仍显示 running」的幽灵状态。

### 2.6 事件 seq 热点

- 原来每个事件都要 `SELECT max(seq)`；现为进程内按 run 缓存 `_seq_cache`，加锁分配，
  DB 的 `(run_id, seq)` 唯一约束兜底，冲突时 reload 后重试一次。
- 锁使用 `threading.Lock` 而非 `asyncio.Lock`：临界区全是同步 DB 操作，且不会把锁绑定到某个事件循环
  （测试里多次 `asyncio.run` 也不炸）。

### 2.7 运行指标 API 与前端展示

`GET /api/runs/{run_id}/metrics` 返回：

- `wall_ms`、节点状态计数；
- `execution`：attempts / retries / busy_ms / avg / p95 / max / stale_attempts；
- `usage`：tokens_in / tokens_out / total / estimated_cost（按模型价格估算）；
- `gates`：total / open / approved / rejected / avg_decision_ms / open_wait_ms；
- `events` 计数与 `per_node` 明细（attempts、exec_ms、tokens、last_error）。

前端运行页在「运行状态」面板展示「重试 / 尝试」「单节点 P95」「人工门等待」，并随快照一起轮询刷新。

### 2.8 其它修正

- `AM_MAX_REWORK_ROUNDS` 此前在 README 里存在、代码里硬编码 3，现真正读取环境变量。
- `add_attempt_usage()` 现在同时回写 `attempt.model_id`，指标里的成本估算才有依据。

## 3. 验收

```powershell
# 后端
cd backend; ..\.venv\Scripts\python.exe -m pytest tests -q     # 33 passed

# 前端
cd frontend; npm run typecheck; npm run build
```

手工验证建议：

1. `AM_NODE_TIMEOUT_S=0.05` 启动 API，任选一个 AGENT 节点跑 run，应看到 `节点执行超时` 失败并进入重试/升级门。
2. 观察事件流出现 `node_retry_scheduled`，节点 `config.retry_at` 与退避时间一致。
3. run 结束后访问 `/api/runs/{id}/metrics`，核对 attempts、retries、p95 与门等待时间。

## 4. 后续候选

- attempt 级 checkpoint / 幂等键，支持崩溃后从断点续跑（而非整节点重来）。
- 跨进程租约与心跳仲裁，为多 worker 部署铺路。
- `metrics` 落库或接入 Prometheus，保留历史趋势。
- 事件表按 run 归档，避免长 run 的 `events` 无限增长。
- 前端路由级代码分割（当前单包 ~1.2MB）。
